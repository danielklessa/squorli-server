# apps/server – App server (`@squorli/server`)

Part of the project description. The entry point is the root [AGENTS.md](../../AGENTS.md) (commands, definition of done, cross-cutting conventions, the map of all documentation in its section 0). Whoever changes the server's structure, routes, schema, configuration or pitfalls updates this file in the same step.

Read as well, depending on the task:
- New REST/WS types, `PROTOCOL_VERSION`, a new permission: `packages/protocol/AGENTS.md`.
- Web radio (`src/radio/`, `src/routes/radio.ts`): `docs/features/radio.md`.
- Read states, mutes, the mention counter (`src/routes/readState.ts`): `docs/features/mentions-unread.md`.
- Directory (`src/directory.ts`, phases M6a-M6d, second factor, account page): `docs/features/directory.md`.
- What the clients do with camera/screen permissions (`VIEW_VIDEO`): `apps/web/src/voice/AGENTS.md`.
- AFK detection and AFK channel (`src/hub.ts`, `src/voice/afk.ts`, the AFK parts of `routes/settings.ts` and `livekit/`): `docs/features/afk.md`.
- Smoke test against a test DB (`DIRECTORY_URL=` is not optional): root `AGENTS.md` section 7.

## Structure

  src/index.ts         Entry point: load .env, config, migrations, plugins, routes, static files; POST /api/directory/notify (push after a name change) and POST /api/directory/leave (push: the user asked at the directory to delete their account here; handled synchronously via users/deleteUser.ts, 204 done / 409 founder / 502 directory unreachable)
  src/webManifest.ts   Web app manifest of the browser client for "add to home screen" (`webAppManifest(serverName)`: name "Squorli - <server name>", the Squorli icons under /app-icons/, standalone; tested); served by index.ts as GET /api/manifest.webmanifest (no-cache, a route because of the name). docs/features/home-screen.md

  src/directory.ts     DirectoryClient: server key (server_settings.directory_private_key, generated at first start, published as `serverKey` in /api/health), register() after app.listen (signature + host proof: the directory fetches DIRECTORY_PROOF_URL), Bearer token in memory (24 h, re-register once on 401), syncAll() every 5 min after listen (POST /api/servers/resolve in chunks of 200: changed handles/names saved, voice presence renamed, members broadcast), syncOne() on a push from the directory (POST /api/directory/notify {publicKey} in index.ts, no auth needed: the server re-fetches with its own token), refresh(): on login and on GET /api/me (cached state older than 5 min) look up key -> handle + display name (`?server=PUBLIC_DOMAIN`, 2.5 s timeout, outage tolerated; without a token only the public handle) and cache them in users.handle / users.display_name (server name wins over the global one; none set = local name stays), and since 19 September 2026 the avatar: `users.avatar_url` = `directoryAvatarUrl(DIRECTORY_URL, key, avatarUpdatedAt)` (address of the image at the directory with its cache version, null = none; refresh, syncAll and syncOne treat a changed address like a changed name, so the push after an upload reaches the member list; the image never passes through this server, `Member.avatarUrl`/`Me.avatarUrl` hand the address to the clients); confirmLeave(): POST /api/servers/leave/confirm with the token (200 = the directory had a pending, user-signed deletion for this host and removed it; 404 not_pending), pendingLeaves(): GET /api/servers/leaves, processed at the start of every 5-minute sync (missed pushes)
  src/bootstrap.ts     On startup: settings, roles "Gast" (default: view + voice), "Mitglied", "Admin", category "Allgemein" with #allgemein and lobby, one-time adoption of users without membership
  src/authz.ts         Pure permission logic (outranks, canSetRolesOf = roles of an owner only by the first owner, canTouchRole, canGrant, effectivePermissions), tested
  src/state.ts         Load server state (settings/categories/channels/roles/members), actorOf() = permission context, broadcastStructure()
  src/hub.ts           WebSocket connections per user: online status, broadcast, sendToUser, disconnectUser (kick/ban), disconnectSession (remote logout, close 4011), closeUser (account deleted, close 4012); AFK state: `setIdle(ws, idle)` per connection, a user is AFK once all their connections are idle, when the connection in use closes and only idle ones remain the user turns AFK AFK_AFTER_MS later, `isAfk`, `afkUsers()`, presence listeners also fire on AFK changes; `setStale(ws)` = the client went silent (ws/liveness.ts), counts as idle (tested, hub.test.ts)
  src/auth/            Challenge store, /api/auth/challenge + /verify (ban check, consume invite, set owner, session with device label from the user agent); session.ts: requireSession() (returns sessionId, updates last_used_at throttled), requireMember()
  src/users/           GET/PATCH /api/me (display name; GET refreshes handle + name from the directory when stale and broadcasts members); M6c: GET /api/me/sessions, DELETE /api/me/sessions/:id | /others | /current (device management, remote logout closes the WS with 4011); deleteUser.ts: account deletion requested through the directory (first owner refused as `founder`, confirm at the directory, then delete the `users` row = cascade to sessions/members/roles/bans/messages/attachment rows, attachment files removed, WS close 4012 `account_deleted`, members broadcast)
  src/routes/          readState.ts (GET /api/read-state = per text channel lastReadSeq, latestSeq, unread, mentions, muted plus serverMuted for the member; POST /api/channels/:id/read; PUT /api/channels/:id/mute and PUT /api/me/mute; WS `read.update` and `mute.update` to the member's own connections), settings.ts (/api/state, /api/settings incl. `requireAccount`, `listed`, `description`, `afkChannelId` (a voice channel or null; the new AFK channel loses its radio and its members are silenced at LiveKit) ; every change of name/listed/description/openJoin/icon re-registers at the directory, debounced 1.5 s; server icon: PUT/DELETE /api/settings/icon with MANAGE_SERVER, GET /api/server-icon public, file DATA_DIR/server-icon), channels.ts (categories + channels), roles.ts, members.ts (set roles, kick, bans; PUT /api/members/:id/owner = appoint/revoke owner, only by an owner; moderation: POST /api/members/:id/move, POST /api/members/:id/stream/stop, PUT /api/members/:id/stream), invites.ts, messages.ts (history, send, edit, delete), radio.ts (web radio: stations with MANAGE_SERVER, PUT/DELETE /api/channels/:id/radio with CONTROL_RADIO, PUT .../radio/playback, POST .../radio/advance = next/previous video of a YouTube playlist queue with CONTROL_RADIO, or `ended` reported by a member sitting in that voice channel, which is why the routes get the voice presence; an `ended` single video or last video of a queue turns the radio off, and radio/offline `{ channel }` does the same for a Twitch stream that is over (a radio with nothing left to play, docs/features/radio.md, 20 September 2026); docs/features/radio.md), attachments.ts (upload/download under DATA_DIR, cleanup; @fastify/multipart is registered in index.ts)
  src/livekit/         routes.ts: POST /api/rtc-token (voice channels only, CONNECT_VOICE; URL without /rtc path; canPublishSources: camera/screen only with STREAM_VIDEO; the AFK channel gets a token without publish and subscribe grants). admin.ts: RoomServiceClient for moderation (mute tracks, publish permissions at runtime, `silence` = no publishing and no subscribing for members sitting in a channel that just became the AFK channel). sync.ts: `syncStreamGrants` (pure, tested) / `syncStreamGrantsOf` = the publish grants of members sitting in a voice channel follow a change of their permissions (roles assigned, role edited or deleted, owner status)
  src/voice/           VoicePresence: who is in which voice channel (per WS connection, in-memory); afk.ts `AfkMover` (pure, tested): which absent members have to be moved to the AFK channel now (not out of a channel showing a video, once per absence); index.ts asks it on presence changes, i.e. the moment somebody turns absent, and every 5 s and sends `voice.moved` with `reason: "afk"`
  src/radio/           Web radio: youtube.ts (a video's title and embeddability from YouTube's oEmbed when it is started), idle.ts (turns a radio off once its channel has been empty for two minutes), queue.ts (pure: the next playable video of a YouTube playlist queue; around the ends for a skip by hand, not for a video that ended by itself: behind the last entry the radio turns off), playlist.ts (pure: is it a playlist, first entry of m3u/pls, HLS detection), resolve.ts (fetch a station's playlist when the radio starts; public hosts only, SSRF guard), icy.ts (pure: ICY metadata blocks, StreamTitle, encodings), metadata.ts (`RadioMetadata`: reads "now playing" of the stations somebody is listening to, WS event `radio.meta`); tested
  src/ws/              At the hello the handler puts a member who still sits in a LiveKit room back into the voice presence (`restored` entries of voice/presence.ts, `LivekitAdmin.roomsByIdentity`; after a restart or for clients that do not say their channel again; docs/features/voice-video.md, 18 September 2026) and drops such entries in the heartbeat once the participant is gone. `liveness.ts` (pure, tested): which connections are alive; the handler pings every connection every 30 s, terminates one that was silent for 90 s (a dead connection would keep its voice presence and keep its user from ever turning AFK) and marks one whose client sent nothing for 150 s as stale. GET /api/ws (hello -> welcome with ServerState + voice.state per channel; ping, voice.join/leave, typing, activity = the connection's user is idle or back, see hub.ts). Server -> client additionally voice.moved / voice.stop (moderation; voice.moved with `reason: "afk"` = moved to the AFK channel by the server)
  src/db/schema.ts     Drizzle schema: users (handle, handle_checked_at, avatar_url = address of the directory avatar), sessions (id, label, last_used_at), server_settings (owner_id = first owner, icon_mime, icon_updated_at, directory_private_key = server key for the directory, require_account, listed, description, afk_channel_id = AFK channel with FK set null), members (stream_blocked, is_owner, muted = the member muted this server), channel_mutes, categories, radio_stations, channels (audio_bitrate, audio_stereo, radio_station_id, radio_stream_url, radio_name, radio_started_by, radio_playback, radio_queue = the videos and place of a YouTube playlist), roles, member_roles, invites, bans, messages (bigserial seq), read_states (user + channel -> last_read_seq, docs/features/mentions-unread.md), attachments
  drizzle/             SQL migrations; 0000-0002, 0005-0012, 0014, 0016-0023 generated (0023 adds `channels.radio_queue`; 0022 adds `users.avatar_url`; 0021 drops `afk_move_minutes` of 0020: the time until AFK is fixed, `docs/features/afk.md`), 0003/0004/0013/0015 by hand (`drizzle-kit generate --custom`: permission backfill for STREAM_VIDEO and VIEW_VIDEO, roles Gast/Mitglied, read states of existing members)

  scripts/smoke.mjs    End-to-end smoke test against a running server

## Conventions

- **Checking permissions:** Every protected route fetches `requireMember()` and checks `can(actor, Permission.X)`; effects on other members/roles additionally `outranks()`/`canSetRolesOf()` (PUT /api/members/:id/roles: the first owner may change another owner's roles, nobody else; user's decision, 19 September 2026; the client mirrors the rules in `apps/web/src/memberRank.ts` so the menu only offers what is accepted)/`canTouchRole()`/`canGrant()` from `authz.ts`. The owner is always administrator. Structure changes end with `broadcastStructure()`. Adding a permission and the order in the role editor: `packages/protocol/AGENTS.md`.
- **Media permissions twice:** camera/screen only with `STREAM_VIDEO` and without a block (`members.stream_blocked`, subtracted in `actorOf()`). The client hides the buttons, the app server writes `canPublishSources` into the LiveKit token (microphone always; camera, screen, screen audio only with the permission). LiveKit enforces it; on changes at runtime via `RoomServiceClient.updateParticipant` (`livekit/admin.ts`). **Every route that can change whether a member has `STREAM_VIDEO` must call `syncStreamGrantsOf` (`livekit/sync.ts`) before the structure broadcast** (so far: member roles, owner status, role permissions, role deletion; the stream block and the AFK channel call `setCanStream` themselves). The token's grants are fixed at the join; without the sync the client shows the camera button (it gets the new permissions at once) and LiveKit answers "failed to publish track, insufficient permissions" until the member rejoins (user's report, 18 September 2026).
- **AFK channel takes effect server-side (17 September 2026):** who is absent comes from the clients' `activity` reports (a modified client can only keep its own user present), but the AFK channel itself is enforced: its LiveKit token carries no publish and no subscribe grant, it cannot get a radio (409 `afk_channel`), and the move is the server's `voice.moved`. Details and the user's decisions: `docs/features/afk.md`.
- **Moderation takes effect server-side:** stopping camera/screen = LiveKit `mutePublishedTrack` + WS `voice.stop`; moving = WS `voice.moved` (the client fetches a token for the target channel itself and joins, the server checks that like any join). Only with `MODERATE_VOICE`, never against the owner or oneself, rank must be higher.
- **Owners (several, 14 September 2026):** `server_settings.owner_id` = first owner (at first login, irrevocable), further ones via `members.is_owner` (`PUT /api/members/:id/owner`, owners only, not oneself). `actorOf()` sets `isOwner` from both, the bootstrap marks the first owner in `members` retroactively. Owners always have `ADMINISTRATOR`, rank above every role (`outranks`), cannot be kicked/banned/moderated and are at the very top of the member list. `Member.isOwner` in the protocol; `ServerSettings.ownerId` remains the first one.
- **Only with account (user requirement, 14 September 2026):** `server_settings.require_account` (migration 0011, admin panel > Server, `PATCH /api/settings`). `/api/auth/verify` rejects keys without a directory handle with 403 `account_required`; owners and the very first login are exempt (no lock-out), existing members without a handle are locked out too. If the directory is unreachable, the cached `users.handle` counts. Without `DIRECTORY_URL` the option has no effect and `/api/health` reports `requireAccount: false`; the admin panel disables the checkbox. **Forcing at deployment:** `REQUIRE_ACCOUNT=true|false` in the environment overrides the stored setting (`setRequireAccountForced()` in `state.ts`, applied in `loadSettings()`), `ServerSettings.requireAccountLocked` is then true, `PATCH /api/settings` with `requireAccount` answers 409 `locked_by_config`, the admin panel shows the checkbox disabled with a note. Empty = the admin panel decides. The login screen hides the browser-key path entirely for a key without handle (only "Mit Konto anmelden" remains, with a note); a key with a verified handle is an account and keeps the usual path.
- **Server directory (M6d, 14 September 2026):** the chat server sends `name`, `listed`, `description` (max 200), `openJoin` and `memberCount` with every registration (`ServerRegisterRequest`); the directory fetches the icon itself from `<proofUrl-Basis>/api/server-icon` (host is proven, raster images up to 2 MB, `iconUpdatedAt` stays when the bytes are unchanged) and serves it under `GET /api/servers/<host>/icon`. Clients therefore load server icons only from the directory (`directoryServerIconUrl()`), never from foreign servers. Public listing `GET /api/servers` = servers with `listed` that registered within 3 days. Admin panel > Server: "Im Serververzeichnis auflisten" + Beschreibung (disabled without directory). Changing name/listed/description/openJoin/icon re-registers (debounced 1.5 s, registration limit at the directory is 10/min per IP). Join via link = open the server's own origin.
- **`/api/health` says whether new members need an invite (19 September 2026):** `inviteRequired` = `!settings.openJoin`, so the login shows the invite field from the start. No secret (a sign-in without a code answers `invite_required` anyway) and no `PROTOCOL_VERSION` bump: the client treats a missing field as false (older servers). Checked by the smoke test.
- **Login splash:** server icon and server name from `/api/health` at the top of the login card (fallback: Squorli icon mark and "Squorli"), footer "Betrieben mit Squorli · Version <version>" below the card; `version` comes from `apps/server/package.json` (read at startup, `../package.json` relative to `dist`/`src`, also in the container).
- **Server name and icon:** `/api/health` returns `serverName` and `iconUrl` so that title and favicon are already correct in the login; when logged in, `settings.name`/`settings.iconUrl` apply (live update via `structure`). Icon only as PNG/JPEG/WebP/GIF up to 2 MB (no SVG: could contain scripts and is served same-origin), file `DATA_DIR/server-icon`, URL with `?v=<timestamp>` and `immutable` cache.
- **Database:** Change the schema only in `apps/server/src/db/schema.ts`, then `pnpm db:generate`. Migrations are applied automatically at server start; do not edit generated SQL files by hand.
- **Directory service (M6):** The chat server never depends on the service: handle resolution at login is best effort (timeout 2.5 s, errors only logged), display falls back to the display name or `anon-<key>`. The web client calls the service directly (URL from `/api/health`, CORS open for GET/POST). Registration = signature over the service's host + handle + nonce; one key has exactly one handle, handles are immutable (M6a). The service itself (routes, schema, account page, smoke test) lives in `../squorli-directory` (root `AGENTS.md` section 2a).
- **Device management (M6c):** `sessions.id` is the public identifier (the token stays secret), `label` comes from the User-Agent at login (`labelFromUserAgent`, the client cannot set it), `last_used_at` is written in `resolveSession()` at most every 5 min. Remote logout deletes the row and closes exactly its WebSocket with **Close 4011 `session_revoked`** (`hub.disconnectSession`; kick remains 4010 + `removed`). The client reacts in `store.sessionLost()`: WS close 4011, WS error `unauthorized` and REST 401 with a token set (`api.onUnauthorized`) lead to the login with a message, without reconnect. `store.logout()` calls `DELETE /api/me/sessions/current` (best effort). No `PROTOCOL_VERSION` bump: close codes are not events. The directory knows no devices, only the list of key fetches (`key_fetches`, 90 days, display only): whoever has the key has it.
- **Account deletion through the directory (15 September 2026, user's wish):** a user deletes their account on one server from the directory's account page or via right-click on the server in the rail; both sign the action `server-leave` at the directory. The directory only relays: it pushes `{publicKey}` to `POST /api/directory/leave`, and the server confirms with its own token (`confirmLeave`) before deleting anything, so an unsigned push can at most trigger a check (same principle as `/api/directory/notify`). The first owner (`server_settings.owner_id`) is refused (`founder`), other owners and members are deleted completely (`users` row with cascade, attachment files, WS close 4012, no `removed` event and no `PROTOCOL_VERSION` bump: close codes are not events). Missed pushes are fetched via `pendingLeaves()` in the 5-minute sync. There is no local "delete my account" route on the chat server; the directory is the single entry point (the user's decision).

## Known pitfalls

- **Smoke test without a running server** fails with `ECONNREFUSED`; run `pnpm dev` or `node dist/index.js` first.
- **`PUBLIC_DOMAIN` must match the hostname in the browser address bar exactly** (dev: `localhost`; behind the proxy: `chat.example.org`; access via LAN IP: the IP). Otherwise `POST /api/auth/verify -> 401 (signature_invalid)`. `/api/health` returns `domain`; since the fix, the client shows both values in the error message. The smoke test always signs with `localhost`.
- **Session "logged out from another device" in your own browser:** after "Alle anderen Geraete abmelden" (log out all other devices) or a `DELETE /api/me/sessions/:id`, the session currently in use is kept (`current`); anyone who gets thrown out anyway has two tabs with two sessions of the same key (every login creates a new session; a second tab only shares it via `localStorage`).
- **Schema change while `tsx watch` is running:** the dev server restarts immediately after `schema.ts` is saved, i.e. before `pnpm db:generate` has generated the migration; it then runs against the old schema and queries on new columns fail (server stops responding). After `db:generate`, trigger a second restart (`touch apps/server/src/index.ts`), then the migrations are applied. Check: `SELECT count(*) FROM drizzle.__drizzle_migrations`.
- **Raw SQL with Date parameters** (`sql` + `${new Date()}`) fails in postgres-js; use `now()` in SQL.
- **Attachments are publicly retrievable by ID** (`/api/attachments/<uuid>/<name>`, no token), so that `<img src>` works. Like CDN links on Discord; the UUID is the secret.
- **White screen after deploy, "Expected a JavaScript module ... MIME type text/html":** the browser had the old `index.html` with the old asset hash in its cache. Since the fix: missing files with an extension get a 404 instead of the app shell, `index.html` is served with `cache-control: no-cache`, hashed assets with `immutable`. The user must hard-reload once after the fix. Run `pnpm build` (root) after every client change, otherwise an old client sits in `apps/server/public`. Second cause (fixed): `@fastify/static` ran with `wildcard: false` and registered one route per file at startup; new assets after a build without a restart got a 404. Now `wildcard: true`, files are resolved per request.
- **`Route GET:/ not found` (Fastify 404 on `/`):** the server is running without a built web client. Since the fix, `/` answers with 503 and an explanation; the cause is a start without `pnpm build` (missing `apps/server/public`) or an old Docker image. `/api/health` works regardless.
- **Server icon gone after emptying `apps/server/data`:** the DB still had `icon_mime`, so favicon, sidebar, login and server rail showed a broken image (happened 14 September 2026). Since the fix the settings routes check at startup whether `DATA_DIR/server-icon` exists and otherwise clear the entry with a warning; upload the icon again in Verwaltung > Server. When emptying the data folder, keep `server-icon` or expect this.
- **Fresh database had only the role "Mitglied" (fixed 14 September 2026):** migration 0004 creates "Mitglied" in empty databases as well; since then the bootstrap no longer checks for "no roles" but for "no default role" and creates Gast/Admin/Mitglied individually as needed. Check the fresh-install path: recreate `chat_smoke` from scratch via `DROP DATABASE ... WITH (FORCE)` + `CREATE DATABASE` and run `pnpm smoke` (not only against an incrementally migrated DB).
- **Resetting the dev database** (new owner at the next login): `docker exec squorli-dev-postgres-1 psql -U chat -d postgres -c "DROP DATABASE chat WITH (FORCE)" -c "CREATE DATABASE chat OWNER chat"`, empty `apps/server/data/attachments`, then `touch apps/server/src/index.ts` (migrations + bootstrap run only at startup). The database `directory` in the same container is the old dev database of the directory service (before the move); leave it until the data is taken over into `../squorli-directory`.
- **Only guest after joining:** anyone who cannot write does not yet have the "Mitglied" (member) role. An admin assigns it in the member list (click on the name). This is intended (decision of 13 September 2026), not a bug.
