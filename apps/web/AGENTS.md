# apps/web – Web client (`@squorli/web`)

Part of the project description. The entry point is the root [AGENTS.md](../../AGENTS.md) (commands, definition of done, cross-cutting conventions, the map of all documentation in its section 0). Whoever adds, removes or repurposes a file of the client, or changes a convention or pitfall, updates this file in the same step.

**After every client change:** `pnpm build` from the repo root and tell the user to reload (root `AGENTS.md` section 4, item 7); after a new `<Icon name>` run `pnpm icons`; after a dependency change `pnpm run licenses`.

## Structure

```
apps/web/              Web client: Vite 5 + React 18 + livekit-client. The desktop app (apps/desktop) shows this same build.
  src/identity.ts      Key pair in localStorage (unencrypted; backup at the directory from M6b), identityFromPrivateKey()/storeIdentity() for restoring
  src/api.ts           `ServerApi` class = all REST calls of one chat server (auth with the signature domain as a parameter, profile, sessions, messages, upload, admin), one instance per server with its own token and `base` ("" = the server serving the client, otherwise the origin of a foreign server), `abs()` for relative server URLs (attachments, icon), `onUnauthorized` hook on 401 with a token set; module functions for the directory (directoryLookup, directorySetDisplayName(), directorySearchHandles(), directoryHealth(), ...); ApiError with error code; explainLoginError(err, api, domain)
  src/serverConnection.ts Multi-server client (14 September 2026): `ServerConnection` = one chat server (session, WebSocket with reconnect, ServerState, message cache per channel, presence, typing, unread, log, health data); hooks to the store (state, token, session lost, removed, connected, voice.moved/voice.stop). Remembers the channel of its last `voice.join` and sends it again after every reconnect (the server keeps voice presence per socket, LiveKit outlives it); a heartbeat drops a socket on which nothing arrived between two pings, and `connect()` never leaves an earlier socket open (docs/features/afk.md, 18 September 2026). sessionLost (WS close 4011, WS error unauthorized, REST 401) clears the session with a message; logout() also ends the session server-side
  src/store.ts         UI-free client state: identity, `servers` = `ServerConnState` per server (`homeHost` = host of the address bar = the server serving the client, always present; foreign servers keyed by their directory host, base = `directoryServerUrl()`), `activeHost` = the server shown; `openServer(directoryHost)` switches (and on first use logs in at the foreign server with the browser key, signature over its `/api/health` domain, stored session reused), `retryServer()`, `closeServer()`, `hostFor()` maps a directory host to the store key; sessions per server in localStorage `chat.sessions.v2` (v1 migrated); `homeState()`/`activeState()` helpers; setDirectoryName(); logout() = all servers. M7: second socket to the directory (`directoryLink.ts`, opened by `connectDirectory()` after the directory lookup when the key has an account and the directory reports `features.friends`), `friends`, `conversations` (unread per friend), `dms` (decrypted threads, `Dm.text` null = could not decrypt), `homeOpen`/`currentPeer`, pair-key cache (`deriveDmKey`), actions requestFriend/acceptFriend/declineFriend/removeFriend/blockFriend/unblockFriend, sendDm (seal + send, display via the directory's echo), loadDmHistory, markDmRead, deleteDm, clearDm, searchHandles, friendState() `starting` = still finding out what the first screen is (`init()`, at most 8 s): App.tsx shows `.app-starting` instead of a login or "no server yet" that would only flash by, then calls `platform.window.ready()` (the desktop app's start window makes way; docs/features/desktop.md, 20 September 2026).

Chromium's Gamepad API was tried and only delivers while the window has the focus (docs/features/afk.md, 20/21 September 2026)
  src/gameDetection.ts Game detection of the desktop app (`platform.games`, null in a browser; docs/features/games.md): `GameDetection` keeps per device what belongs to this computer (`chat.games.v1`: hidden ids, added programs; the hidden launcher ids follow the account inside the sealed settings where the directory keeps those: `syncedHidden`, `mergeHidden`, `adoptHidden`, fed by App.tsx from `State.accountHiddenGames` and reported back through `Store.setLocalHiddenGames`), is switched on from outside (`setEnabled`, the account's setting `VoiceSettings.games.enabled`), tells the shell the switch and the programs, and holds the running game and what others may see (`shownGame`); created once in App.tsx, handed to the settings dialog. gamePresence.ts = what goes out (pure, tested): `presenceOf` (a launcher's id only, never an added program's path; the directory's library decides what is a game; one clean line as the name), `directoryGameLookup` (once per id and session, `peek`, a minute's rest after a failure), and what a viewer shows (`shownGameOf`: the directory's name and icon for a launcher's id, nothing for what the directory does not call a game or while its answer is out, else the reported name); App.tsx hands the result to `Store.setGame(game, onServers)`: the directory always, chat servers only with the second switch. GameLine.tsx = the display "Spielt X" with the icon (`GameLibraryContext` from App.tsx, `useShownGame`, `GameLine` with a `fallback`), used by MemberList.tsx (instead of the handle line, and in the menu), Home.tsx (friends list) and DmView.tsx (head). ## Conventions
```

- Server login language choices are visible Deutsch/English buttons with `aria-pressed`, using the resolved locale (saved preference, supported browser language, English fallback) and `store.setLocale()` for safe reloads. The account-creation link occupies a separate row below login choices and explains the configured Directory host/new tab.

- **Server login clarity (19 September 2026):** `LoginScreen.tsx` shows exclusive account sign-in and local-access views (`loginView.ts`, tested). Account creation is an external link to `state.directoryUrl`; do not reintroduce a registration form. Existing verified accounts without a backup retain password setup with `PasswordInput.tsx`. Key/discard details stay collapsed. `.server-login` scopes layout changes. Notes: `docs/features/directory.md`.

- **Never reload the page for the language directly (18 September 2026):** go through `store.reloadForLocale()`; it waits while a voice connection runs, because a reload throws the user out of their channel (docs/features/settings.md). The same goes for any other reload added later.
- **The desktop app words some texts differently (18 September 2026):** a text that says "this browser", "this tab", "the page" or names a browser permission gets a second wording in `src/i18n/app.de.ts` AND `app.en.ts` (only the keys that differ, same placeholders; `index.test.ts` checks both). `t()`/`tOr()` take those first while running in the app (`lookupText`, recognised by `window.squorliDesktop`). Components never choose between two keys for this; a separate key is right only when the app says something else altogether (`settings.idleHintApp`, `voice.screenNoAudioApp`). When writing a new text, ask whether it is true in the app.
- **UI texts are bilingual German/English (user decision, 15 September 2026):** every text a user sees in the web client comes from the catalogs `apps/web/src/i18n/de.ts` (reference, all keys) and `en.ts` (same keys, enforced by the `Messages` type and the test) via `t("key", { params })`; never write a literal German or English sentence in a component, an error mapping or the voice core. The locale is fixed at page load: an explicit choice in `localStorage` (`chat.locale`, select in the login footer and in Einstellungen > Ansicht; with a directory account it follows the account, see `docs/features/settings.md`) wins, otherwise the first entry of `navigator.languages` we support, otherwise English. Dates use `fmtDateTime`/`fmtTime`/`fmtDay` from the i18n module (`localeTag`). The 503 page of the server picks German or English from `Accept-Language` (`preferredLanguage()` in `src/index.ts`). **Everything a user sees carries real umlauts** (ä/ö/ü/ß) in the German catalog (user requirement 13 September 2026); the ae/oe/ue transliteration is used only in comments, identifiers and developer log lines. `PERMISSION_LABELS` in the protocol package stays German and is no longer used by the client (labels come from the `perm.*` keys).
- **Symbols only via `<Icon name="…"/>`** (Lucide web font, ISC license, self-hosted under `apps/web/src/icons/`), no emojis and no Unicode arrows in the UI (user requirement: uniform, white, license-free). Emoji as chat content and as the things to choose in the emoji picker (including its skin tone samples) are content, not UI symbols; the picker's own controls use `<Icon>`. Color = `currentColor`, size = `font-size`. Look up new names at https://lucide.dev/icons, then `pnpm icons`. Hang up = `phone` rotated by 135 degrees, white on red.
- **User settings follow the directory account, the device selection does not (17 September 2026):** a new user-level setting goes into `VoiceSettings` (or its own per-device store), into the protocol's `AccountSettings` **with a default** (older stored objects and older clients must stay valid; copy `directory.ts` to `../squorli-directory`), into `accountSettings.ts` (all three functions) and into `SettingsDialog.tsx`. Device ids never go into the account. **The account's copy is sealed (21 September 2026):** where the directory reports `features.settingsSealed` the store encrypts the settings with a key from the identity's seed before they leave the client and writes nothing in the open (`docs/features/settings.md`); something that must not be readable by the directory's operator (the game display's hide list) goes into `SealedSettingsContent` next to `settings`, never into `AccountSettings`, which older directories still store in the open. Never add a second settings dialog: everything a user sets for themselves is reachable through the gear.
- **Categorized modals: categories always on the left** (user requirement 13 September 2026, applies without instruction to the contrary to all future modals with several sections). Building blocks: `.modal` > `.modal-head` (title, `.spacer`, close) + `.settings-layout` (`.settings-nav` on the left with `<Icon>` + label, `.settings-body` on the right). Examples: settings (`SettingsDialog.tsx`) and admin panel (`AdminPanel.tsx`). No tab bar at the top.
- **No browser dialogs in the client:** `alert`, `confirm`, `prompt` are taboo (user requirement). Confirmations via `askConfirm()`, text inputs via `askInput()` from `apps/web/src/dialogs.tsx`; both return promises and render their own modal (z-index above admin panel/profile). Show errors inline as `.error` text, not as a popup.
- **Browser or desktop app: one build, differences only through `platform` (18 September 2026, user's decision):** the desktop app ships exactly this client's `dist`. Never branch on the user agent or on `window.squorliDesktop` in a component; ask `platform` (`src/platform/`) and extend its interface when something new differs. `Store` and `VoiceClient` stay free of platform imports and take what they need as constructor arguments. `window.location` is only right where the page's real origin is meant (embeds, `postMessage`, URL parameters); what means "the server that serves the page" comes from `platform.home`, which the desktop app does not have. `bridge.ts` and `deepLink.ts` must stay DOM-free (the Electron main process bundles them).
- **The client may have no home server (desktop app, 18 September 2026):** `state.homeHost`, `state.activeHost`, `homeState()`, `activeState()`, `store.home` and `store.active` can be null. Code that means "the server on screen" uses `view` in App.tsx (`{ active, conn, server }` or null); code for the home server checks for null and must leave the browser's behaviour alone. New store features that assume a home server need a branch for `homeHost === null`. A server the key has never been on is never signed in to without a click (join view).
- **Multi-server client (14 September 2026, user's requirement):** the web client of one server talks to other Squorli servers directly (`ServerApi` with `base` = their origin, WebSocket `wss://<host>/api/ws`, LiveKit URL from their `/api/rtc-token`). The rail switches the shown server without leaving the page; the voice connection stays on its server until the user joins a voice channel on another server, which disconnects the previous one. Login at a foreign server = the same browser key, signature over that server's `/api/health` domain, no invite (the rail only lists servers the handle is a member of); its session token is kept per host. Consequences: every chat server answers CORS for **all origins** (`@fastify/cors` `origin: true`, auth is Bearer-only, no cookies, so a foreign origin cannot act without the token; the signature stays bound to `PUBLIC_DOMAIN`), relative server URLs (attachments, icon) are resolved through `api.abs()`, older servers without CORS show "nicht erreichbar oder erlaubt keinen Zugriff aus anderen Clients" with a link to open them directly. The admin panel, settings dialog (sessions, name on this server; the mini profile too), member list and chat always act on the active server. Not multi-server: the login screen, the directory account and the friends/DM view (they belong to the own server's directory).

## Known pitfalls

- **`@types/dom-mediacapture-transform`** is a peer dependency of `@livekit/track-processors` (types for MediaStreamTrackProcessor); as a devDependency in the web package, otherwise `tsc` breaks.
- Old client after a change, white screen after a deploy, `Route GET:/ not found`: `apps/server/AGENTS.md` pitfalls (static serving). Browser audio, output devices, screen share without audio: `src/voice/AGENTS.md`.

## Mobile navigation (19 September 2026)

At widths up to 700 px, App.tsx owns the navigation/content state. The rail and channel/friend list fill the height; text/DM content slides over them with a back button. MobileVoicePreview.tsx is a native bottom dialog showing server voice presence before an explicit join. Voice stays in the existing VoiceClient when the stage is minimized; VoiceDock restores it. Keep desktop rendering and direct voice-channel joining unchanged. Layout and animation use existing brand tokens; respect reduced motion.

Mobile zoom policy (19 September 2026, user request): index.html fixes the viewport scale; styles.css allows panning without pinch zoom up to 700 px and keeps form controls at least 16 px to prevent focus zoom. Desktop CSS is unchanged.

Mobile settings (19 September 2026): settings-backdrop/settings-modal scoped rules make the settings full-viewport at <=700 px. Categories stay on the left as icon/label buttons; navigation and body scroll independently. Keep mobile changes scoped so desktop and admin dialogs retain their layout.

Mobile administration (19 September 2026): admin-backdrop/admin-modal share the mobile settings layout at <=700 px. Categories remain left with icons and labels, both columns scroll independently. Roles, channel creation and channel editor actions stack within the content column; keep desktop grids unchanged.

Dialog opening focus (19 September 2026): SettingsDialog and AdminPanel focus their close button on narrow viewports (<=700 px) or coarse primary pointers; never autofocus a mobile text input. Settings retain desktop profile-input autofocus. Evaluate this policy when the dialog mounts.
