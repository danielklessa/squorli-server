## Conventions

- **Protocol version:** Bump `PROTOCOL_VERSION` in `@squorli/protocol` on incompatible changes (currently 4; new permission bits are not an incompatible change; a new server event is one when clients must understand it, because the client parses events strictly with zod and drops what it cannot parse. An event that older clients may safely miss, such as `read.update`, needs no bump, and a bump is costly: the multi-server client cannot connect to servers of another version); the server rejects other versions with WS code 4002. The constant is also in `apps/server/scripts/smoke.mjs`, update it there too.
- **Feature flags instead of a version bump:** a field the server only sends when it knows a feature (`ServerSettings.radioAutoStop`, `afkChannelId` with null for "none"; the directory's `DirectoryHealth.features.*`) tells the client whether it may use the matching client event or route. A new **client** event needs such a flag, because servers answer unknown client events with `bad_message` (`ClientActivity` is only sent when `afkChannelId` is present, `DirectoryClientActivity` only with `features.afk`).
- **Order and grouping of permissions (user's requirement, 17 September 2026, applies to every permission added from now on):** the role editor shows permissions in groups sorted by meaning (`PERMISSION_GROUPS` in `permissions.ts`: `admin` "Verwaltung" first with `ADMINISTRATOR` at its top (user's decision), then `text` "Kanäle und Nachrichten", `voice` "Sprachkanäle" (until the web radio: "Sprache und Video"), `members` "Mitglieder"; apart from `ADMINISTRATOR` a group runs from everyday to powerful; group titles from the `permGroup.*` keys, rendered as `fieldset.perm-group` in `AdminPanel.tsx`). The bit order is history and never the display order. Whoever adds a permission must sort it into the group and position where it belongs by meaning (next to related ones, e.g. watching before sharing), never simply append it, and must re-check the whole arrangement each time: does a group get too long, does a new group make more sense, are the group titles still accurate. A test in `index.test.ts` fails if a permission is in no group or in two. New permissions: append the bit in `permissions.ts`, add the label (`perm.*` in both catalogs), sort it into `PERMISSION_GROUPS`, and for existing servers write it into the appropriate role via a custom migration (`drizzle-kit generate --custom`) (see 0003/0004 as examples); the bit values are pinned in `index.test.ts`.
- **Key backup (M6b):** The private key leaves the client only encrypted. `packages/protocol/src/backup.ts`: PBKDF2-SHA256 (600,000 iterations, 16-byte salt) -> HKDF into two keys: AES-256-GCM (encrypts the 32-byte seed, stays in the client) and auth key (is sent, the service stores only its SHA-256 in `key_backups.auth_hash`). Storing: `PUT /api/backup`, signed over "community-directory-backup\n<host>\n<nonce>\n<ciphertext>", upsert (= change password). Fetching in two steps: `GET /api/backup/:handle/params` (salt, iterations) -> client derives -> `POST /api/backup/fetch` with auth key -> blob with iv + ciphertext. Wrong password = 401 `auth_invalid`; rate limit `BACKUP_RATE_LIMIT` per IP **and** per handle (default 10/min), uploads have their own window. Password at least `BACKUP_MIN_PASSWORD` (8) characters, checked client-side only; no reset possible (the directory does not know it).
- **Mention scanner:** whoever changes how `apps/web/src/markdown.ts` reads fences, code spans or escapes changes `src/mentions.ts` too (`docs/features/mentions-unread.md`).

## Known pitfalls

- **`@squorli/protocol` has no build:** its entry is `src/index.ts`. The server therefore bundles it into `dist/index.js` via `noExternal`. Anyone who introduces further workspace packages as runtime dependencies of the server must add them to `tsup.config.ts` as well.
