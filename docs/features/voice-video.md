# Feature notes: Voice, camera, screen share, stage

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. Standing rules live in the `AGENTS.md` of the area. Whoever changes the feature adds or updates its entry here in the same step.

Code: `apps/web/src/voice/`, `VoiceStage.tsx`, `VoiceDock.tsx`, `VideoWindows.tsx`, `VideoAudioControls.tsx`, `videoDisplay.ts`, `CameraPicker.tsx`, `UserVolumeControl.tsx`; server `apps/server/src/livekit/`, `apps/server/src/voice/`. Standing rules: `apps/web/src/voice/AGENTS.md`.

**Camera froze in a pop-out on Firefox (18 September 2026, user's report: "wenn auf Firefox die Cam-Übertragung ausgepoppt wird, friert die Kamera in dem neuen Fenster ein"):** LiveKit's adaptiveStream watches every attached `<video>` with ONE `IntersectionObserver` created in the main window (`root: null`, `HTMLElementInfo`). Firefox never reports an element of another window as intersecting (Gecko's implicit root is the observer's own top-level document; Chrome measures against the element's document), so LiveKit took the pop-out's view for invisible, paused the track 100 ms after attaching, and the window kept the first frames. Fix: `PopoutElementInfo` in `videoDisplay.ts` implements LiveKit's exported `ElementInfo` for a view in another window (`visible` always true, the window shows nothing else; size from the element; a `ResizeObserver` of the pop-out's own window so the simulcast layer follows the window's size) and `attachVideoView()` registers it through `track.observeElementInfo()` before `attach()` (LiveKit then skips its own info for the element; `detach()` stops it). Remote tracks only; local tracks have no adaptiveStream. Verified with a Firefox nightly zip (158, unpacked into the scratchpad, headless, popups allowed through `user.js`) and headless Chrome, first with a plain probe (Firefox: main-window observer `isIntersecting: false`, the pop-out's own observer `true`; a main-realm `MediaStream` plays fine in the pop-out), then with a real `RemoteVideoTrack` (canvas stream, `adaptiveStream` on) bundled with esbuild: `track.attach()` -> visibility `true, false` in Firefox (paused), `attachVideoView()` -> stays `true`; Chrome `true` both ways. Not checked: a real LiveKit session in Firefox, release Firefox (the mechanism is old Gecko behaviour, not a nightly detail).

**Tile stayed black after somebody turned their camera off (18 September 2026, user's report: "wenn ein Benutzer seine Cam-Übertragung beendet, passiert es häufig, dass die Kachel schwarz bleibt"):** LiveKit's `setCameraEnabled(false)` does not unpublish the camera, it MUTES the track (it stays published; only screen shares are unpublished). Receivers get `TrackMuted`, and the client answered that only with `refreshParticipants()`, never `refreshTiles()`, although `refreshTiles()` already skipped muted cameras (`!cam.isMuted`). So the tile stayed, showing black, until any other event rebuilt the tiles (a stream-state change, someone joining), which is why it happened "often" and not always. Now `TrackMuted`/`TrackUnmuted` also call `refreshTiles()`; turning the camera back on shows the tile again for the same reason. Own tile was fine (`setCameraEnabled` refreshes explicitly). Checked: typecheck, tests, build; not checked in a real session.

**Joining failed with "Constraints could not be satisfied" and a proxy hint (18 September 2026, user's report from community.k9-kommando.de):** the message is the browser's `OverconstrainedError` from `getUserMedia`, not a connection error: the microphone stored under Einstellungen > Audiogeräte is requested with `deviceId: { exact }`, and the device was gone (unplugged, or the browser handed out new device ids). The join caught every error in one place and wrapped it in `voice.connErrGeneric` ("check /rtc/validate ... the proxy does not forward /rtc"), which sent the operator looking at a proxy that was fine (`/rtc/validate` returned 401 when checked). Now: `openMic()` in `micPipeline.ts` retries without the device when the chosen one is gone (`OverconstrainedError`/`NotFoundError`, recognised by `name` because Chromium's is no `Error` instance), so the default microphone takes over; the stored choice is kept, so the device is used again once it is back, and the settings show the device actually in use (`inputDeviceId` = `activeDeviceId()`); the debug log notes the fallback. This covers the join, the switch in the settings and the republish after a profile change. A microphone that still fails (no permission, no device at all) is reported as `voice.errMic` without the proxy hint; `setInputDevice()` reports it the same way instead of an unhandled rejection; `errorText()` falls back to the error's name when it has no message. The join still ends when the microphone fails (listening without a microphone was not asked for). Checked: `micPipeline.test.ts` (4, fake `getUserMedia`), typecheck, tests, build. Not checked: a real browser with an unplugged device.

**Screen share froze in the pop-out or in fullscreen (17 September 2026, user's report: "manchmal bleibt ein Screenshare hängen, wenn er ausgepoppt oder im Vollscreen ist"):** LiveKit's adaptiveStream pauses EVERY received video five seconds after the MAIN page is hidden (`pauseVideoInBackground`, default on; it only knows `document.visibilityState` of the page that loaded it, a video element in a pop-out window does not count, only Picture-in-Picture does). Hidden is also a main window that is minimized or, on Windows, completely covered by other windows, which is exactly how a pop-out on a second monitor gets used. Now `adaptiveStream: { pauseVideoInBackground: false }` (`voiceClient.ts`) and **each video view decides for its own window**: `TrackVideo` (`VideoWindows.tsx`) detaches its element once its `ownerDocument` has been hidden for 5 s and attaches it again when visible (`videoDisplay.ts` `watchDocumentHidden`, tested); a track without an attached element is paused by adaptiveStream as before, so a hidden tab without pop-outs still receives no video. Verified in headless Chrome over the DevTools protocol with a real `RemoteVideoTrack` (canvas stream) shown in the page and in a pop-out, main window minimized: before, both tracks turned invisible after about 6 s; now only the page's view does and comes back with the window, the pop-out's stays visible throughout. Not checked: a real LiveKit session, Windows' occlusion of a covered (not minimized) window.

**Playback volume per person, 0-200 % (17 September 2026, user's wish):** right-click on a member in a voice channel (sidebar), on their tile in the stage or the member list's menu shows "Lautstärke für mich" with a slider, the percentage and a reset to 100 % (`UserVolumeControl.tsx`); not for yourself. Local playback only, nothing is sent. Stored per device in `chat.userVolumes.v1`, keyed by the person's **public key** so it holds on every server (`voice/userVolumes.ts`, tested; only real adjustments are stored); deliberately not in the directory account, because it depends on the headset in front of this browser and is a map without bound. `VoiceClient.getUserVolume/setUserVolume(publicKey)` also work without a connection; `setPeerKeys` / `JoinOptions.peerKeys` map LiveKit identities to keys (`App.tsx`), bots fall back to `id:<identity>`. Up to 100 % the `<audio>` element's volume does it; above, a `GainNode` on the speaker meter's `MediaStreamAudioSourceNode` plays into the shared `AudioContext` while the element stays attached at volume 0 (Chromium feeds a remote stream into Web Audio only while an element plays it). Consequences: deafening sets that gain to 0 (`setDeafened` -> `applyUserVolumes`), a context that is not running falls back to 100 % instead of silence (re-applied on `statechange`), and the boosted voice follows the voice output device only where `AudioContext.setSinkId` exists (Chromium; elsewhere the system default). The volume control of a camera pop-out is the same per-person value (slider to 200 % there, screen audio stays 0-100 %). `ContextMenu` arrow navigation includes `[data-menu-item]` (the slider). Typecheck, all tests and build green; not checked in a browser with real audio.

**Permission to watch camera and screen (17 September 2026, user's requirement):** new role permission `VIEW_VIDEO` ("Kamera- und Bildschirmübertragungen sehen" / "Watch camera and screen shares", Admin > Roles). A member whose roles do not carry it hears the voice channel but receives no camera, no screen share and no screen audio; the stage shows avatars and a notice while somebody is sharing. **Guests do not have it (user's decision):** the default role "Gast" comes without it on fresh servers (`DEFAULT_EVERYONE_PERMISSIONS` unchanged = 1152), "Mitglied" has it (`DEFAULT_MEMBER_PERMISSIONS` = 24000); on existing servers migration 0013 grants it to every non-default role and leaves the default role alone, so pure guests stop seeing shares after the update. Enforced by LiveKit through the senders' track subscription permissions, see `apps/web/src/voice/AGENTS.md` "Watching camera/screen". Typecheck, all tests and the smoke test green; not checked in a browser with real cameras.

**Join and leave cues (16 September 2026):** Four different short sounds mark voice-room changes: you joining, you leaving, someone else joining your room, someone else leaving it. `apps/web/src/voice/sounds.ts` synthesizes them with Web Audio (no audio assets): your own pair is a sine C5/G5, the pair for other people a shorter, quieter triangle E5/A5; rising means arriving, falling means leaving. `voiceClient.ts` triggers them on a completed join, on leaving, and on LiveKit's participant events; switching between rooms plays only the join cue, a failed connection attempt plays nothing, participants already present within 1.5 s of connecting are not announced, and deafening silences all cues. Settings tab "Töne"/"Sounds" in `VoiceDock.tsx` has one switch per cue with a preview button plus a shared volume, stored per device in `chat.voice.v1` (`sounds`). `sounds.test.ts` covers the cue shapes, the stored-settings merge and the play decision.

**Video pop-outs and fullscreen (15 September 2026):** Camera and screen tiles expose separate-window and fullscreen buttons. `VideoWindows.tsx` manages one window per track at App level, retaining it across text/stage view changes, moving video display into the pop-out with a restore placeholder in the main stage, and closing windows when their track disappears or the main page closes. Pop-outs have no app frame or app header/footer; browser chrome (including the address bar) remains browser-controlled. Only the initial pop-out size follows the displayed video dimensions or track settings (16:9 fallback), limited to available screen space. After opening, window size is entirely user-controlled; metadata, format changes, manual resizing and fullscreen transitions never trigger automatic resizing; controls reuse the main-stage styles: close and fullscreen buttons at the top right, with per-feed playback controls at the bottom right. `VideoAudioControls.tsx` shares the volume slider, percentage and local mute toggle between received screen shares in the stage and pop-outs. Stage window/audio controls appear on hover or control keyboard focus (always visible on touch); pop-out controls follow the hover/focus rules below. Muting sets only the selected remote track volume to zero and restores its previous level on unmute, including across pop-out/restore; global deafen still takes precedence. Sender labels remain at the bottom left and audio controls at the bottom right on the same row. The control width is capped at 60% of the tile and names truncate within the remaining space to prevent overlap. Percentage outputs use intrinsic width with a four-character minimum so 100% fits. Controls hide when the window loses focus or the pointer leaves (keyboard-focused controls remain accessible; touch controls stay visible while the window is focused). A bottom-left label shows the sender using the voice server member name, including live renames; double-click or F/Enter toggles fullscreen. Existing audio elements move between documents: microphone audio follows camera pop-outs, screen audio follows screen pop-outs. This preserves one playback instance, volume, output-device selection and global deafen. Closing/restoring a pop-out returns its video and audio to the main window. Autoplay failures show a temporary unblock button. Fullscreen uses the target element's document, with translated blocked/unsupported/failure messages. Shared view detach and fullscreen behavior have unit coverage in `videoDisplay.test.ts`. Real multi-window/media browser acceptance is pending; no browser is connected in the editing environment.

**Voice connection card (15 September 2026):** `VoiceDock.tsx` now separates connection status, channel/server names, the stage shortcut, audio-unblock notices, microphone meter/muted label and equal-size controls. Toggle buttons expose pressed states, the connection label is a live status, and the mobile navigation scrolls to keep the taller voice dock reachable. Existing version 2 brand tokens and voice behavior are preserved; German/English stage labels updated together.

**Voice channel moderation (13 September 2026, user's requirement):** permission `MODERATE_VOICE`: move members to other voice channels or remove them, end their camera/screen share, block camera/screen per member (`members.stream_blocked`, overrides roles). LiveKit enforces muting and publish permissions server-side (`livekit/admin.ts`), the client follows via WS event. Also: camera selection with multiple cameras, background blur (`@livekit/track-processors`), separate output device for screen audio.
