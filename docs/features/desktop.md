# Feature notes: Desktop app (M4)

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. Whoever changes the feature adds or updates its entry here in the same step.

Code: `apps/web/src/platform/` (what differs between browser and desktop app), `apps/desktop/` (Electron shell, `apps/desktop/AGENTS.md`). Plan: `docs/PLAN.md` 3.4, 3.7 and M4.

## Decisions (18 September 2026, user)

The user's wish: "Die Desktop App soll das gleiche UI haben wie wir auf dem Server als Web-App ausspielen", every future UI update must reach both, and the build must work on the GitLab system and on GitHub. Asked and decided:

- **Where:** `apps/desktop` in this public repo, Apache-2.0, Electron. Not a repo of its own.
- **The UI is not moved into a package of its own. `apps/web` is the shared client: one build, two shells.** The desktop app packs exactly `apps/web/dist` and serves it from its own scheme (`app://squorli`); the absolute paths (`/assets`, `/brand`, `/player-window.html`) work unchanged. So a UI change cannot reach one and miss the other, there is no package registry (nothing is published anywhere, the GitHub build runs on a bare checkout), and `tools/`, the Dockerfile and the website's screenshot tools keep their paths. `packages/ui` stays a later option (PLAN 3.7). Rejected: moving the UI to `packages/ui` with two thin shells (two renderer builds that can drift, much churn for no gain).
- **Differences between browser and app** (screen share codec, global push-to-talk, system audio, window background, updates, links) go through the `Platform` interface; the client recognises the app at run time by the bridge of its preload script (`window.squorliDesktop`).
- **Installers and update feed:** the binaries live in the GitHub Releases of `danielklessa/squorli-server`; the app only asks `https://squorli.com/updates/stable/` (generic provider), whose files the website generates with absolute GitHub addresses. The storage stays exchangeable. Rollout switch = the manual website deploy.
- **Platforms first:** Windows (NSIS) and Linux (AppImage, deb), unsigned. macOS later (auto-update there needs signing and notarization).
- **Login:** the directory account at `https://directory.squorli.com` is the default (fixed; a development override only). A server can also be added by address or `squorli://` link, also one without a directory (then with the device's key). Known limit: a server that names another directory works by key only; with `requireAccount` it answers `account_required`.
- **Last viewed server:** per device in localStorage, not in the directory's `AccountSettings` (every rail click would be a signed push, two devices would overwrite each other, and it would tell the directory what the user looks at). A fresh device falls back to the newest `AccountStatus.servers[].lastSeenAt`.
- **Window background:** first decided as Windows 11 `backgroundMaterial` (acrylic/mica) plus an opacity slider; **changed on 18 September 2026 after the user saw it** (entry "Own title bar and background modes"): opaque, mica, or a really see-through window; acrylic dropped.
- **Releases:** tag `desktop-v<semver>` = version of `apps/desktop/package.json`; `v*` stays reserved for the server image. The GitLab push mirror carries tags to GitHub, where the installers are built into a draft release.
- **Links:** `squorli://server/<host>` and `squorli://invite/<host>/<code>`. A link never signs in by itself: an unknown host shows the server first and waits for a click.
- **User agent:** `… Squorli-Desktop/<version> Chrome/<v> Electron/<v> Safari/537.36`; `labelFromUserAgent` learns it (copy rule to `../squorli-directory`).

**Audio of a single window, system audio without the app (18 September 2026, user's wish: "dass wir in der App auch nur den Ton des einzelnen Fensters teilen können"; decided: yes, before P4):** Electron 44 only hands out the whole system's audio (`loopback`). Windows can do more since Windows 10 2004: WASAPI process loopback. **Decision on the way (mine): a small helper program, not a Node addon.** `apps/desktop/native/window-audio/main.cpp` (about 150 lines, MSVC, static runtime) -> `squorli-window-audio.exe`: `--include-hwnd <n>` / `--include-pid <n>` = what that process tree plays, `--exclude-pid <n>` = everything except that tree; PCM (48 kHz, 16 bit, stereo) on stdout, "ready"/"error" on stderr, ends when its stdin closes (the app is gone). An addon would be tied to every Electron version's ABI and would put node_modules back into the package; the helper is one file under `resources/native`, built by `native/build.mjs` (finds Visual Studio through vswhere; `pnpm --filter @squorli/desktop native`; not committed; the release workflow builds it on the Windows runner).
- *Shell:* `windowAudio.ts` (`helperPath()`, `ScreenAudioCapture`: spawns the helper, 20 ms chunks to the client over `screenAudio`, stops on the client's word, a new share, and quit), `captureSource.ts` (pure, tested: window handle of a source id and of Electron's handle buffer), `displayMedia.ts`: every source says whether audio can go with it (`ScreenSource.audio`): with the helper a window = its application's audio, a screen = the system's audio **without this app** (`--exclude-pid` of the main process, whose tree holds Chromium's audio service), the app's own windows never (it would be the others' voices); without the helper only screens, through Chromium's loopback as before. With the helper Chromium gets no audio to capture.
- *Client:* `platform/screenAudio.ts` + `public/worklets/pcm-player.js` (plain JS by URL, because the app's CSP allows no blob scripts): an AudioContext at 48 kHz, an AudioWorklet with a two-second ring buffer (starts at 80 ms, drops down when more than 0.5 s behind, silence when dry) and a MediaStream destination give a track. `PlatformMedia.takeScreenAudio()` / `stopScreenAudio()`: the voice client publishes that track as `ScreenShareAudio` (stereo, no DTX/RED, 128 kbit/s) right after the share started and ends the capture when the share ends, also when it ends by itself (`LocalTrackUnpublished`). The picker's checkbox follows the chosen source: "Ton dieses Fensters mitteilen" / "Systemton mitteilen" / disabled with a note. **This also answers the echo question of P2:** the app's own playback is simply not part of what is captured.
- **Checked:** the helper alone: a quiet tone played by another process is captured with `--include-pid` (rms 0.035) and absent with `--exclude-pid` (rms 0.0001), "no such window" exits 1, it ends by itself when stdin closes. In the running app, in a voice channel, through the client's own share button: picker with the audio checkbox, one helper process while sharing, the worklet's output peaks at exactly the tone's amplitude (0.0600, context running at 48 kHz), no "ohne Ton" notice (the audio publication exists), helper gone after "Bildschirmfreigabe beenden" and after closing the app. The installer carries `resources/native/squorli-window-audio.exe`. Typecheck, tests (desktop 17), build.
- **Not checked:** the window mode end to end in the app (the test shared a screen; `--include-hwnd` differs from the tested `--include-pid` by one Windows call, and the handle parsing is unit-tested), what a listener hears (no second participant), long runs (clock drift handling), applications that play through another process than their window's (then nothing is captured), the helper on the GitHub runner, Windows 10. Linux and macOS have no equivalent yet.

**P1: client without a home server, server viewed last (18 September 2026):** with `platform.home === null` the store has no home connection (`Store({ home: null, defaultDirectoryUrl })`; `homeHost`, `activeHost`, `homeState()`, `activeState()`, `store.home`, `store.active` are nullable now) and the client has a login of its own instead of the home server's session. **The browser's behaviour is unchanged**: every branch asks `homeHost === null`.
- *Login (`DesktopLogin.tsx`):* the directory account first (handle + password, code with an authenticator, code by e-mail; `store.loginDirectoryAccount()` fetches the key, replaces the device key, awaits the account's server list and opens a server), below it "go on with this device's key" (`continueWithDeviceKey()`; shows the handle when the key has one). A different handle than the device key's asks before replacing the key, the same handle does not. Registering a handle and setting a password stay on the directory's account page (link).
- *Which server opens (`clientHome.ts`, tested):* `chooseInitialServer` = the server viewed last while it is still the user's, else the account's most recently seen one without a pending account deletion, else the first added one, else none. When the directory did not answer, the remembered server stands. Stored per device in `chat.client.v1` (`signedIn`, `hosts`, `lastHost`; validated on load), written only without a home server.
- *Servers by address (`store.addServer()`, `parseServerAddress`, tested):* a host, an address, an invite link (`https://<host>/invite/<code>`) or a `squorli://` link; the host must pass `ServerHost` and the address is rebuilt by `directoryServerUrl`. **A server the key has not been on is only looked at (`/api/health`); the join view (`ServerStatus` with `join`, App.tsx) waits for a click**, because signing in reveals the public key and creates an account there. It carries an invite field (prefilled from the link; the server's "invite required" message lands there too). A server the key has been on (stored session, added before, on the account's list) connects right away. A joined server the account's list does not name is kept in `localHosts`; once the list names it, it is dropped from there. "Close" removes an added server.
- *Rail (`railServers.ts`, tested):* without a home entry: the account's servers, then the added ones, plus the one being looked at; a plus button adds a server (`askInput`). Icons still come from the directory only, so an added server shows initials. The rail is shown even when the directory is unreachable. The server browser's "Öffnen" shows the server inside the client (`onOpen`).
