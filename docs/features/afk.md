# Feature notes: AFK detection and AFK channel

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. Standing rules live in the `AGENTS.md` of the area. Whoever changes the feature adds or updates its entry here in the same step.

**AFK detection, AFK channel, AFK in the friends list (17 September 2026, user's requirement):** a user counts as absent (AFK) after 10 minutes without activity (`AFK_AFTER_MS`, fixed for everyone). An admin names one voice channel the AFK channel; a member who is absent in a voice channel is moved there. In the AFK channel microphone and audio are always off and camera or screen share are impossible. The state goes to the directory too, so friends see it.

The user's decisions (asked on 17 September 2026):
- **What counts as activity:** input in a Squorli window (pointer, keys, wheel, touch; video pop-outs included), **speaking** (open speech gate of an unmuted microphone, so somebody who plays and talks is not moved), and **system-wide input through the Idle Detection API** where the browser has it (Chromium) and the user switched it on. The browser asks for that permission and only inside a click, so it is a switch in Einstellungen > Ansicht ("Abwesenheit"), stored per browser (`chat.idleDetection.v1`), not in the directory account: the permission belongs to the browser. While the detector reports the user active they are never idle; once it reports idle or a locked screen, the ten minutes without input or speech decide. Firefox and Safari work from the first two alone.
- **Coming back:** the user stays in the AFK channel; the dock says why they are there and offers "Zurück zu <Kanal>". Never automatically: a stray mouse move must not put a microphone back on air.
- **Exception from the move:** nobody is moved out of a channel whose radio shows a video (Twitch or YouTube): watching together needs no input. The AFK status shows regardless. Once the video ends, the next sweep moves them. No exception for people sharing or watching camera/screen (not chosen).
- **One time, fixed at 10 minutes (user's decision of 17 September 2026, replacing the first version of the same day):** "Wir sollten die 10 Minuten bis AFK Zustand doch fest schreiben, es macht wegen des Verzeichnis keinen Sinn wenn jeder Server das für sich einstellen kann." The first version had the status after 5 minutes and a move time per server (5/10/15/30/60 minutes, `afkMoveMinutes`, column `afk_move_minutes` from migration 0020). Since friends see one state through the directory and the same person sits on several servers, there is now one time for everything: absent after 10 minutes, and the server moves a member of a voice channel to the AFK channel at that moment. The setting, `AFK_MOVE_MINUTES` and the column are gone (migration 0021 drops the column; 0020 had already run on the dev database and generated SQL is not edited by hand). The only server setting is which channel is the AFK channel.

How it works:
- **The client measures, the servers combine.** `ActivityTracker` (pure, tested) turns idle after `AFK_AFTER_MS`; the store reports every change as `{ type: "activity", idle }` on every chat server connection and on the directory socket. A connection counts as active until it says otherwise (a fresh or reloaded client is somebody using it); after a reconnect only `idle: true` is repeated. A user is AFK once **all** their connections are idle (`Hub` on the chat server, `Hub` in the directory's `friends.ts`), so a second tab or device in use keeps them present; a client from before the feature never reports idle and so keeps its user present.
- **No `PROTOCOL_VERSION` bump and no `DIRECTORY_WS_VERSION` bump.** A server that knows the event sends `settings.afkChannelId` (null = no AFK channel; the field missing = a server from before the feature; a flag like `radioAutoStop`), the directory reports `features.afk`; the client sends `activity` only then (an older server would answer `bad_message`). `Member.afk`, `Friend.afk` and `friends.presence.afk` default to false; older clients strip the unknown fields and `reason` of `voice.moved`.
- **Status:** `Member.afk` travels with the member list (the hub's presence listeners fire on AFK changes too, `broadcastStructure(["members"])`). Shown as an amber crescent on the avatar's presence dot (`Avatar` prop `afk`, label "Abwesend"/"Away"; brand: amber = away, the shape carries the state as well as the color) in the member list and the friends list, and as a moon next to voice members in the sidebar. The first version's crescent sat on the 6 px presence dot and could not be recognized (user's report, 17 September 2026): the AFK mark on the avatar is now larger than the online dot (1.125 rem, filled crescent), and the rows of the member list and the friends list carry an amber moon icon on the right as well; checked with a headless Chrome screenshot at 1:1 scale.
- **Move:** `AfkMover` (`voice/afk.ts`, pure, tested) is asked on every presence change (so right when somebody turns absent) and every 5 s (a video that held its channel's members back ends without an event): AFK users sitting in a voice channel that is not the AFK channel and shows no video get `voice.moved` with `reason: "afk"` (`by` = server name), at most once per absence. When the connection a user was active on closes and only idle ones remain, the hub waits `AFK_AFTER_MS` before it calls them absent (they were active a moment ago; tested with fake timers). The client joins the AFK channel itself, like after a moderator's move, remembers where it came from and leaves the view alone (`joinVoice` option `auto`).
- **AFK channel is enforced by LiveKit:** `POST /api/rtc-token` for the AFK channel grants `canPublish: false, canSubscribe: false`; participants still see who is there. The client joins with `JoinOptions.afk`: no microphone request at all, shown muted and deafened (attribute `deafened` for the others), mute/deafen/camera/screen refused and the buttons disabled, no radio control. When the admin changes which channel it is, the server silences the members already inside through `RoomServiceClient.updateParticipant` (`LivekitAdmin.silence`) and gives the old channel's members their grants back (`setCanStream`); current clients additionally rejoin with a fresh token (App.tsx compares the channel's role with `voice.afkRoom`). The AFK channel has no radio: `PUT /api/channels/:id/radio` answers 409 `afk_channel`, and a running radio is turned off when the channel becomes the AFK channel. Anyone may join the AFK channel by hand.
- **Setting:** `server_settings.afk_channel_id` (FK to channels, `on delete set null`; deleting the channel broadcasts the settings too; migration 0020, and 0021 drops the first version's `afk_move_minutes`), `PATCH /api/settings` with `MANAGE_SERVER` (400 `unknown_channel` for anything but a voice channel). Admin area > Kategorien/Kanäle, section "AFK-Kanal" (only with `MANAGE_SERVER`; it is about a channel, so it lives there).

**Desktop app: system-wide detection without a switch (18 September 2026, user's question whether the settings' section is needed there):** the shell grants `idle-detection` by itself (`apps/desktop/src/main/security.ts`), so the permission state is `granted` from the start, nothing is asked and a detector starts without a click (checked in the shell). A switch would only make the app worse: it runs in the background while the user works elsewhere, and without the system's view they would count as away after ten minutes at the computer. So `platform.systemIdle` (`"permission"` in a browser, `"always"` in the app) decides: `resumeIdleDetection(tracker, always)` starts the detector at load regardless of `chat.idleDetection.v1`, and Einstellungen > Ansicht > Abwesenheit shows an explanation only (`settings.idleHintApp`, which also says that nothing but active/away is sent). Browser behaviour and texts unchanged. Checked in the dev shell with a fresh profile: one detector started at load with the storage key unset, the section shows the text and no checkbox, no console errors.

**Connections that die without a close (18 September 2026, user's report):** "Ich war gerade 20 Minuten nicht am PC, hatte Kopfhörer und Mikrofon stumm geschaltet und war danach noch immer im Sprachkanal. Im Moment sehe ich einen Nutzer, der gleichzeitig im Sprachkanal und im AFK-Kanal ist, ohne als Benutzer AFK anzuzeigen." The screenshot showed the cause: the sidebar (the server's voice presence) listed three members in the channel, the stage (LiveKit) two. Presence and the AFK state are kept per WebSocket, and two things left connections behind that nobody used any more:
- **The server never noticed a dead connection.** The client pinged, the server answered, but nothing ended a connection whose other end had vanished (sleep, network change, a proxy in between). Such a connection kept its place in a voice channel (the member in two channels) and, because it could never report idle, kept its user present for ever (AFK = ALL connections idle), so no status and no move. Now `ws/liveness.ts` (pure, tested) with the handler's heartbeat: a WebSocket ping to every connection every 30 s (browsers answer by themselves, older clients and throttled tabs included); nothing heard for 90 s = terminated, which removes presence and hub entry. A connection that answers pings but whose client code has sent nothing for 150 s (its `ping` comes every 20 s, once a minute in a throttled tab) is a frozen page: `Hub.setStale` counts it as idle until the client speaks again; closing it starts no waiting time.
- **The client did not say its voice channel again after a reconnect.** Voice (LiveKit) survives a reconnect of the chat socket, the server's presence does not (it goes with the socket). After a server restart or a network blip the member was still talking but in no channel for the server: missing in the sidebar, and `AfkMover` found no channel to move them from. `ServerConnection` now remembers the channel of its last `voice.join` (cleared by `voice.leave`, removal, session end) and sends it again after every `welcome`. It also notices a dead connection itself: when nothing arrived between two of its pings (20 s apart; a timer that fired late proves nothing and is skipped), it drops the socket without waiting for the close and connects again; `connect()` always lets go of an earlier socket first, so one client never holds two.

No protocol change: the ping is the WebSocket's own, the events are the known ones. The directory's socket had the same gap and got the same cure on the same day (user: "das directory bitte auch anpassen"): heartbeat and `Hub.setStale` there (`../squorli-directory/docs/features/friends-dm.md`), and `directoryLink.ts` here replaces a dead socket like `ServerConnection` does. Checked with a test server on :3001 (fresh `chat_live`), headless Chrome with a fake microphone in a real voice channel plus raw `ws` clients: after the client's socket was closed under a running voice connection the member was in the channel's list again once reconnected (voice never dropped); a socket made deaf was replaced after 37 s and the place announced again, no console errors; a connection answering no pings was terminated after 105 s; with one idle and one silent connection the user turned AFK after 165 s and came back the moment the silent client sent a ping. Also checked: Electron's IdleDetector really reports idle in the dev shell (threshold 60 s, `idle` arrived), so the app's system-wide detection was not the cause. Not checked: a real sleep or network change, a proxy in between, the user's production server (it needs this version).

**Planned: controller input and running videos as activity (20 September 2026, user's report and decisions; what is built of it follows in the next entry):** "Ich werde immer beim YouTube gucken in den AFK Kanal verschoben, das nervt und wäre bei einem Controller Spiel noch nerviger, weil ich als Benutzer ja aktiv etwas tue." Decisions: controller input counts as activity, for every controller and not only Xbox; for games no fullscreen signal at all, input only (a game left in its menu is absence; fullscreen detection was discussed and dropped, videos are often not fullscreen either); a running video counts as activity for at most 4 hours without any input (autoplay, a sleeping viewer); "watching a video" is never shown to others. Desktop app only, Windows first, no protocol or server change. First steps: a diagnostic line in the debug view to find out whether Chromium's Gamepad API still delivers while a game has the focus and the app is minimized or in the tray (the user tests with an Xbox controller and a Thrustmaster joystick; fallback: native helper with Raw Input and XInput), and measuring the candidate video signal `ES_DISPLAY_REQUIRED` (readable without administrator rights on the user's PC; to measure: set by Chrome, Firefox and Edge for a windowed video, not set by Squorli's own voice connection; the client ignores it while it shows video itself). A later, separate feature shows which game a user plays (off by default; AFK and the game display stay independent); keep the `activity` event open for an optional field. Full plan with the measurements and the later stages: `../squorli-directory/docs/PLAN-activity-games.md`.

**Built of it (20/21 September 2026): controller input as activity in the desktop app, through a native helper.** First try: Chromium's Gamepad API, polled by the client, with a test line in the debug view. The user's test: "schon ohne Fokus werden die Eingaben nicht erkannt". Chromium delivers gamepad data only to the window that has the focus, so that path is useless for somebody playing a game and was removed again. Now: `apps/desktop/native/system-watch/main.cpp` (`squorli-system-watch.exe`, Windows) reports `input` when a controller was used, at most once a second: XInput controllers polled four times a second (empty slots every 3 s), every HID joystick, gamepad and multi-axis controller through Raw Input with `RIDEV_INPUTSINK` (delivered while another window has the focus), parsed from the device's own report description (`HidP_*`), so no list of devices. Only a real step counts, compared with the state at the last counted input: a changed button or hat switch, an axis moved by a tenth of its range (XInput: a fifth of a stick's way, half a trigger); drift, flicker, vendor-defined values (motion sensors) and a throttle lever that stays where it is are no input; the first sight of a device only sets the reference. The helper also prints `display 0|1`, whether some program keeps the display on (`ES_DISPLAY_REQUIRED`). The shell (`apps/desktop/src/main/systemWatch.ts`, lines parsed by the tested `systemWatchLines.ts`) runs it as long as the app runs, restarts it at most five times, and sends `SystemActivityEvent`s over the new channel `squorli:system-activity`; a client that subscribes gets the current display state at once. Client: `platform.systemActivity` (null in a browser, in an older app, without the helper; `DesktopInfo.systemWatch`), `systemActivity.ts` calls `activity.touch()` per report. The display state had no effect at first and was only shown in the debug view (rows "Controller-Eingaben" and "Bildschirm wird wach gehalten") until it was measured; the rule built on it is the next entry. The helper reads no keyboard, no mouse and no window contents. Known gap: a controller switched to its maker's own report format (a PlayStation controller over Bluetooth once a game or Steam opened it) sends reports the description does not explain; with Steam Input it appears as an XInput controller and is covered.

Checked: typecheck, tests (web 286 with `systemActivity.test.ts`, desktop 31 with `systemWatchLines.test.ts`), build, the helper compiles without warnings (`pnpm --filter @squorli/desktop native`, now builds both helpers). The helper alone: `ready`, `display 0`, ends 5 ms after stdin closes. The unpackaged app with a scratch profile over the DevTools protocol: one helper process while the app runs and none after it, `info.systemWatch` true, a subscriber gets `{ type: "display", required: false }`. **Not checked (no controller on this side): that input of the user's Xbox controller and Thrustmaster joystick is reported while a game has the focus, that an untouched controller reports nothing, the display state with a video in Chrome, Firefox and Edge (windowed) and in a voice channel without video, a packaged app.**

**The user's tests of the helper and the video rule (21 September 2026):** the user ran the tests asked for and reported "Die Tests waren alle erfolgreich". Asked for were: controller and joystick input is counted while a game has the focus and the app is minimized or in the tray, untouched devices count nothing, the display state is "ja" for a windowed video in Chrome, Firefox and Edge and "nein" on pause and in a voice channel without video. Built on that, the rule decided on 20 September: **a playing video keeps the user present for at most 4 hours since they were last really there.** `ActivityTracker.setVideoPlaying(on)` (`activity.ts`, tested): while a video plays the tracker does not turn idle, until `VIDEO_ACTIVE_MAX_MS` (4 h) have passed since `lastPresent` = the last `touch()` (input in a Squorli window, speech, controller) or the last moment the system-wide detector reported the user active; a video that stopped still counts for `VIDEO_GAP_MS` (2 minutes: the gap between two videos of a playlist, an advertisement, buffering; without it a playlist watcher would be moved to the AFK channel in the pause between two videos). A pause is a click, so the ten minutes count from there. The display state does not say which program holds it, and Squorli holds it itself while it shows video: `systemActivity.ts` `setOwnVideo(tracker, on)`, fed by App.tsx with `videoActive(voice.participants, embedSource !== null)` (a camera or screen share of anybody in the channel, or the radio's Twitch/YouTube player; wider than "a video is on screen", which errs towards today's behaviour), makes the tracker ignore the state for that time; the server's exception for a channel whose radio shows a video is unchanged. "Watching a video" is never sent anywhere, the servers still only learn idle or not. Einstellungen > Ansicht > Abwesenheit says so in the app when the helper is there (`settings.idleHintAppSystem`); the debug view's row shows "ja (nicht gewertet ...)" while Squorli's own video hides the state. Known: a tool that holds the display on for good (PowerToys Awake, a presentation mode) keeps its user present for 4 hours after their last input; a video that plays on while the user is gone does the same. Checked: typecheck, tests (web 290: 3 new in `activity.test.ts`, 1 new and 1 changed in `systemActivity.test.ts`), build. **Not checked: the rule in the running app** (it needs more than ten minutes hands off with a video, then four hours for the cap; the pure rule and its wiring are covered by the tests), a packaged app.

Limits: a browser only sees input in its own windows unless the user allows the Idle Detection API; a background tab checks its timer about once a minute (browser throttling), so the status can come up to a minute late there. A speech gate held open by background noise keeps its user present. The directory operated at https://directory.squorli.com shows AFK to friends only once it runs this version (`features.afk`).
