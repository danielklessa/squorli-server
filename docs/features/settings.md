# Feature notes: Settings dialog, mini profile, settings in the directory account

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. Standing rules live in the `AGENTS.md` of the area. Whoever changes the feature adds or updates its entry here in the same step.

Code: `apps/web/src/SettingsDialog.tsx`, `MiniProfile.tsx`, `accountSettings.ts`, `voice/settings.ts`, `voice/useVoiceSettings.ts`, `store.ts`; protocol `AccountSettings`, `SoundSettings` in `directory.ts`. Standing rule for new settings: `apps/web/AGENTS.md`.

**Sprechen and Audiogeräte are one tab, with a microphone test (19 September 2026, user's wish: "In den Einstellungen bitte Sprechen und Audiogeräte in einen Tab behandeln. Für das Mikrofon soll es noch eine Möglichkeit geben sein eigenes Mikrofon zu testen. Während man testet, wenn man zeitgleich in einem Kanal eingeloggt ist, wird der Ton nicht in den Kanal übertragen."):** the tab `voice` is now "Sprache und Audio" / "Voice and audio" (`settings.tab.voice`; the tab id `audio` and the key `settings.tab.audio` are gone, the heading "Sprechen" is `settings.speaking`; `voice.errMic` names the new tab). Order: Eingabe (microphone, "Mikrofon testen", level meter with the threshold mark, shown in a channel or during the test), Sprechen, Mikrofonverstärkung, Ausgabe; the tab still says where its settings live, and the device selection stays per browser (`settings.devicesLocal`). The test (`client.startMicTest(settings)` inside the click, `voice.micTest`) plays the microphone behind the boost and before the gate to the voice output device; in a channel the microphone counts as muted while it runs (the dock and the others see it), and the tab says so (`settings.micTestRunningJoined`). It ends with the button, with leaving the tab, with closing the dialog, and with joining or leaving a channel. How it works: `apps/web/src/voice/AGENTS.md`, "Microphone test". `.meter` got `flex-shrink: 0`: in the longer tab the scrolling flex column squeezed it to a line. Not chosen: a recorded and delayed playback (live listening shows the same and needs no second step); deafening during the test (the user asked only that nothing is sent). Checked in headless Chrome with Chromium's fake microphone (harness bundles of the real sources): in no channel the monitor carries signal (RMS 0.33), still does after a device change on the same stream, and ending it stops the capture; with a running pipeline and a recording stand-in for the published track: `mute` before `monitor-on`, `unmute` after the test, still muted when it was muted by hand before, the monitor carries signal while the closed gate keeps the published track at 0; the dialog rendered with the built CSS (screenshots idle and testing, German). Confirmed by the user the same day with a real microphone and a second person: he hears himself on the chosen output device, the other person hears nothing during the test and hears him again afterwards. Not checked: Firefox/Safari, the desktop shell.

**A language change does not end voice (18 September 2026, user's requirement: "Wenn ich die Sprache in meinem Client ändere möchte ich nicht aus Sprachkanälen geschmissen werden"):** the texts follow a language change through a reload (`i18n/index.ts`: the locale is fixed at page load, many texts are computed once at module load), and a reload ends the voice connection. Now every reload for the language goes through `store.reloadForLocale()` (the choice in the settings, and the account's language arriving from the directory): while a voice connection runs (`store.voiceActive`, set by App.tsx from the voice client) the choice is only stored (and pushed to the account as before), `localeReloadPending` makes Einstellungen > Ansicht say so (`profile.languagePending`), and App.tsx calls `applyPendingLocale()` when voice has ended, which reloads then; choosing the old language again clears it. Not chosen: switching the texts live without a reload (every component calls `t()` without a hook and some texts are module constants; that is a rewrite of its own). The login screens' language selects still reload at once (no voice there). Checked with a test server on :3001 in headless Chrome: English chosen while in voice = still connected, same page load, `chat.locale` stored, the hint shows (screenshot); after hanging up the page reloaded by itself in English; no console errors. Not checked: the account's language arriving from the directory while in voice (same function), the desktop shell.

**One settings dialog, mini profile, settings in the directory account (17 September 2026, user's wish):** the gear next to your name in the dock opens `apps/web/src/SettingsDialog.tsx`, the single place for all user and profile settings (categories on the left: Profil, Ansicht, Sprechen, Audiogeräte, Kamera, Töne, Sitzungen, Konto); it replaces `ProfileDialog.tsx` (deleted) and the modal that lived inside `VoiceDock.tsx`. Clicking your name opens `MiniProfile.tsx` (a `ContextMenu` that opens upwards from the name: `MenuAnchor.above`, `menuPosition`) where only the display name on the server shown can be changed, plus a button to the settings. With a directory account **every setting except the device selection** (microphone, outputs, camera) is stored in the directory and stays changeable from the client of any chat server: the client signs with the user's key and writes to the directory itself (action `settings`, `api.directorySetSettings`, `POST /api/settings` there), so the chat server is not involved and `PROTOCOL_VERSION` stays 4. `accountSettings.ts` maps between the per-device working copy (`chat.voice.v1`, `chat.locale`) and the protocol's `AccountSettings`; `store.ts` adopts the account's copy when the account status arrives and pushes user changes 800 ms coalesced (`State.settingsSyncError`), seeds an account that has none, and falls back to the cue-only sync against a directory without `features.settings`. The global display name shown in Profil comes from the signed account status (`store.refreshAccountServers()` merges `status.displayName` into `State.directoryAccount`), because the public key lookup never carries names; the dialog follows a late-arriving name until the user edits the field, so an empty field cannot delete a name that had not arrived yet. Language: the account's choice wins unless the user changed it on this device since it was last in step (`chat.locale.account`); a reload happens only when the active locale really changes, and `store.setLocale()` pushes before it reloads. New option Ansicht > "Mich selbst als Sprecher hervorheben" (`VoiceSettings.featureSelfInSpeakerView`, account `stage.featureSelf`, default on): when off, the speaker view never features your own camera tile by itself (pinning by click still works, and alone in the room you are still shown). Account management (password, authenticator, e-mail) stays on the directory's account page, linked from Konto (user's decision). Typecheck, tests and both smoke tests green (`docs/VERIFIED-STATE.md`); the dialogs themselves were not checked in a browser.

**Cue settings follow the directory account (16 September 2026, user's wish: set once, valid on every server):** the per-device copy in `chat.voice.v1` stays the working copy ("local profile"), so servers without a directory keep working unchanged. With a directory account the account's copy wins: `store.refreshAccountServers()` reads `AccountStatus.soundSettings` and applies it to the device (`saveVoiceSettings(..., "directory")`), an account without stored settings is seeded with the device's; every user change (`saveVoiceSettings(..., "user")`) is pushed 800 ms coalesced via the signed action `sound-settings` (`api.directorySetSoundSettings`, `POST /api/sound-settings` at the directory). `voice/settings.ts` is now a tiny external store (cached copy, `subscribeVoiceSettings` with the source, `sameSoundSettings`); `voice/useVoiceSettings.ts` exposes it as React state so App and VoiceDock share one copy (the `onSettings` prop is gone), and App hands `sounds` to the voice client. The sounds tab says where the settings live ("account" or "device") and shows the last save error (`State.soundSyncError`). `SoundSettings` is the protocol schema (`packages/protocol/src/directory.ts`, also `directorySoundSettingsPayload` = "<4 bits>\n<volume>", `SoundSettingsUpdateRequest`, `AccountStatus.soundSettings`); tests in `sounds.test.ts` and `settings.test.ts`.

**Mobile settings layout (19 September 2026, user request):** full-viewport settings at <=700 px, safe-area header and content padding, compact left-hand icon/label categories, independently scrolling navigation and body. Controls have 44 px touch targets; inputs/selects fill the available width, long names and session/license rows wrap. The dialog has an accessible title and categories expose the current selection. Desktop rules and the admin dialog are unchanged. Checked: real SettingsDialog bundled in isolated headless Chrome, all browser categories at 320x640, 390x844 and 700x400 without horizontal body overflow; full-viewport bounds; German voice/audio screenshot reviewed. Root typecheck, tests and build passed. Not checked: real phone keyboard, Safari, actual device changes or microphone capture in this layout check.

**Mobile opening focus (19 September 2026, user request):** settings and administration initially focus Close at <=700 px or with a coarse primary pointer (including wider touch screens). The profile field only autofocuses on desktop. This avoids opening the software keyboard on dialog entry; fields remain normally focusable by tapping. Root typecheck, tests and build passed; real-device keyboard acceptance pending.
