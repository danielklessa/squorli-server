# Feature notes: Admin panel and general UI (roles, channels, context menus, UI refresh)

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. Standing rules live in the `AGENTS.md` of the area. Whoever changes the feature adds or updates its entry here in the same step.

Code: `apps/web/src/AdminPanel.tsx`, `roleOrder.ts`, `ChannelsTab.tsx`, `channelOrder.ts`, `ContextMenu.tsx`, `menuPosition.ts`, `Avatar.tsx`, `styles.css`.

**Own scrollbars; the dock's message keeps off the edge (18 September 2026, user's wishes: "nutze eine custom scrollbar, die dargestellte sieht echt nicht schön aus"; "der Text 'Getrennt: …' klebt am linken Rand"):** scrollbars everywhere (also in pop-outs, which copy the styles): 12 px, a rounded translucent thumb (`--muted` at 32 %, 58 % on hover, brand blue while dragged) with 3 px of air, no track, no arrows; Chromium through `::-webkit-scrollbar*` (the standard properties would switch those off, so they only apply where the pseudo elements are unknown: `@supports not selector(::-webkit-scrollbar)`, Firefox: thin, same colour). The message the dock shows after a voice connection ended (`.dock > .error`) had no padding; it has now. Checked: computed thumb style in the app; the dock's padding not looked at in a real disconnect.

**Areas: smaller gaps, the member list as an area of its own, side columns resizable (18 September 2026, user's wishes while trying the desktop app: "die Benutzerliste rechts dürfte auch eine Gap zum Hauptbereich haben. die gaps zwischen den Bereichen gerne nur halb so groß. Die Bereiche wären noch ganz gut wenn der Benutzer sie in der größe ändern kann"):** applies to browser and app alike (one client). New `--gap` = 6 px (half of the former 12 px; off the brand's 4 px grid because the user asked for half) around the channel list, the main area and the member list; the member list is a panel now (`--bg2`, panel radius, the gap on all sides) instead of a flat strip on the app background. The channel list and the member list can be dragged wider or narrower by a handle lying over their gap (`ColumnHandle.tsx`: pointer capture, arrow keys 16 px / Shift 48 px, Home or double click = default; `role="separator"` with value limits); widths 208-448 px and 176-416 px, per device in `chat.layout.v1` (`layout.ts`, tested), applied as `--left-w`/`--members-w` on `.app`. Below 900 px the handles are hidden with the member list. Pitfall noted in the CSS: an absolutely placed grid child needs start AND end line (`grid-column: 2 / 3`); an open end means the container's edge. Checked in Chrome with real mouse events (DevTools protocol): gaps 6 px, both drags change the widths, stored, applied after a reload; screenshot looked at. Not checked: touch, the narrow layout, the home view.

**Compact role rows (17 September 2026):** Role drag handle, name and both arrow buttons share one grid row. Names truncate with an ellipsis and expose the full name in a tooltip; the default-role label stays inline. This keeps the left role list compact without changing ordering behavior.

**Role ordering (17 September 2026):** The Roles tab in `AdminPanel.tsx` replaces the numeric position field with drag handles, insertion markers and up/down controls in the left-hand role list. Focused handles also accept arrow keys. Ordering saves immediately through the existing role API, separately from unsaved name/color/permission edits. `App.tsx` supplies the active user ID so own/higher roles and the default role cannot be dragged; owners can reorder all non-default roles. `roleOrder.ts` preserves rank slots and repairs ties without crossing the actor's rank boundary. Four tests cover directions, fixed roles, ties, owner access and no-op drops. Typecheck, all 97 tests and production build passed. Browser visual/drag acceptance remains pending (no connected browser). No backend, protocol or brand changes.

**Channel management (17 September 2026):** `apps/web/src/ChannelsTab.tsx` separates channel names/actions from category, topic and audio controls in responsive editors. Categories and channels can be reordered with native drag handles and before/after insertion markers; grouped up/down buttons remain available for touch and keyboard use, and focused handles accept arrow keys. Reordering uses the existing update endpoints, serializes writes and disables further reorder actions while saving. `channelOrder.ts` normalizes positions, including duplicate legacy values; four unit tests cover insertion in both directions, boundaries and stale IDs. German/English labels and save status are included. Typecheck, all 93 tests and production build passed; visual and native drag interaction verification remains pending because no browser was connected. Existing brand tokens are reused without brand-package or sibling-project changes.

**Member context menus (15 September 2026):** Member buttons open a floating body-portal menu on right-click or ordinary click (also keyboard/touch). `ContextMenu.tsx` supplies viewport positioning, outside dismissal, Escape/Tab handling and arrow-key navigation; role selection and voice-channel moves use hover/click/keyboard submenus that flip left near the viewport edge. Existing moderation permissions and confirmation dialogs are preserved. `menuPosition.test.ts` covers six placement cases. No server, protocol or brand-package change.

**Web UI refresh (15 September 2026):** The browser client uses the existing version 2 brand tokens for a framed conversation area, roomier navigation, member handles and a profile dock. `apps/web/src/Avatar.tsx` is the shared image/initials presentation component for channel messages, DMs, members, friends, voice participants and profile previews. It accepts an optional image URL and falls back on load errors; avatar upload, persistence and protocol fields are not implemented. At <=700 px, navigation is collapsible and the server rail is horizontal. The brand package and sibling projects are unchanged. Verification: typecheck, all 50 tests and production build passed; browser visual/interaction review remains pending because no browser was available.

**Roles of owners, and a menu that only offers what works (19 September 2026; user's report: assigning a role to an owner fails; user's decision: "der Haupt-Owner soll das können, ansonsten gilt, wenn man es nicht vergeben kann soll es auch nicht angezeigt werden"):** until now nobody could change an owner's roles (`outranks` refuses owners as targets, 403 `target_above_you`), and the member menu offered "Rollen" for everyone as soon as one had `MANAGE_ROLES`, with every role in it, so the refusal showed as a raw error. Server: `canSetRolesOf` in `authz.ts` = own roles as before, an owner's roles only by the first owner (`server_settings.owner_id`), everyone else by rank; used by `PUT /api/members/:id/roles`. Kick, ban and voice moderation of owners stay impossible for everyone. Client: `memberRank.ts` mirrors the server's rules (`topPositionOf` incl. the default role, `canSetRolesOf`, `assignableRoles` = roles below the own highest, owners all, never the default role); `MemberList.tsx` shows "Rollen" only when the target's roles may be changed and at least one role can be given, and lists only those roles. Roles the target holds but I may not touch are not listed and stay untouched (the request sends the complete list, the server compares only what changed). Own roles are still not offered in the own menu (as before). Checked: `authz.test.ts` and `memberRank.test.ts`, smoke test 110 green without a directory (new: the first owner sets another owner's roles, a further owner gets 403 for the first owner's), and the built client on :3002 in headless Chrome with a first owner, a further owner, a moderator and a guest: as the first owner the further owner's menu has "Rollen" with all roles; as the further owner neither owner's menu has it, the others' do; as a moderator whose highest role equals "Mitglied" no menu has it. Not changed: kick/ban buttons still show for non-owners regardless of rank (the server refuses by rank; the user's rule was about assigning).

**Header controls of one height (19 September 2026; user's wishes: "Die Buttons in einer Sprach-Lobby oben sollen alle die selbe Höhe haben", "alles genau so hoch wie den Toggle", the ones without a ground keep none until hovered, the icon centered in the button):** `--head-control-h` in `styles.css` is the height of the layout switch `.seg` (one line of 0.875rem text at line-height 1.5 + 0.5rem + its 3px frame = 35 px); the radio button already reached it by its padding, the icon buttons of a main header (`.chat-head > button.icon`: participants-without-video, pop-out) and the debug button get it as squares with no vertical padding, so the flex centering of `button.icon` puts the glyph in the middle. No ground was added. The debug button sat half a pixel lower than the controls inside the header (it was centered on the header's full height, they on the height above its 1px border line): now `(--head-h - 1px) / 2`. Measured in the built client (headless Chrome, voice lobby): radio button, switch, pop-out and debug button each 35 px high at the same top, icon centers within 0.01 px of the button centers, icon buttons transparent; screenshot reviewed. Change `.seg` and `--head-control-h` together.

**Member list on a phone (22 September 2026, user request):** "in der mobilen Ansicht soll im Serverhead noch auf der rechten Seite ein Button sein mit dem man die Benutzerliste einblenden kann. Die Benutzerliste kommt dann von rechts ins Bild". At <=700 px the member column had been hidden altogether. Now the server head ends with a `users` button (`onOpenMembers` of `Sidebar.tsx`, passed only at narrow widths) and the member list (`MemberList.tsx`, the same component as the desktop column) becomes a full-size panel that slides in from the right over rail and navigation, like the content does: `.members-col` under `@media (max-width: 700px)`, `.mobile-members` on `.app` from `mobileMembers` in `App.tsx`. On the phone the list carries a sticky header "Mitglieder · n" with an X (`onClose`), the desktop column has none. The panel closes by itself when content opens over it (a member's "Nachricht schreiben"), when the home view toggles or another server is shown, and when the width changes. The context menus work as on the desktop. Desktop rendering unchanged. Checked: `docs/VERIFIED-STATE.md` of the same date.

**Mobile navigation (19 September 2026, user request):** keep the desktop view unchanged. At <=700 px the full-height server rail sits beside the current server navigation or friends. Selecting a text channel or friend opens full-width content from the right; the top back arrow returns to navigation. The content is not mounted behind mobile navigation. Server connection/join errors remain accessible. Existing palette, typography and assets retained; no brand package changes. Voice details: voice-video.md.

**Mobile page zoom (19 September 2026, user request):** fixed viewport scale with maximum-scale=1 and user-scalable=no; mobile touch-action allows horizontal/vertical panning without pinch zoom. Form controls use at least 16 px on mobile to avoid focus zoom. Browser accessibility overrides may still allow zoom. Checked: root typecheck, tests and build; no real-phone acceptance.

**Mobile administration (19 September 2026, user request):** apply the same full-viewport layout as user settings, with compact left-side icon/label categories, independent column scrolling, safe-area padding and 44 px touch controls. Roles and channel creation forms stack vertically; channel names/actions use separate rows. The dialog has an accessible title and the selected category is exposed with aria-current. Desktop rules remain unchanged. Checked: real AdminPanel bundled in isolated headless Chrome with populated example channels, categories, roles, radio stations, invitations and bans; all six categories fit 320x640, 390x844 and 700x400 without horizontal content overflow, full-viewport bounds and no page errors. Channel screenshot reviewed. Root typecheck, tests and build passed. No real-phone keyboard or write operations tested.

**Mobile opening focus (19 September 2026, user request):** settings and administration initially focus Close at <=700 px or with a coarse primary pointer (including wider touch screens). The profile field only autofocuses on desktop. This avoids opening the software keyboard on dialog entry; fields remain normally focusable by tapping. Root typecheck, tests and build passed; real-device keyboard acceptance pending.
