# Feature notes: Web radio in voice channels (stations, typed addresses, Twitch, YouTube, now playing)

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. Standing rules live in the `AGENTS.md` of the area. Whoever changes the feature adds or updates its entry here in the same step.

Code: server `apps/server/src/radio/`, `apps/server/src/routes/radio.ts`; protocol `RadioStation`, `ChannelRadio`, `RadioPlayback`, `twitchChannelOf()`, `youtubeVideoOf()`; client `apps/web/src/voice/radioPlayer.ts`, `RadioControl.tsx`, `RadioTab.tsx`, `radioLabel.ts`, `EmbedPlayer.tsx`, `embedControl.ts`, `twitch.ts`, `youtube.ts`, `watchSync.ts`, `playerWindow.ts`, `playerWindowMain.ts`, `apps/web/player-window.html`.

**Web radio in voice channels (17 September 2026, user's wish):** the server keeps a list of web radio stations, a member with the new permission `CONTROL_RADIO` tunes a voice channel to one of them for everybody in it, and every listener chooses their own volume or turns the radio off for themselves.
- **The audio never passes through the chat server or LiveKit (Claude's decision, not confirmed by the user):** every client in the channel plays the station's address itself in a plain `<audio>` element (`apps/web/src/voice/radioPlayer.ts`, no CORS needed that way). Reasons: root `AGENTS.md` section 6 "media never passes through the app server", no bandwidth on the operator (128 kbit/s per listener otherwise), and relaying would make the operator a rebroadcaster. **Consequences:** listeners are not in sync to the second, the station sees each listener's IP address (as with any radio player; turning the radio off for yourself disconnects, so the station then sees nothing), an `http://` address only plays on an https page where the browser upgrades it to https (Chromium and Firefox do; the admin tab warns), and a station that rejects browsers cannot be played. HLS (`#EXT-X-` playlists) is passed through and only plays where the browser does HLS natively (no hls.js: "no new dependencies").
- **Permission `CONTROL_RADIO` (bit 15, 32768):** "Webradio in Sprachkanälen starten und stoppen". Sorted into the `voice` group after `STREAM_VIDEO` and before `MODERATE_VOICE`; **the group title changed from "Sprache und Video" to "Sprachkanäle" / "Voice channels"** because the radio is neither (the re-check `packages/protocol/AGENTS.md` requires). Neither "Gast" nor "Mitglied" get it, and **no migration grants it** (nothing worked before that must keep working; administrators and owners have it anyway): an admin ticks it on a role. The station list is maintained with `MANAGE_SERVER`.
- **Protocol (additive, `PROTOCOL_VERSION` stays 4):** `RadioStation { id, name, url }`, `RadioUrl` (http/https, max 2048), `ChannelRadio { stationId, name, streamUrl, startedBy }`, `Channel.radio` (`.nullable().default(null)`), `ServerState.radioStations` and `ServerStructure.radioStations` (both optional: **a missing list means a server from before the radio, and the client then offers no radio button and no admin tab**; older clients strip the unknown fields). New `StructurePart` `"radioStations"`.
- **Database (migration 0017, generated):** table `radio_stations` (name, url), columns `channels.radio_station_id` (FK, set null), `radio_stream_url`, `radio_started_by`. The radio of a channel is **persistent** (survives a restart, keeps running in an empty channel: a lounge with a permanent station is a use case; clients only load the stream while they are connected to that voice channel) - Claude's decision, not confirmed by the user.
- **API (`apps/server/src/routes/radio.ts`):** `POST/PATCH/DELETE /api/radio/stations[/:id]` (`MANAGE_SERVER`, at most 200 stations; changing a station's address or deleting it turns the radio off in the channels playing it, a rename shows at once because channels carry the station's name via a join), `PUT /api/channels/:id/radio { stationId }` and `DELETE /api/channels/:id/radio` (`CONTROL_RADIO`, voice channels only, 404 `unknown_station`). Everything arrives through the `structure` event.
- **Playlists (`.m3u`, `.m3u8`, `.pls`; user's requirement "auch m3u"):** browsers cannot play them and may not fetch them across origins, so the **server resolves them when the radio is started** (`apps/server/src/radio/`: `playlist.ts` pure parser, `resolve.ts` fetch). Decided by the path's extension only, so a plain stream address causes **no server request at all**. The first http(s) entry wins, relative entries resolve against the playlist, a playlist may name another one (4 hops including redirects), a response with an `audio/*` type is taken as the stream itself, 5 s timeout, 64 kB body. **SSRF guard:** the address comes from a member, so every hop must resolve to public addresses only (`net.BlockList`: loopback, private, link-local, CGNAT, multicast, ULA, NAT64; redirects are followed by hand and checked again; **do not add `::ffff:0:0/96`: Node's BlockList matches IPv4 against it and would block everything**, the IPv4 rules already cover the mapped spelling, pinned by a test). Errors: 502 `radio_unreachable` / `radio_empty_playlist` / `radio_forbidden_host`. Consequence: a playlist on the operator's own LAN is refused; a direct stream address there works (the clients fetch it). Not covered: DNS rebinding between the check and the fetch.
- **Client:** `RadioPlayer` (UI-free, own tiny store like the voice client) lives in `App.tsx`: it gets the stream address only while the voice connection is `connected`/`reconnecting` to a channel with a radio, follows deafen (`el.muted`) and plays on **its own output device when one is chosen** (Einstellungen > Audiogeräte > "Webradio", user's wish of 17 September 2026; `VoiceSettings.radioOutputDeviceId`, per browser like every device id and therefore never in the directory account; null = "Wie Sprache" = the voice output device; `setSinkId`, Chromium only; the dialog only stores, `App.tsx` hands `radioOutputDeviceId ?? outputDeviceId` to `radio.setOutputDevice`, which switches a running stream over at once). **Volume (0-100 %) and the own off switch are stored per device** (`chat.radio.v2`; **the volume starts at 5 % until the user has set their own, user's requirement (first 30 %, then 15 %, then 5 % on the same day)**: stations are mastered far louder than voices, and the volume is only written once the slider was moved, so turning the radio off and on does not freeze the default; `chat.radio.v1` from the first day always stored it and is removed), deliberately not in the directory account (like the per-person volumes: depends on the headset; no directory change needed). "Off for me" unloads the element (no data, no connection to the station); moving the slider turns it back on. A stream that ends or fails reconnects after 2/5/15/30 s, the menu shows an error from the third failure on; blocked autoplay starts with the next click or key anywhere. `RadioControl.tsx` = the button in the stage head (`.radio-toggle`, icon `radio`, station name while one plays; **members with `CONTROL_RADIO` always see it, listeners only while a station is set**, user's requirement; **exactly as high as the Sprecher/Kacheln toggle `.seg` next to it**, user's requirement: its padding is the `.seg` frame of 3 px plus the `.seg` buttons' padding, and a zero-width `::before` keeps a text line box when only the icon shows; measured in headless Chrome, 35 px in all three states; whoever changes `.seg` changes `.radio-toggle` too) and its `ContextMenu`: station and status, own volume/off, and for controllers the station list (`menuitemradio`) plus "Radio für alle ausschalten". The sidebar marks a voice channel with a running radio (`.channel-radio`). Admin area > "Radio" (`RadioTab.tsx`, `MANAGE_SERVER`): add, rename, re-address and delete stations.
- **A typed address instead of a station (17 September 2026, user's wish: "eine URL-Eingabe für jeden mit Radio-Einstell-Rechten"):** the radio menu has a field below the station list; `PUT /api/channels/:id/radio` takes `{ stationId }` or `{ url }` (`SetChannelRadioRequest` is a union; the address follows `RadioUrl`, playlists are resolved and guarded exactly like a station's). `ChannelRadio.stationId` is null then and the name is the address's host (`channels.radio_name`, migration 0018 generated; `radioHostOf` in `state.ts`); a channel's radio is on while `radio_stream_url` is set. **Consequence the operator should know (README says so): with the station list only admins decided which hosts every listener's browser connects to; with a typed address everybody holding `CONTROL_RADIO` does, and whoever runs that host sees the IP addresses of the members in the channel.** The permission is granted deliberately and to nobody by default, and the user asked for exactly this, so there is no separate permission or switch. Twitch as a source: next entry.
- **Twitch as a radio source, shown with Twitch's official player (17 September 2026; user's decision after the options below were put to them: "Variante mit dem offiziellen Player, wie eine Videoübertragung in der Lobby; wenn der Benutzer das Radio-Audio muted, wird auch das zugehörige Video bei ihm ausgeblendet"):** a station's or typed address of the form `https://www.twitch.tv/<login>` (also without www, with m.; exactly one path segment, reserved pages excluded) is a Twitch source: `twitchChannelOf()` in the protocol, `ChannelRadio.twitchChannel` (`.default(null)`), derived from `radio_stream_url` when channels are loaded (no column, no migration); `resolveStreamUrl` normalizes the spelling and asks nobody, the name of a typed one is `twitch.tv/<login>`, and the "now playing" reader skips such channels (`index.ts`). **Why not audio only (probed the same day):** Twitch has no plain audio stream; the web player's unofficial API (`gql.twitch.tv` `streamPlaybackAccessToken`, the token carries the requester's `user_ip`) leads to a master playlist at `usher.ttvnw.net` with an `audio_only` variant (160 kbit/s AAC in MPEG-TS), but usher sends no CORS header to a foreign origin and the media playlist answers 403 to a foreign `Origin` (only the CloudFront segments are open), so a browser on our page cannot play it. The alternatives (server relays the playlists and clients use hls.js; server relays the audio, which makes the operator a rebroadcaster and costs bandwidth per listener) both lean on that unofficial API; the user chose the official embed. **Client:** `TwitchPlayer.tsx` is ONE `<iframe src="https://player.twitch.tv/?channel=...&parent=<location.hostname>&autoplay=true&muted=true">` mounted in `App.tsx` (body portal, `position: fixed`, z-index 4 = under menus and dialogs) for as long as the voice connection plays a Twitch source and the user has not turned the radio off; **Twitch's embed script is deliberately not loaded** (it would run in our origin next to the session in localStorage): the script is only a wrapper around `postMessage`, which `twitch.ts` speaks itself (`{ eventName: 11 SetVolume | 10 SetMuted, params, namespace: "twitch-embed-player-proxy" }`, read from `player.twitch.tv/js/embed/v1.js`; undocumented, harmless if Twitch ever ignores it). The player starts muted; on its first signs of life (`UPDATE_STATE`, `ready`, `video.ready`, `playing`, each answered once) and on every change it gets the user's radio volume first and then the mute state (muted = deafened or volume 0), so it never blasts at Twitch's own volume; after that a change made inside Twitch's own controls stays until our slider moves again. **One iframe that follows a slot** because moving an iframe in the DOM reloads it and unmounting it with the stage would cut the sound the moment a text channel is opened: the stage's Twitch tile (`TwitchTile` in `VoiceStage.tsx`, an item of kind `twitch` that counts like a screen share for the speaker view, real shares win) only reserves room (`TwitchSlot`), and a `requestAnimationFrame` loop lays the player over it, **completely: no bar, label or enlarge button of ours** (user's corrections of the same day: a status bar on the tile got in the way of the player's controls, and the player shows the channel's name on hover by itself; enlarging works through the "Sprecher" view or Twitch's own fullscreen). **[The pop-out described next was replaced the same day by a window of our own, see the next entry; `TwitchPlayer.tsx` became `EmbedPlayer.tsx`, `twitchPopoutSrc` is gone.]** **The one control of ours is "open in a window of its own"** (user's wish), the `.tile-window-actions` button of the video tiles, placed under Twitch's LIVE badge: `useTwitchPopout` opens `twitchPopoutSrc` (`player.twitch.tv/?channel=...&parent=twitch.tv&player=popout&volume=<radio volume>`, the shape of Twitch's own pop-out link) with `window.open`; while that window is open the embedded player is not rendered (the sound would play twice) and the tile shows the video tiles' "Wird im Pop-out angezeigt / Hier anzeigen"; closing the window brings the player back; the window is closed when the radio stops or changes, the voice channel is left, the radio is turned off for oneself or the page goes away; a blocked pop-up becomes the stage's notice. We cannot reach that window afterwards, so our volume is only its start value and deafen does not silence it. **Hover over a cross-origin iframe:** in the headless test the parent's `:hover` did not apply while the pointer was over the iframe, so the button does not depend on it: it stays clickable while invisible (`opacity: 0`, no `pointer-events: none`) and shows itself on its own `:hover`/focus as well as on the container's. **Twitch pauses a player that is too small and does not restart it while it stays small (measured: plays at 316x178, pauses at 276x155; its guidelines ask for 400x300), so `twitchPlayerBox` uses a slot only from 320x180 px; otherwise, and whenever the stage is not on screen, the player floats at 320x180 in the bottom right corner** (a box in the voice dock was tried first and paused at 212 px). "Radio for me off" unmounts the player: no tile, no floating window, no connection to Twitch. Not possible with an embed: a separate output device (the setting only applies to audio streams) and "now playing". **Operator facts (README):** `parent` must equal the page's host name, so the client must be served over https (or on localhost); Twitch sets its own cookies and sees every listener's IP address; ads and the mature-content gate are Twitch's. Verified in headless Chrome over the DevTools protocol against a live channel: plays, takes 5 % / 40 % / mute / unmute (read back from the player's state updates), keeps playing as the same iframe element when its tile shrinks below the limit, when the stage closes and when it returns into a big tile, and disappears when the radio is turned off; screenshot of tile and floating window. Also there: the pop-out address plays as a top-level window at the start volume 0.05, and our button appears on hovering its corner and receives the click. Not checked: inside the real app with two people, Firefox/Safari, autoplay with sound in a fresh profile without the headless autoplay flag.
- **Embedded players: pausing fixed, pop-out window of our own (17 September 2026, user's report: "es pausiert öfter mal, wenn ich in einen anderen Tab wechsle oder auspoppe/wieder einpoppe"):** measured in Chrome over the DevTools protocol: **Twitch pauses an embedded player 37 ms after its page becomes hidden** (another tab, minimized), **ignores Play while hidden and does not start again by itself**; Play works as soon as the page is visible. So `TwitchControl` (`embedControl.ts`, UI-free, tested) sends Play (command 3) when the page is visible again, unless the viewer paused it themselves (a pause while the page is visible), and also starts a player that came up without playing (`UPDATE_STATE` with `Idle`/`Ready` for 3 s; at most 4 tries, the channel may be offline). Listening with the tab in the background needs the pop-out: a window of its own stays visible. **The pop-out is now a page of OUR origin** (`apps/web/player-window.html` + `src/playerWindowMain.ts`, second Vite entry; pure part `playerWindow.ts`) that frames the official player and relays `postMessage` both ways plus its own visibility, instead of opening `player.twitch.tv` as a top page: measured, **the players only take commands from their parent page** (commands posted from the opener straight into the iframe are ignored), and the top-level Twitch page would not start with sound in a fresh window. With the relay the window stays under our control (volume, deafen, restart, YouTube's playing in step) and plays with sound without a click inside it. The page only frames `player.twitch.tv` and `www.youtube-nocookie.com` addresses (`playerOriginOf`), does nothing without an opener, and the server sends every `.html` with `no-cache` (`index.ts`, was only `index.html`). `usePlayerWindow` replaces `useTwitchPopout`. **Sound the browser refuses:** measured, a page whose player had been playing in the pop-out window could not start a NEW player with sound afterwards although `navigator.userActivation.hasBeenActive` was still true (muted it started; after any click in the page it started with sound; a pop-up that played nothing did not have this effect). So a player that should play but does not is set muted and told to play (YouTube then plays muted, Twitch does not even then), the viewer gets the notice `radio.soundBlocked`, and **the next `pointerdown`/`keydown` anywhere in the page turns the sound on** (`onGesture`). "Hier anzeigen" is such a click and is enough for YouTube; Twitch loads for longer than Chrome counts the click, so it asks for one more. Six German texts of the video pop-out that had `?` in place of umlauts ("In eigenem Fenster ?ffnen") were corrected on the way.
- **YouTube videos and live streams as a source, videos played in step (17 September 2026, user's wish: "das gleiche auch für YouTube-Videos und -Streams; Benutzer mit Radio-Recht steuern den Player bei Videos für alle (gleichzeitig Pause, Spulen usw.)", and during the work: "globale Steuerung muss nur bei Videos gehen, nicht bei Livestreams"):** `youtubeVideoOf()` in the protocol takes `watch?v=`, `youtu.be/`, `/live/`, `/shorts/`, `/embed/` (also m., music., youtube-nocookie) and the start offset (`t=90`, `t=1m30s`, `start=`); `ChannelRadio.youtubeVideo` and `ChannelRadio.playback` (both `.default(null)`). `resolveStreamUrl` normalizes to `https://www.youtube.com/watch?v=<id>` without a request; when the radio is started, the server asks **YouTube's oEmbed endpoint** (`radio/youtube.ts`; a fixed address, nothing the member typed is fetched) for the title, which names a typed address, and refuses videos that do not exist (400/404 -> `radio_unknown_video`) or may not be embedded (401/403 -> `radio_not_embeddable`); YouTube unreachable = no title, not a refusal. oEmbed does not catch every embedding ban (NASA's live stream answered 200 and then error 150 in the player): the client then shows a notice (`radio.errNotEmbeddable`). **Player:** the same single iframe, slot, floating window and pop-out as Twitch (`EmbedPlayer.tsx`, source kinds `twitch` | `youtube`, stage item kind `player`), `https://www.youtube-nocookie.com/embed/<id>?enablejsapi=1&origin=<our origin>&autoplay=..&mute=1&start=..`; **YouTube's `iframe_api` script is not loaded either**, `youtube.ts` speaks the widget's `postMessage` format itself (JSON strings `{event: "listening" | "command", func, args, id, channel: "widget"}`; the player answers `initialDelivery`/`infoDelivery` with `playerState`, `currentTime`, `playbackRate`, `volume`, `muted`, `videoData.isLive`, and `onError`; checked live: all commands work, about 4 reports per second, it keeps playing in a hidden tab). **Playing in step:** `RadioPlayback { playing, position, rate, at }` lives on the channel (`channels.radio_playback` jsonb, migration 0019; `at` = server time in ms, `radioPositionAt()`), starts as playing at the address's offset, and is changed with `PUT /api/channels/:id/radio/playback` (CONTROL_RADIO, YouTube sources only, else 409 `no_playback`; the server stamps `at`), which goes out as the **server event `radio.playback`** (no version bump) and stays on the channel for whoever connects later. Clients time it by the server's clock (`ServerConnState.clockOffset` from the welcome's `serverTime`). **Who steers:** members with CONTROL_RADIO steer through YouTube's own controls in their own player; `watchSync.ts` `decideSync` (pure, tested) tells their action from what a player does by itself: paused while it should play (only counts once the player has actually played since we last told it to, so a player the browser refused cannot pause everyone), playing while paused, ahead of the shared place (no player runs ahead by itself), time went backwards, another speed -> published; merely behind = buffering -> caught up (not again for 10 s, not while buffering). Everybody else is brought back when they pause or seek, with a notice (`radio.syncFollowOnly`); they can turn the radio off for themselves. After our own commands the player gets 2.5 s to settle; a paused player reports nothing, so `YoutubeControl` looks at it once per second itself (found in the browser check: a pause made during the settle time was never published); our own publication counts as the shared state at once and its echo from the server is no news (otherwise dragging the progress bar fights itself); a controller's player that buffers while the video is paused for everyone is not paused again (it swallowed their play). **Live streams are not steered for everyone** (user's decision): `decideSync` returns nothing for `live` reports, every viewer's player is their own. Known limits: a mid-roll ad that reports time 0 in a controller's player would count as a jump back (not seen in embeds so far); the radio output device does not apply to the players.
- **Radio stops when the channel is empty (17 September 2026, user's wish: "wenn niemand mehr im Kanal ist, soll nach 2 Minuten auch das Radio/der Stream beendet werden, in den Servereinstellungen abschaltbar"):** `ServerSettings.radioAutoStop` (optional = feature flag for older servers, column `server_settings.radio_auto_stop` default true, migration 0019; switch at the top of Admin > Radio, `PATCH /api/settings`). `radio/idle.ts` `RadioIdleStop` (tested with fake timers): `syncRadioMeta()` in `index.ts` (presence change, radio change, 30 s timer, once at startup) hands it the channels with a radio and nobody inside (none while the setting is off); a channel that stays on the list for `RADIO_IDLE_STOP_MS` (protocol, 2 minutes) is turned off after one more check against presence, setting and database, and the periodic sync does not restart the clock. After a restart an abandoned radio gets the full two minutes again; a radio started in an empty channel has two minutes for somebody to come. Env `RADIO_IDLE_STOP_MS` exists for tests only (smoke test, see root `AGENTS.md` section 7); the admin text says two minutes.
- **"Now playing" in place of the station's name (17 September 2026, user's wish: "wenn rich Informationen da sind und Platz zum Darstellen ist, sollen diese an Stelle des Sendernamens stehen"):** the rich information is the station's ICY metadata (`StreamTitle`, usually "Artist - Title"). A browser cannot read it from an `<audio>` element (and fetching the stream a second time with the `Icy-MetaData` header would double every listener's traffic and depend on CORS), so **the server reads it** (`apps/server/src/radio/metadata.ts` `RadioMetadata`, pure parser `icy.ts`): one connection per stream address, **only while a member sits in a voice channel playing it** (`presence.onChange`, the radio routes' `onRadioChange` and a 30 s timer call `syncRadioMeta()` in `index.ts`), the audio is thrown away. **This softens "no audio through the server": it costs the server the stream's bitrate (about 16 kB/s at 128 kbit/s) per listened station, not per listener, and nothing while nobody listens** (Claude's decision, not confirmed by the user; short polling was rejected because the example station sends the real title only after about 250 kB and every poll would count as a new listener there). Titles go to everyone as the **server event `radio.meta { channelId, title | null }`** on a change and after the welcome (no `PROTOCOL_VERSION` bump: older clients drop it and keep showing the name); a title equal to the station's name or its `icy-name` (what stations send between songs) counts as none, as does one without a letter or digit; UTF-8 with a Latin-1 fallback, at most 300 characters. **`node:http(s)` with `insecureHTTPParser` instead of `fetch`:** the example station's CDN answers an `Icy-MetaData` request with a header the strict parser refuses ("Missing expected CR after response line"). The same SSRF guard as for playlists applies per redirect hop, and here additionally at connect time (`lookup` option: the address actually connected to must be public, which closes the DNS rebinding gap for this path). Stations without `icy-metaint`, on internal addresses or with an "ICY 200 OK" status line simply have no title; failures retry after 5/15/60/300 s; nothing about playback depends on any of this. **Client:** `ServerConnState.radioTitles` (cleared on every welcome), `RadioControl` gets `nowPlaying`: the button shows the title instead of the name **only when it can be shown in full** - `radioLabel.ts` `fitsInstead` (tested): a hidden copy gives the title's width, the head's `.spacer` the free space, a label that is already cut off means no room at all; the rule gives the same answer whichever text is showing, so the label cannot flip, and it is decided in a layout effect (no flicker) and re-checked by a `ResizeObserver`. `.radio-toggle` may now grow to 26rem. The menu always shows station and "Jetzt läuft" (`radio.nowPlaying`), the tooltips of the button and of the sidebar mark name both. Verified: unit tests (ICY parser incl. chunk boundaries, apostrophes, encodings; label rule), live against the example station and SomaFM (titles after about 2 s, two channels share one connection), end to end against a test server (no event before somebody joins, title after joining, title for a client that connects later, `null` after leaving), headless Chrome screenshots of the real component at several head widths through the Vite dev server.
- **Verified:** unit tests (playlist parser, SSRF rules, settings), 6 new smoke checks, headless Chrome screenshot of button states, menu, sidebar mark and admin tab, and a headless Chrome playback probe: the user's example `https://streams.radiobob.de/bob-national/mp3-128/streams.radiobob.de/` (302 to the CDN) and the addresses resolved from SomaFM's `.m3u` and `.pls` reach `playing` in a plain `<audio>` element (SomaFM answers 403 to the `HeadlessChrome` user agent, so probe with `--user-agent`). The separate radio output device was checked in headless Chrome over the DevTools protocol with fake audio devices (`--use-fake-device-for-media-stream`; `--dump-dom` returns before `getUserMedia` answers, so it cannot be used for this): the playing example stream moves to another output with `setSinkId` without stopping, back to the default with an empty id, and an id that no longer exists is rejected (`NotFoundError`), after which the player simply stays where it was. Not checked: the feature in the running app with two real people, Firefox/Safari, real output devices.
