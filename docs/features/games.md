# Feature notes: game detection and game display

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. Whoever changes the feature adds or updates its entry here in the same step.

Code: shell `apps/desktop/native/system-watch/main.cpp` (the `game` lines and the watch list on stdin), `apps/desktop/src/main/gameWatch.ts`, `games/launchers.ts`, `games/scan.ts`, `games/match.ts`, `systemWatch.ts`; bridge `apps/web/src/platform/bridge.ts` (`DetectedGame`, `RunningGame`, `CustomProgram`, `GameWatchSettings`, `DesktopInfo.gameDetection`), `platform.games`; client `apps/web/src/gameDetection.ts`, `gamePresence.ts` (what goes out, what a viewer shows), `GameLine.tsx` (the display), `GamesTab.tsx`, the tab "Spiele" in `SettingsDialog.tsx`. Plan with all stages: `../squorli-directory/docs/PLAN-activity-games.md`.

**The user's decisions (20 September 2026):** others shall see which game somebody plays, with the game's icon. Off by default; one switch turns it on, and then friends and server members see it ("show on servers" is an opt-out inside the feature, one switch for all servers at first). Games come from the launchers: the client reports the launcher's id (`steam:730`), and name and icon come from the directory, never from the playing user or a foreign chat server; everything else shows a name only. The user can hide single games ("never show this one"); that list fills from what is installed, not from what was played, so an embarrassing game can be hidden before its first start, and it is kept per device. The game display and the AFK state stay independent: ten minutes without input or speech is away, even while a game runs. Fullscreen plays no part. Windows first, Linux within stage 2. Three stages: AFK signals (`docs/features/afk.md`), local detection (this entry), display for others.

**Stage 2, Windows part: local detection, nothing is sent (21 September 2026).**
- **What is installed.** `games/scan.ts` reads, without writing anything: Steam (`SteamPath` from the registry, `steamapps/libraryfolders.vdf`, every `appmanifest_<id>.acf`), the Epic Games Launcher's `.item` manifests (whole games only: `bIsApplication`, category `games`, not an add-on of another game, not unfinished), GOG's registry entries (not those that depend on another), and the Xbox app's folders (each drive's `.GamingRoot` names the folder, which the user may have renamed; `Content\MicrosoftGame.config` gives store id and name; add-on packs have nothing to start and are left out). Parsers in `games/launchers.ts` (pure, tested): Valve's text format, `reg query` output, the Epic JSON, the Xbox XML. Ids: `steam:<appid>`, `epic:<AppName>`, `gog:<id>`, `xbox:<StoreId>`, never an executable's name (names like game.exe collide). Not read yet: Ubisoft, EA, Battle.net, Riot.
- **What runs.** The shell hands the system watch helper a watch list on its stdin: the folders of the installed games and the executables the user added (`games/match.ts` `watchLine`). Once a second the helper walks the visible top-level windows from the top of the z-order down (no owned windows, no tool windows) and prints `game <path>` for the first one whose program lies in the list, which is the game used last, and `game` alone when none has a window any more. **The helper never reports a program outside the list**, and while detection is off the list is empty and the launchers' files are not even read. A program counts while it has a window of its own, minimized or behind other windows too, so a game that ran before the app or before the switch is found; a service that merely runs (Wallpaper Engine draws into the desktop's window and has none of its own) does not count. What is known about a process is asked once and forgotten every minute and at every new list. `gameOfPath` maps the path to the game (an added program by its exact path, else the deepest installation folder that holds it). Install paths stay in the main process; the client gets id, name and source.
- **Settings, per device** (`gameDetection.ts`, `chat.games.v1`: the switch, the hidden ids, the added programs; pure parts tested). Einstellungen > Spiele (only where `platform.games` exists): the switch with a text that says what is read and that nothing is shown to others yet; "Gerade erkannt"; the list of installed games and added programs with a tick each (no tick = never shown), a search from 12 entries, "Programm hinzufügen" (the system's file dialog through the shell, then a name) and "Neu einlesen". The shell checks added paths once more (`readGameWatch`: a full path of an .exe on a drive, no tabs or line breaks, at most 100). The list is read again when the tab opens, on "Neu einlesen" and hourly. When the display for others comes, the switch moves to the account's settings; the hide list stays on the device.
- **The build** of the helpers moves a running helper aside (`.exe.old`): Windows lets a file in use be renamed but not overwritten, and a developer's running app holds the helper. `electron-builder.yml` packs `*.exe` only.

Checked: typecheck, tests (desktop 49: `launchers.test.ts`, `match.test.ts`, the game lines in `systemWatchLines.test.ts`; web 295: `gameDetection.test.ts`), build, both helpers compile without warnings. The helper alone: a watched executable in front is reported within a second, a folder entry too (with umlauts elsewhere in the line), an empty list ends it, a folder that does not hold it reports nothing. The real scan on the user's computer: 33 games in 30 ms (Steam 26, Epic 2 of 8 manifests, Xbox 5 on two drives, one of them with a renamed folder, add-on packs left out; GOG is not installed there). The unpackaged app with a scratch profile over the DevTools protocol: `info.gameDetection`, no list while off, the app's own executable added as a program is reported as running, a malformed entry is dropped, no paths in what the client gets, switching off ends the running game. The tab by headless Chrome screenshots of a harness page (on, hidden game, off, end of the list with a long name and an added program). **Not checked: a real game in front** (Steam, Epic, Xbox: whether the path Windows reports for an Xbox game lies under its `Content` folder is open), a game protected by anti-cheat, the file dialog, GOG on a real installation, a packaged app.

**The user's first test and two fixes (21 September 2026):** "Ich habe ein Spiel im Vordergrund, es wird nichts angezeigt" (`pnpm dev:desktop`, Aviassembly from Steam, which the scan knew). Two causes. (1) The client: `GameDetection` subscribed to the running game in its constructor and App.tsx ended that subscription in an effect's cleanup; React's development mode runs every effect twice, so under Vite the detection was deaf for good (a built client was not affected). Now `start()` tells the shell the settings and subscribes, called from the effect, returning the cleanup; tested by stopping and starting once more. (2) The helper's first version only looked at the window in front and took a game from the moment it came to the front: a game already running when the switch was turned on, with Squorli in front, was not found until the user went back into it. Replaced by the walk through the windows described above. Checked against what ran on the user's computer: with Steam's folder watched the helper reports Aviassembly while another window is in front, with only Wallpaper Engine's folder watched it reports nothing (that program ran, too), an empty list ends the game; the built React client in a scratch instance tells the shell its stored settings by itself after a reload (a fresh subscriber learns the running program). **The user's second test (21 September 2026): all successful.** "Erkennung funktioniert in Steam, XBox und Epic", the Steam and the Xbox title were multiplayer games with anti-cheat, and an added program is detected too (which also covers the file dialog). So the path Windows reports for an Xbox game does lie under its `Content` folder, and anti-cheat does not keep the helper from asking for a process' path. Still not checked: GOG on a real installation, a packaged app.

**Stage 3, step 1: the directory's game library and its protocol part (21 September 2026).** `packages/protocol/src/directory.ts` (copied to the directory repo): `LibraryGameId` (`steam:<app id>`, `gog:<product id>`, `xbox:<store id>`; the ids the detection here produces for those launchers fit, Epic and added programs have no catalog and stay local with a name), `DirectoryGame` (`id`, `name`, `show`, `iconUpdatedAt`), `directoryGameUrl`, `directoryGameIconUrl`, `features.gameLibrary`. The directory answers `GET /api/games/<id>` with what the launcher's own catalog says, public and cacheable like avatars; `show: false` marks what is no game (Steam tells applications such as Wallpaper Engine and tools apart from games), so the playing client will not report it and viewers will not show it. No client code uses it yet. Checked here: typecheck, protocol tests 61 (2 new); the service side in the directory repo's notes.

**Stage 3, step 2: reporting the game (21 September 2026).** From here on something leaves the computer, so the texts of Einstellungen > Spiele say so. How it works:
- **Protocol** (`friends.ts`, copied to the directory repo; `index.ts`): `GamePresence` = `{ id?, name }`, `id` a `LibraryGameId` only, `name` one line of at most 64 characters (`GameName`). It rides on the `activity` report of both sockets as an optional `game` (a game, null = none, left out = the message says nothing about it, which is what clients from before send); `Member.game`, `Friend.game` and `friends.presence.game` default to null. No version bump and no new flag: servers and directories from before it drop the unknown field unread, older clients drop `game` from what they receive. The two switches are user settings and follow the account: `AccountSettings.games` = `{ enabled (false), servers (true) }`, optional without a default on purpose, like the message cue: an account from before it, or a directory that does not know the field, says nothing and the device's value stays (`accountSettings.ts`, all three functions; `VoiceSettings.games`).
- **What goes out** (`gamePresence.ts`, pure, tested): an id leaves the computer only when it is a launcher's id the directory's library can know; **the id of an added program contains its path and never goes anywhere**, such a game and an Epic one go out by name alone. The playing client asks the directory's library first (`directoryGameLookup`, once per id and session): `show: false` = nothing is reported (Wallpaper Engine, tools, the operator's word), an id the catalog does not know goes out by name alone, and when the directory cannot be asked, id and local name go out. The name is the directory's when it has one. The hide list and the switch are applied before all that (`GameDetection.state.shown`).
- **Who gets it:** `Store.setGame(game, onServers)` hands it to the directory socket always (friends) and to every chat server connection only while "Auch den Mitgliedern meiner Server zeigen" is on; fresh connections learn it after their welcome. The store stays free of the platform: App.tsx feeds it from the detection and the account's switch turns the detection on (`GameDetection.setEnabled`; the switch is no longer stored in `chat.games.v1`, which keeps the hide list and the added programs per device).
- **Chat server:** `Hub` keeps the game per connection like the idle state; a member's game is the last report among their connections and goes with that connection; presence listeners fire on a change, so the member list is broadcast (`state.ts` `Member.game`). The server only relays: it checks the schema and nothing else, viewers ask the directory. A connection's changes take effect at most every 5 s (`GAME_CHANGE_MS` in `ws/handler.ts`; each is a broadcast to everybody), what arrives in between waits and the last one counts. AFK and the game are independent. The directory does the same for friends and additionally drops a report whose id its library knows as "not shown".
- **A consequence of the user's decisions to know about:** the switch follows the account, the hide list stays on the device. Switching the display on at one computer turns it on at every computer with the app, and a game hidden here is not hidden there. The settings' texts say both.

Checked: typecheck, tests (protocol 66 with `games.test.ts` 5; server 62 with 3 new in `hub.test.ts`; web 303 with `gamePresence.test.ts` 5, the rewritten `gameDetection.test.ts`, 1 new in `accountSettings.test.ts`; desktop 49), build. Smoke test on :3001 against a fresh scratch database without a directory: 121 green (4 new: a reported game reaches every member next to the afk state, an id that is no launcher's is refused while a name alone is relayed, a report without the field leaves the game alone, null removes it). The directory's side: its notes. **Not checked: the whole way from a running game in the desktop app to another client** (the pieces are tested one by one; nothing displays a game yet, that is step 3), two real people, a client and a server of different ages together (only by the schema tests).

**Stage 3, step 3: the display (21 September 2026).** "Spielt X" with the game's icon, in every client, the browser too (only the desktop app can report, everybody can see). Where: the member list (the line under the name; it takes the place of the handle line while somebody plays, the handle stays in the member's menu, which shows the game as well), the friends list (a second line under the name) and the head of a conversation with a friend. Offline members and friends show none.
- **What a viewer shows** (`gamePresence.ts` `shownGameOf`, pure, tested): a game with a launcher's id shows **the directory's name and icon**, whatever name the playing client sent along; what the directory does not call a game shows nothing, also when a client that did not ask reports it; while the directory's answer is still out nothing shows, so a hidden program never flashes up. A game by name alone (Epic, an added program), an id the catalog does not know and a directory that cannot be asked show the reported name, which is the playing user's own text like a display name, with a gamepad instead of an icon. Without a directory, or with one that has no library, every game shows by its reported name.
- **How** (`GameLine.tsx`): App.tsx hands the one `directoryGameLookup` it also reports with down through `GameLibraryContext`, so an id is asked once per session for both sides; `peek` answers what is known without a render in between, so a list drawn again does not blink; a failed request leaves its id alone for a minute (`GAME_LOOKUP_RETRY_MS`), since every row of a member list asks for the same game. The icon is a plain `<img>` from the directory (`directoryGameIconUrl`, cacheable for good through `?v=`), without a referrer, and gives way to the gamepad when it does not load. The full text is the line's tooltip, long titles are cut with an ellipsis.
- **What a viewer gives away:** asking for name and icon tells the directory this viewer's address and the game's id, not who plays it; the same as with avatars.
- **Not built, on purpose:** icons in the list of Einstellungen > Spiele from the directory. Asking the library for every installed game would hand the directory the list of a user's games, and the settings promise that only the running game is sent; icons there have to come from the computer itself (open in stage 2).

Checked: typecheck, tests (web 306: 3 new for `shownGameOf`, the lookup's test now covers `peek` and the minute after a failure), build. A harness page under the user's Vite with the real `MemberList` and `HomeSidebar`, by headless Chrome screenshots at 1500 and 700 px, **asking the public directory** (which carries the library since the user's update): Counter-Strike 2 shows the directory's name and its icon although the harness reported another name, a game by name alone and an id Steam does not know show the reported name with the gamepad, Wallpaper Engine and an app from the Microsoft Store (`show: false`) show the handle line and no game, an away friend shows moon and game, offline rows show none, a long title is cut; the member's menu by a DOM dump after a click. The harness was removed afterwards. **Not checked: the whole way with two real clients** (a running game in the desktop app, seen by another account), the head of a conversation (markup only), a phone's width beyond the friends list.

**Open in stage 2:** Linux (no helper there: Steam's `SteamAppId` in a process' environment is the likely way), the games' icons in the list, more launchers, a small maintained list for programs that hide behind another executable (Minecraft Java is `javaw.exe`).
