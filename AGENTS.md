# AGENTS.md – Working guide for AI agents and new developers

This file is the central project description for all coding agents (Claude Code, Codex, Cursor, etc.).
`CLAUDE.md` includes it and only adds Claude-specific rules.
**Mandatory:** Whoever changes the structure, commands, configuration, protocol or milestone state updates this file in the same step.

Last check of the complete workflow: 14 September 2026 (all green, see section "Verified state").

## 1. What the project is

**Video pop-outs and fullscreen (15 September 2026):** Camera and screen tiles expose separate-window and fullscreen buttons. `VideoWindows.tsx` manages one window per track at App level, retaining it across text/stage view changes, moving video display into the pop-out with a restore placeholder in the main stage, and closing windows when their track disappears or the main page closes. Pop-outs have no frame or app header/footer; fullscreen and per-feed volume controls appear as a neutral hover/focus overlay (always visible on touch); double-click or F/Enter toggles fullscreen. Existing audio elements move between documents: microphone audio follows camera pop-outs, screen audio follows screen pop-outs. This preserves one playback instance, volume, output-device selection and global deafen. Closing/restoring a pop-out returns its video and audio to the main window. Autoplay failures show a temporary unblock button. Fullscreen uses the target element's document, with translated blocked/unsupported/failure messages. Shared view detach and fullscreen behavior have unit coverage in `videoDisplay.test.ts`. Real multi-window/media browser acceptance is pending; no browser is connected in the editing environment.

**Voice connection card (15 September 2026):** `VoiceDock.tsx` now separates connection status, channel/server names, the stage shortcut, audio-unblock notices, microphone meter/muted label and equal-size controls. Toggle buttons expose pressed states, the connection label is a live status, and the mobile navigation scrolls to keep the taller voice dock reachable. Existing version 2 brand tokens and voice behavior are preserved; German/English stage labels updated together.

**Member context menus (15 September 2026):** Member buttons open a floating body-portal menu on right-click or ordinary click (also keyboard/touch). `ContextMenu.tsx` supplies viewport positioning, outside dismissal, Escape/Tab handling and arrow-key navigation; role selection and voice-channel moves use hover/click/keyboard submenus that flip left near the viewport edge. Existing moderation permissions and confirmation dialogs are preserved. `menuPosition.test.ts` covers six placement cases. No server, protocol or brand-package change.

**Web UI refresh (15 September 2026):** The browser client uses the existing version 2 brand tokens for a framed conversation area, roomier navigation, member handles and a profile dock. `apps/web/src/Avatar.tsx` is the shared image/initials presentation component for channel messages, DMs, members, friends, voice participants and profile previews. It accepts an optional image URL and falls back on load errors; avatar upload, persistence and protocol fields are not implemented. At <=700 px, navigation is collapsible and the server rail is horizontal. The brand package and sibling projects are unchanged. Verification: typecheck, all 50 tests and production build passed; browser visual/interaction review remains pending because no browser was available.

**Published container documentation (15 September 2026):** The official image is `ghcr.io/danielklessa/squorli-server:latest`, listed at https://github.com/danielklessa/squorli-server/pkgs/container/squorli-server. README and website guides document APP_IMAGE, profile/overlay-aware pull and up --no-build, image pinning and the local-build alternative. Portainer users must explicitly set APP_IMAGE to override the stack's legacy default. This documentation update does not change runtime defaults.

**Public source address:** Always use https://github.com/danielklessa/squorli-server for the open-source server in documentation, website links and clone examples. Internal development remotes and container registry settings are separate; this rule does not change them.

**Website and brand update (15 September 2026):** Squorli Server is the open-source project (Apache License 2.0, see `LICENSE`); Squorli Directory is not open source and is operated at https://directory.squorli.com. The sibling `../squorli-website` uses Astro/Vite for the German/English website at https://squorli.com and German/English technical guides. Read `docs/brand/PRODUCT.md` for shared product wording. Canonical `docs/brand/` must now be mirrored to **both** siblings and all three runtime brand folders. From the website run `pnpm brand:sync`, then `pnpm brand:check`. Update affected README/plan/public-copy descriptions together. Website-only documentation changes do not imply backend or protocol changes.

**Squorli**: self-hosted community chat with voice and video channels (modeled on Discord, but every server belongs to its operator).
Solo development, TypeScript/Node, shipped as Docker containers. The name Squorli applies since 14 September 2026 (user's decision) in the code, in package names (`@squorli/*`), Compose projects, image tags and in the user interface.

**Brand and design: all questions about logo, colors, typography, spacing and tone of voice are governed by [docs/brand/AGENTS.md](docs/brand/AGENTS.md)** (brand package version 2 with assets, `squorli-tokens.css`, `palette.json`, `brand-guide.html`). Read it before any design change; the tokens have been adopted as `--sq-*` in `apps/web/src/styles.css` and `apps/directory/web/static/style.css`, the SVGs exist as copies under `apps/web/public/brand/` and `apps/directory/web/static/brand/` (the source remains `docs/brand/`; on changes, update both copies).
Product plan, architecture decisions and milestones: [docs/PLAN.md](docs/PLAN.md). Read it before building larger features.

**Current state: M3 (video and screen share) implemented in the browser; webcam and screen share transmission tested successfully with real devices (15 September 2026). Remaining acceptance (15 real cameras, tab audio from Chrome for everyone, test matrix 3.6) pending. M6a-M6d done (directory: handles, password backup, authenticator, devices, server registration and server directory). M7 friends and end-to-end encrypted direct messages via the directory done (14 September 2026; plan in `../squorli-directory/docs/PLAN-friends-dm.md`).** Available: everything from M2 (login with membership, categories/channels, roles, kick/ban, text chat with attachments, admin panel) plus camera with simulcast, stage with tile and speaker view, screen share with audio as a separate audio track (only Chromium delivers audio, other browsers get a notice), video bitrates in the debug view, test page `/test/screenshare.html` for the browser matrix, video bots. Voice as in M1 (LiveKit, VAD/PTT, device selection). Remaining M1 acceptance (restrictive network, TURN) deferred, see section 8.
**M6 brought forward (user's decision, 14 September 2026):** directory service so that registration works properly. **Since 14 September 2026 it lives in its own, unpublished repo `../squorli-directory`** (user's decision: the directory is not published with the chat; until then `apps/directory` in this monorepo). Operated on a **dedicated host with its own subdomain**; this repo only knows `DIRECTORY_URL`. Sync rules for the shared protocol part and the brand package: section 2a. The second factor is a TOTP authenticator; SMTP is prepared in configuration and schema but will only be implemented later. Phases: **M6a (done)** register and resolve handles, chat server shows verified handles; **M6b (done 14 September 2026)** password-encrypted key backup: create an account (handle + password) directly on the service's account page (user's wish), log in on any chat server with handle + password, change the password on the account page, backup for existing browser keys in the login; **M6c (done 14 September 2026, without e-mail)** TOTP authenticator and recovery codes as second factor for key retrieval and account changes (user's decisions of 14 September 2026: factor on retrieval + password change + disabling + regenerating codes, never on chat login by key; setup only on the account page; dependency `qrcode-generator` allowed), device management = sessions per chat server with remote logout (Profile > Geraete) plus a read-only display of key retrievals on the account page (the service has no sessions; whoever has the key has it); **M6d (done 14 September 2026)** server registration with host proof (1/2) and server directory (2/2): server rail with the own handle's servers, public listing with description/icon/member count/open join, icons served by the directory, join via link.
**Voice channel moderation (13 September 2026, user's requirement):** permission `MODERATE_VOICE`: move members to other voice channels or remove them, end their camera/screen share, block camera/screen per member (`members.stream_blocked`, overrides roles). LiveKit enforces muting and publish permissions server-side (`livekit/admin.ts`), the client follows via WS event. Also: camera selection with multiple cameras, background blur (`@livekit/track-processors`), separate output device for screen audio.
**Roles (user's decision, 13 September 2026):** the default role is "Gast" (guest) and may only see channels and join voice channels. "Mitglied" (member: write, attach, invite, camera/screen) is assigned manually by admins; migration 0004 automatically turned existing members into "Mitglied".
Decisions from PLAN 9 for M2 (preliminary, made by Claude on 13 September 2026, not confirmed by the user): text chat = channel messages with edit/delete, no reactions/threads (direct messages came with M7 on 14 September 2026, user's decision: 1:1 only, between friends, end-to-end encrypted via the directory); moderation = role permissions + kick/ban, no audit log, no report function; permissions apply server-wide, no channel overrides. Not available: desktop client (M4), TURN acceptance.

## 5. Conventions

- **Language:** Documentation, READMEs and AI instructions (AGENTS.md, CLAUDE.md, docs/, deploy READMEs, comments in env templates and deploy configs) are always in English (decision of the user, 14 September 2026). Code comments are English. **UI texts are bilingual German/English (user decision, 15 September 2026):** every text a user sees in the web client comes from the catalogs `apps/web/src/i18n/de.ts` (reference, all keys) and `en.ts` (same keys, enforced by the `Messages` type and the test) via `t("key", { params })`; never write a literal German or English sentence in a component, an error mapping or the voice core. The locale is fixed at page load: an explicit choice in `localStorage` (`chat.locale`, select in the login footer and in Profile > Profile) wins, otherwise the first entry of `navigator.languages` we support, otherwise English. Dates use `fmtDateTime`/`fmtTime`/`fmtDay` from the i18n module (`localeTag`). The 503 page of the server picks German or English from `Accept-Language` (`preferredLanguage()` in `src/index.ts`). **Everything a user sees carries real umlauts** (ä/ö/ü/ß) in the German catalog (user requirement 13 September 2026); the ae/oe/ue transliteration is used only in comments, identifiers and developer log lines. `PERMISSION_LABELS` in the protocol package stays German and is no longer used by the client (labels come from the `perm.*` keys).
- **Formatting:** `.editorconfig` (2 spaces, LF, UTF-8, newline at end of file). No linter/formatter configured; keep the existing style (compact one-liners are common).
- **TypeScript:** `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`. ESM everywhere (`"type": "module"`). Imports without file extension.
- **Validation:** All inputs (HTTP bodies, WS messages, env) go through zod schemas. Define new REST/WS types first in `packages/protocol/src/index.ts`, derive the types from there, never declare them twice.
- **Protocol version:** Bump `PROTOCOL_VERSION` in `@squorli/protocol` on incompatible changes (currently 4; new permission bits are not an incompatible change, new server events are, because the client parses them strictly with zod); the server rejects other versions with WS code 4002. The constant is also in `apps/server/scripts/smoke.mjs`, update it there too.
- **Voice channel presence vs. media:** `voice.join`/`voice.leave` over the WebSocket are the intent ("I am in the channel", for everyone's sidebar). Whether someone actually sends, hears or speaks is known only to LiveKit; the client shows both together. Participants known only to LiveKit (bots) appear as "(extern)" (external).
- **Mute and deafen (Discord logic, user requirement 13 September 2026):** `setMuted()` = microphone muted by hand; `setDeafened()` = incoming audio muted (`<audio>.muted`) **and** microphone force-muted. Undeafening restores the microphone only if it was not muted by hand (`micMutedByUser` in the voice core). Clicking the microphone while deafened ("Ton aus") lifts both. Deafen ("Ton aus") is set as the LiveKit attribute `deafened` (token grant `canUpdateOwnMetadata`) so others see it in the sidebar and tiles.
- **Voice codec:** always Opus in the browser (mandatory WebRTC codec, nothing better available). Quality per voice channel in the admin panel: `audioBitrate` (kbit/s, choice from `AUDIO_BITRATES`, default 64) and `audioStereo`. Mono = DTX + RED (silence costs nothing, redundancy against packet loss) with the browser's echo/noise suppression; stereo = `forceStereo`, capture with `channelCount: 2` and **without** audio processing (which would mix down to mono), for music. Changing the channel switches connected clients live (`setAudioProfile()`: republish the microphone).
- **Unlock audio inside the user gesture:** `client.prepareAudio()` sits in `App.joinVoice()` before the first `await`. It creates the single shared `AudioContext` (microphone gate and level meter hang off it), calls `resume()` and plays 0.1 s of silence once (`SILENT_WAV`) so that Safari/Firefox unlock `<audio>` playback for the document. Without this the context was only created after the token and `room.connect()`: level 0 (nobody heard the user) and silent playback on the first join (reported by two users on 14 September 2026). In addition, every gesture in the document (pointerdown/keydown, capture) releases blocked audio; the dock shows "Ton freigeben" (release audio, playback) or "Mikrofon freigeben" (release microphone, context not `running`), the debug view shows the "Audio" line. `MicPipeline.start()` waits for `resume()` at most 300 ms.
- **Speaker outline:** own participant = `gateOpen && !micMuted` (immediate). Others = local RMS measurement per subscribed microphone track (AnalyserNode, 50 ms, `VoiceGate` with threshold 0.015 and 250 ms hold, `addMeter()`); LiveKit's `isSpeaking` (server notification, ~0.5-1 s later) only as a fallback when the audio context is not running. `deploy/livekit/livekit.yaml` sets `audio.update_interval: 150` for this.
- **Speech gate is local:** voice activation and PTT switch a GainNode in `micPipeline.ts`, not the LiveKit track. The track stays published and "unmuted"; only the mute button uses LiveKit mute (visible to others). This avoids signaling on every word (PLAN 3.5).
- **Owners (several, 14 September 2026):** `server_settings.owner_id` = first owner (at first login, irrevocable), further ones via `members.is_owner` (`PUT /api/members/:id/owner`, owners only, not oneself). `actorOf()` sets `isOwner` from both, the bootstrap marks the first owner in `members` retroactively. Owners always have `ADMINISTRATOR`, rank above every role (`outranks`), cannot be kicked/banned/moderated and are at the very top of the member list. `Member.isOwner` in the protocol; `ServerSettings.ownerId` remains the first one.
- **Only with account (user requirement, 14 September 2026):** `server_settings.require_account` (migration 0011, admin panel > Server, `PATCH /api/settings`). `/api/auth/verify` rejects keys without a directory handle with 403 `account_required`; owners and the very first login are exempt (no lock-out), existing members without a handle are locked out too. If the directory is unreachable, the cached `users.handle` counts. Without `DIRECTORY_URL` the option has no effect and `/api/health` reports `requireAccount: false`; the admin panel disables the checkbox. **Forcing at deployment:** `REQUIRE_ACCOUNT=true|false` in the environment overrides the stored setting (`setRequireAccountForced()` in `state.ts`, applied in `loadSettings()`), `ServerSettings.requireAccountLocked` is then true, `PATCH /api/settings` with `requireAccount` answers 409 `locked_by_config`, the admin panel shows the checkbox disabled with a note. Empty = the admin panel decides. The login screen hides the browser-key path entirely for a key without handle (only "Mit Konto anmelden" remains, with a note); a key with a verified handle is an account and keeps the usual path.
- **Multi-server client (14 September 2026, user's requirement):** the web client of one server talks to other Squorli servers directly (`ServerApi` with `base` = their origin, WebSocket `wss://<host>/api/ws`, LiveKit URL from their `/api/rtc-token`). The rail switches the shown server without leaving the page; the voice connection stays on its server until the user joins a voice channel on another server, which disconnects the previous one. Login at a foreign server = the same browser key, signature over that server's `/api/health` domain, no invite (the rail only lists servers the handle is a member of); its session token is kept per host. Consequences: every chat server answers CORS for **all origins** (`@fastify/cors` `origin: true`, auth is Bearer-only, no cookies, so a foreign origin cannot act without the token; the signature stays bound to `PUBLIC_DOMAIN`), relative server URLs (attachments, icon) are resolved through `api.abs()`, older servers without CORS show "nicht erreichbar oder erlaubt keinen Zugriff aus anderen Clients" with a link to open them directly. The admin panel, profile dialog (devices, name on this server), member list and chat always act on the active server. Not multi-server: the login screen, the directory account and the friends/DM view (they belong to the own server's directory).
- **Server directory (M6d, 14 September 2026):** the chat server sends `name`, `listed`, `description` (max 200), `openJoin` and `memberCount` with every registration (`ServerRegisterRequest`); the directory fetches the icon itself from `<proofUrl-Basis>/api/server-icon` (host is proven, raster images up to 2 MB, `iconUpdatedAt` stays when the bytes are unchanged) and serves it under `GET /api/servers/<host>/icon`. Clients therefore load server icons only from the directory (`directoryServerIconUrl()`), never from foreign servers. Public listing `GET /api/servers` = servers with `listed` that registered within 3 days. Admin panel > Server: "Im Serververzeichnis auflisten" + Beschreibung (disabled without directory). Changing name/listed/description/openJoin/icon re-registers (debounced 1.5 s, registration limit at the directory is 10/min per IP). Join via link = open the server's own origin.
- **Login splash:** server icon and server name from `/api/health` at the top of the login card (fallback: Squorli icon mark and "Squorli"), footer "Betrieben mit Squorli · Version <version>" below the card; `version` comes from `apps/server/package.json` (read at startup, `../package.json` relative to `dist`/`src`, also in the container).
- **Server name and icon:** `/api/health` returns `serverName` and `iconUrl` so that title and favicon are already correct in the login; when logged in, `settings.name`/`settings.iconUrl` apply (live update via `structure`). Icon only as PNG/JPEG/WebP/GIF up to 2 MB (no SVG: could contain scripts and is served same-origin), file `DATA_DIR/server-icon`, URL with `?v=<timestamp>` and `immutable` cache.
- **Checking permissions:** Every protected route fetches `requireMember()` and checks `can(actor, Permission.X)`; effects on other members/roles additionally `outranks()`/`canTouchRole()`/`canGrant()` from `authz.ts`. The owner is always administrator. Structure changes end with `broadcastStructure()`. New permissions: append the bit in `permissions.ts`, add the label, and for existing servers write it into the appropriate role via a custom migration (`drizzle-kit generate --custom`) (see 0003/0004 as examples); the bit values are pinned in `index.test.ts`.
- **Media permissions twice:** camera/screen only with `STREAM_VIDEO` and without a block (`members.stream_blocked`, subtracted in `actorOf()`). The client hides the buttons, the app server writes `canPublishSources` into the LiveKit token (microphone always; camera, screen, screen audio only with the permission). LiveKit enforces it; on changes at runtime via `RoomServiceClient.updateParticipant` (`livekit/admin.ts`).
- **Moderation takes effect server-side:** stopping camera/screen = LiveKit `mutePublishedTrack` + WS `voice.stop`; moving = WS `voice.moved` (the client fetches a token for the target channel itself and joins, the server checks that like any join). Only with `MODERATE_VOICE`, never against the owner or oneself, rank must be higher.
- **Background blur:** `@livekit/track-processors` (BackgroundBlur, MediaPipe segmentation in the browser). Loads WASM from jsdelivr and the model from storage.googleapis.com; without internet on the client the effect does not work (self-host later via `assetPaths`). Check support via `supportsBackgroundProcessors()`; Firefox/Safari show the option disabled.
- **Separate output for screen audio:** `setSinkId` per `ScreenShareAudio` track (Chromium only). LiveKit's `switchActiveDevice("audiooutput")` re-routes all tracks, as does `MediaDevicesChanged`; `applyScreenSink()` therefore runs again after subscription, device change and settings change. The debug view shows device, track count and errors ("Bildschirm-Ton Ausgabe"); without a track (0) there is simply no remote share with audio yet.
- **Video (M3):** camera 720p with simulcast (180p/360p/720p, VP8), `adaptiveStream` + `dynacast` in the room: receivers get the layer that matches the size of the `<video>`. The stage only has to render the `<video>` at a suitable size. Screen share: 1080p30 (`ScreenSharePresets.h1080fps30`, up to 5 Mbit/s), **without simulcast** (otherwise adaptiveStream fetches the coarse layer for small tiles, text becomes unreadable), `contentHint: "detail"`. It always requests `audio: true` and publishes the audio as its own track (`ScreenShareAudio`), never mixed with the microphone; whether audio arrives is reported by `screenAudio` in the state, `explainScreenAudio()` provides the hint text. Cancelling in the browser dialog (NotAllowedError/AbortError) is not an error.
- **Database:** Change the schema only in `apps/server/src/db/schema.ts`, then `pnpm db:generate`. Migrations are applied automatically at server start; do not edit generated SQL files by hand.
- **Configuration:** Exclusively via environment variables, validated in `config.ts`. The server loads `apps/server/.env` via `process.loadEnvFile` (built into Node, no dotenv dependency); variables already set take precedence. In the container there is no .env file, everything comes via compose.
- **No new dependencies** without need; if necessary, pin the version as before (caret ranges) and commit the lockfile.
- **Directory service (M6):** The chat server never depends on the service: handle resolution at login is best effort (timeout 2.5 s, errors only logged), display falls back to the display name or `anon-<key>`. The web client calls the service directly (URL from `/api/health`, CORS open for GET/POST). Registration = signature over the service's host + handle + nonce; one key has exactly one handle, handles are immutable (M6a). The service itself (routes, schema, account page, smoke test) lives in `../squorli-directory` (section 2a).
- **Key backup (M6b):** The private key leaves the client only encrypted. `packages/protocol/src/backup.ts`: PBKDF2-SHA256 (600,000 iterations, 16-byte salt) -> HKDF into two keys: AES-256-GCM (encrypts the 32-byte seed, stays in the client) and auth key (is sent, the service stores only its SHA-256 in `key_backups.auth_hash`). Storing: `PUT /api/backup`, signed over "community-directory-backup\n<host>\n<nonce>\n<ciphertext>", upsert (= change password). Fetching in two steps: `GET /api/backup/:handle/params` (salt, iterations) -> client derives -> `POST /api/backup/fetch` with auth key -> blob with iv + ciphertext. Wrong password = 401 `auth_invalid`; rate limit `BACKUP_RATE_LIMIT` per IP **and** per handle (default 10/min), uploads have their own window. Password at least `BACKUP_MIN_PASSWORD` (8) characters, checked client-side only; no reset possible (the directory does not know it).
- **Account page of the service (`../squorli-directory/apps/directory/web/`):** deliberately without a framework (one script file, tsup), same colors as the client, German texts with umlauts, no browser dialogs. "Konto anlegen" (create account) first registers the handle and then stores the backup; if only the backup fails, the key stays in page memory and the next click repeats only the backup step; afterwards you are directly in the account area. "Anmelden" (sign in; handle + password, code if needed) fetches the seed into page memory only (never localStorage) and signs the account actions with it; "Abmelden" (sign out) nulls it. The chat client links the page in the login ("Noch kein Konto?", "Konto verwalten" with `?handle=`) and in Profile > Konto and signs in with "Mit Konto anmelden": `api.directoryRestore()` fetches and decrypts, `store.loginWithHandle()` replaces the device key (with a confirmation via `askConfirm` if the previous one has a handle) and then logs in normally.
- **Second factor (M6c):** TOTP per RFC 6238 (own implementation `../squorli-directory/apps/directory/src/totp.ts`, no library) or recovery code; the service recognizes the form (6 digits = TOTP). Required, if `totp_enabled`, for `POST /api/backup/fetch`, `PUT /api/backup`, `totp-disable` and `recovery-regenerate`; **never at chat login by key** (the key is the factor). `totp_required` (401) comes only after a correct password or valid signature, so that nobody learns without the password whether an account has an authenticator; public responses (`/api/handles`, `/api/keys`) reveal nothing. Each TOTP step is valid once (`totp_last_step`, otherwise 401 `totp_reused`), window +-1 step; recovery codes are consumed atomically (`used_at`). Only failed attempts count against `BACKUP_RATE_LIMIT` per account (`RateLimiter.blocked()/hit()`), likewise only wrong passwords per IP/handle. The secret is stored AES-256-GCM-encrypted in the DB (`secrets.ts`, key `DIRECTORY_SECRET_KEY`, AAD = account ID); without the key `features.totp=false` and 503 `totp_unavailable`, recovery codes (SHA-256 only) keep working. Setup: `totp-setup` generates the secret (only with a backup, otherwise 409 `no_backup`), it becomes active only with `totp-enable` + code, which at the same time returns the 10 recovery codes (shown once). Signed account actions: `directoryActionMessage(host, action, nonce, code)`, body `SignedActionRequest`/`CodeActionRequest`; the code is part of the message so that it cannot be swapped.
- **Device management (M6c):** `sessions.id` is the public identifier (the token stays secret), `label` comes from the User-Agent at login (`labelFromUserAgent`, the client cannot set it), `last_used_at` is written in `resolveSession()` at most every 5 min. Remote logout deletes the row and closes exactly its WebSocket with **Close 4011 `session_revoked`** (`hub.disconnectSession`; kick remains 4010 + `removed`). The client reacts in `store.sessionLost()`: WS close 4011, WS error `unauthorized` and REST 401 with a token set (`api.onUnauthorized`) lead to the login with a message, without reconnect. `store.logout()` calls `DELETE /api/me/sessions/current` (best effort). No `PROTOCOL_VERSION` bump: close codes are not events. The directory knows no devices, only the list of key fetches (`key_fetches`, 90 days, display only): whoever has the key has it.
- **Account deletion through the directory (15 September 2026, user's wish):** a user deletes their account on one server from the directory's account page or via right-click on the server in the rail; both sign the action `server-leave` at the directory. The directory only relays: it pushes `{publicKey}` to `POST /api/directory/leave`, and the server confirms with its own token (`confirmLeave`) before deleting anything, so an unsigned push can at most trigger a check (same principle as `/api/directory/notify`). The first owner (`server_settings.owner_id`) is refused (`founder`), other owners and members are deleted completely (`users` row with cascade, attachment files, WS close 4012, no `removed` event and no `PROTOCOL_VERSION` bump: close codes are not events). Missed pushes are fetched via `pendingLeaves()` in the 5-minute sync. There is no local "delete my account" route on the chat server; the directory is the single entry point (the user's decision).
- **Security:** Do not weaken the auth path (single-use challenge, domain binding of the signature, session TTL). LiveKit secret at least 16 characters (schema), 32+ in production. `TRUSTED_PROXIES` only relevant in external mode.
- **Symbols only via `<Icon name="…"/>`** (Lucide web font, ISC license, self-hosted under `apps/web/src/icons/`), no emojis and no Unicode arrows in the UI (user requirement: uniform, white, license-free). Color = `currentColor`, size = `font-size`. Look up new names at https://lucide.dev/icons, then `pnpm icons`. Hang up = `phone` rotated by 135 degrees, white on red.
- **Categorized modals: categories always on the left** (user requirement 13 September 2026, applies without instruction to the contrary to all future modals with several sections). Building blocks: `.modal` > `.modal-head` (title, `.spacer`, close) + `.settings-layout` (`.settings-nav` on the left with `<Icon>` + label, `.settings-body` on the right). Examples: settings (`VoiceDock.tsx`) and admin panel (`AdminPanel.tsx`). No tab bar at the top.
- **No browser dialogs in the client:** `alert`, `confirm`, `prompt` are taboo (user requirement). Confirmations via `askConfirm()`, text inputs via `askInput()` from `apps/web/src/dialogs.tsx`; both return promises and render their own modal (z-index above admin panel/profile). Show errors inline as `.error` text, not as a popup.
- **Tests:** Vitest, files `*.test.ts` next to the code. Pure logic (stores, schemas) via unit test; flows via `scripts/smoke.mjs`.

## 6. Architecture in brief

- One process: Fastify serves the API, the WebSocket (`/api/ws`) and the static web client (SPA fallback to `index.html`, unknown `/api/*` -> 404 JSON).
- Identity = Ed25519 public key; the first login creates the user (`onConflictDoUpdate`). What is signed is `community-chat-login\n<domain>\n<nonce>`, so `PUBLIC_DOMAIN` must match the hostname the client sees (dev: `localhost`).
- Media never passes through the app server: the client fetches `/api/rtc-token` and connects directly to LiveKit (`wss://<PUBLIC_DOMAIN>/rtc`, the proxy forwards `/rtc*` to `livekit:7880`). UDP 7882 / TCP 7881 must be reachable directly.
- Operating modes: `PROXY_MODE=bundled` (bundled Caddy with Let's Encrypt on 443) or `external` (own proxy, see `deploy/proxies/README.md`, status untested).
- The challenge store is in-memory (single node). Multi-node later via Redis.

## 7. Known pitfalls

- **Smoke test without a running server** fails with `ECONNREFUSED`; run `pnpm dev` or `node dist/index.js` first.
- **`PUBLIC_DOMAIN` must match the hostname in the browser address bar exactly** (dev: `localhost`; behind the proxy: `chat.example.org`; access via LAN IP: the IP). Otherwise `POST /api/auth/verify -> 401 (signature_invalid)`. `/api/health` returns `domain`; since the fix, the client shows both values in the error message. The smoke test always signs with `localhost`.
- **Windows:** `process.exit()` while WebSockets are still closing triggers a libuv assertion; the smoke test therefore waits for `close`. Follow the same pattern in future scripts.
- **Docker build from Windows:** without `.dockerignore`, the host `node_modules` end up in the build context; do not delete the file. `tools/` is deliberately excluded: the Dockerfile must not call `tools/icons.mjs`; the generated icon files under `apps/web/src/icons/` are in the repo and are sufficient.
- **`pnpm deploy` under pnpm 10** aborts without `--legacy` with `ERR_PNPM_DEPLOY_NONINJECTED_WORKSPACE` (the flag is in the Dockerfile).
- **`@squorli/protocol` has no build:** its entry is `src/index.ts`. The server therefore bundles it into `dist/index.js` via `noExternal`. Anyone who introduces further workspace packages as runtime dependencies of the server must add them to `tsup.config.ts` as well.
- **Testing the image locally:** `docker run --rm -p 3000:3000 --network squorli-dev_default -e PUBLIC_DOMAIN=localhost -e DATABASE_URL=postgres://chat:chat@postgres:5432/chat -e LIVEKIT_URL=http://livekit:7880 -e LIVEKIT_API_KEY=devkey -e LIVEKIT_API_SECRET=<32 characters> squorli/app:local`, then run the smoke test.
- **Background processes on Windows:** `tsx watch` and Vite survive a hard kill of the parent shell. `pnpm dev` (wrapper) cleans up via `taskkill /T`; anyone using `pnpm dev:apps` directly checks `netstat -ano | grep ":3000 "` and `taskkill //F //T //PID <pid>` before restarting. **Beware German Windows:** `netstat` prints `ABHÖREN` instead of `LISTEN`; filter with `grep -E "ABH|LISTEN"`, otherwise the cleanup finds nothing and an old test server (with an old protocol) stays on the port while the new one cannot bind.
- **"Batchvorgang abbrechen (J/N)?" on Ctrl+C** ("Terminate batch job (Y/N)?") comes from the cmd.exe shells that pnpm opens for `tsx watch` and `vite`. Cosmetic; the wrapper terminates them immediately. Do not answer with J/N.
- **Wrapper test:** Ctrl+C cannot be triggered from scripts via `kill -INT` (MSYS does not reach native processes). Tested with `GenerateConsoleCtrlEvent` from PowerShell; alternatively terminate the apps via `taskkill`, the wrapper then stops the containers through the exit path.
- **Port 3000/5173/5432/7880-7882 in use:** dev compose and the Vite proxy are hard-wired to these ports.
- **Compose project is called `squorli-dev` since 14 September 2026 (previously `community-chat-dev`):** if old containers are still running, they occupy 5432/7880-7882 and the new stack does not start. Run `docker compose -p community-chat-dev down` (without `-v`) once, then `pnpm dev`. The data volume is pinned in `compose.dev.yml` to the old name `community-chat-dev_pgdata-dev` and declared as `external: true` (Compose requires this for volumes from another project); `tools/dev.mjs` creates it via `docker volume create` before `compose up`, so that a fresh machine starts as well. Anyone using `pnpm docker:dev` directly must create the volume once themselves. The dev DB is preserved this way (verified on 14 September 2026: users and handles present after the switch). Containers are now called `squorli-dev-postgres-1` / `squorli-dev-livekit-1` (in all `docker exec` commands). For an already running prod stack (`community-chat`), the same applies to `deploy/compose.yml` (network `squorli_internal`, volumes not pinned: back up data first).
- **LiveKit dev container** runs with `--dev` (keys `devkey`/`secret`); `.env.development` deliberately uses a longer secret only for token signing; a real media connection is not yet part of the client in M0.
- **Directory service in dev:** `pnpm dev` in `../squorli-directory` (own Postgres on :5433, service on :3100); the chat server needs `DIRECTORY_URL=http://localhost:3100` in `apps/server/.env`. Chat smoke test with directory: start the chat server with `DIRECTORY_URL=http://localhost:3101` against a smoke instance there (see its AGENTS.md). Until 14 September 2026 the dev database `directory` lived in `squorli-dev-postgres-1`; the README there has the `pg_dump | psql` line for taking the data over.
- **`EADDRINUSE :3000` right after `pnpm dev` (fixed 14 September 2026):** `tools/dev.mjs` used to load the entire `apps/server/.env` via `loadEnvFile` into its environment, which all apps inherit. The directory service thereby got `PORT=3000` and the chat `DATABASE_URL`. Now the wrapper reads only `LIVEKIT_DEV_NODE_IP` from the file and passes it exclusively to Compose. Rule: the wrapper never sets app variables; each app loads its own `.env`.
- **`DIRECTORY_URL` missing in `apps/server/.env` after the update:** `.env.development` has it, an existing `.env` gets it by hand (`DIRECTORY_URL=http://localhost:3100`); without it the login shows "Dieser Server nutzt kein Verzeichnis" (this server does not use a directory).
- **Session "logged out from another device" in your own browser:** after "Alle anderen Geraete abmelden" (log out all other devices) or a `DELETE /api/me/sessions/:id`, the session currently in use is kept (`current`); anyone who gets thrown out anyway has two tabs with two sessions of the same key (every login creates a new session; a second tab only shares it via `localStorage`).
- **Smoke test against a test DB:** `docker exec squorli-dev-postgres-1 psql -U chat -d chat -c "CREATE DATABASE chat_smoke"`, then `PORT=3001 PUBLIC_DOMAIN=localhost DATABASE_URL=postgres://chat:chat@localhost:5432/chat_smoke npx tsx src/index.ts` in `apps/server` and `SMOKE_URL=http://localhost:3001 pnpm smoke`. This way the owner of the dev DB remains your own browser key.
- **Schema change while `tsx watch` is running:** the dev server restarts immediately after `schema.ts` is saved, i.e. before `pnpm db:generate` has generated the migration; it then runs against the old schema and queries on new columns fail (server stops responding). After `db:generate`, trigger a second restart (`touch apps/server/src/index.ts`), then the migrations are applied. Check: `SELECT count(*) FROM drizzle.__drizzle_migrations`.
- **Raw SQL with Date parameters** (`sql` + `${new Date()}`) fails in postgres-js; use `now()` in SQL.
- **Attachments are publicly retrievable by ID** (`/api/attachments/<uuid>/<name>`, no token), so that `<img src>` works. Like CDN links on Discord; the UUID is the secret.
- **White screen after deploy, "Expected a JavaScript module ... MIME type text/html":** the browser had the old `index.html` with the old asset hash in its cache. Since the fix: missing files with an extension get a 404 instead of the app shell, `index.html` is served with `cache-control: no-cache`, hashed assets with `immutable`. The user must hard-reload once after the fix. Run `pnpm build` (root) after every client change, otherwise an old client sits in `apps/server/public`. Second cause (fixed): `@fastify/static` ran with `wildcard: false` and registered one route per file at startup; new assets after a build without a restart got a 404. Now `wildcard: true`, files are resolved per request.
- **`Route GET:/ not found` (Fastify 404 on `/`):** the server is running without a built web client. Since the fix, `/` answers with 503 and an explanation; the cause is a start without `pnpm build` (missing `apps/server/public`) or an old Docker image. `/api/health` works regardless.
- **Server icon gone after emptying `apps/server/data`:** the DB still had `icon_mime`, so favicon, sidebar, login and server rail showed a broken image (happened 14 September 2026). Since the fix the settings routes check at startup whether `DATA_DIR/server-icon` exists and otherwise clear the entry with a warning; upload the icon again in Verwaltung > Server. When emptying the data folder, keep `server-icon` or expect this.
- **`apps/server/public/` and `apps/server/.env` are gitignored**; never commit them. New variables in `.env.development` must be copied by hand into the existing `apps/server/.env` (e.g. `LIVEKIT_PUBLIC_URL`).
- **"could not establish signal connection" / Safari "Load failed":** the client cannot reach the LiveKit URL issued by the server. Usually `apps/server/.env` still contains `LIVEKIT_PUBLIC_URL=ws://localhost:7880` from `.env.development` while the server runs publicly. Remove the variable (default `wss://PUBLIC_DOMAIN`, the proxy forwards `/rtc`). The server warns about this combination at startup; the client names the URL in the error message and in the debug view. Second cause: `LIVEKIT_PUBLIC_URL=wss://domain:7880` (port 7880 does not speak TLS and is not exposed; correct is without a port via the proxy). Third cause: the proxy does not forward `/rtc` (`/rtc/validate` must return 401).
- **Participant drops out of the channel after ~15 s:** the signal connection is up, media (ICE) never gets established, LiveKit disconnects with CONNECTION_TIMEOUT/UNKNOWN. Causes: 7882/udp + 7881/tcp not forwarded to the chat host, LiveKit does not know its public IP (`LIVEKIT_NODE_IP`), or the dev stack is running with `--node-ip 127.0.0.1`. The client shows the disconnect reason as an error and logs room events in the debug view; on the server, search `docker logs <livekit>` for "ice" / "connection timeout". SIGNAL_CLOSE, by contrast, = WebSocket closed (proxy timeout, network switch, phone in the background).
- **LiveKit URL for clients without `/rtc`:** livekit-client appends `/rtc` itself. `wss://domain/rtc` would result in `/rtc/rtc` and fails. The server delivers `LIVEKIT_PUBLIC_URL` or `wss://PUBLIC_DOMAIN`.
- **LiveKit in Docker on Windows/macOS:** without `--node-ip`, LiveKit offers the internal container IP as ICE candidate, and browsers on the host then get no media. `compose.dev.yml` sets `--node-ip ${LIVEKIT_DEV_NODE_IP:-127.0.0.1}`; `tools/dev.mjs` loads `apps/server/.env` for this. For a second device in the LAN set `LIVEKIT_DEV_NODE_IP=<host LAN IP>`, for tests from outside the public IP, and open the client from that device via the LAN IP (then `localhost` is no longer a secure context: microphone only with HTTPS, see PLAN 5 mkcert).
- **LiveKit dev secret:** `--dev` sets `devkey`/`secret`; the container receives the longer secret from `.env.development` via `LIVEKIT_KEYS`, because `config.ts` requires at least 16 characters. Token check without a browser: `GET http://localhost:7880/rtc/validate?access_token=<jwt>` must return 200.
- **Browser autoplay:** audio from other participants may be blocked until the user clicks once; the client then shows "Ton freigeben" (unblock audio) (`room.startAudio()`).
- **Choosing an output device** (setSinkId) exists only in Chromium; Firefox/Safari show an empty list.
- **Screen share without audio:** only Chromium delivers audio, and there only with "Tab" (tab audio) or on Windows with "entire screen" with system audio enabled; individual windows never. Firefox/Safari never. The stage shows a yellow notice in both cases. The matrix in PLAN 3.6 is checked with `/test/screenshare.html` per browser/operating system and recorded there.
- **`docker stats` does not measure the load test:** `pnpm bots` attaches itself to the network namespace of the LiveKit container; the media traffic runs over loopback and does not show up in NET I/O. Read the bandwidth from the `lk` table (subscriber) or from the debug view in the client.
- **`@types/dom-mediacapture-transform`** is a peer dependency of `@livekit/track-processors` (types for MediaStreamTrackProcessor); as a devDependency in the web package, otherwise `tsc` breaks.
- **Fresh database had only the role "Mitglied" (fixed 14 September 2026):** migration 0004 creates "Mitglied" in empty databases as well; since then the bootstrap no longer checks for "no roles" but for "no default role" and creates Gast/Admin/Mitglied individually as needed. Check the fresh-install path: recreate `chat_smoke` from scratch via `DROP DATABASE ... WITH (FORCE)` + `CREATE DATABASE` and run `pnpm smoke` (not only against an incrementally migrated DB).
- **Resetting the dev database** (new owner at the next login): `docker exec squorli-dev-postgres-1 psql -U chat -d postgres -c "DROP DATABASE chat WITH (FORCE)" -c "CREATE DATABASE chat OWNER chat"`, empty `apps/server/data/attachments`, then `touch apps/server/src/index.ts` (migrations + bootstrap run only at startup). The database `directory` in the same container is the old dev database of the directory service (before the move); leave it until the data is taken over into `../squorli-directory`.
- **Only guest after joining:** anyone who cannot write does not yet have the "Mitglied" (member) role. An admin assigns it in the member list (click on the name). This is intended (decision of 13 September 2026), not a bug.
- **Production compose always with `--env-file ../.env`:** `env_file:` in the service only covers the container environment; the `${POSTGRES_PASSWORD}`/`${LIVEKIT_API_KEY}` placeholders in `compose.yml` are filled by Compose only from `deploy/.env` or the `--env-file`. Without the flag: empty DB password, `LIVEKIT_KEYS: ": "`. Check with `docker compose --env-file ../.env ... config`.
- **external mode publishes no HTTP ports.** A proxy on the host needs the overlay `proxies/nginx.ports.yml`; a proxy in a container attaches to the network `squorli_internal`.

## Standard container installation

The default user installation requires no Git clone, Node.js or application build. Download only .env.example, deploy/compose.yml, Caddyfile, livekit.yaml and the optional nginx port overlay into a fresh squorli directory. Configure .env with APP_IMAGE and the matching proxy mode, then run Compose pull and up --no-build from squorli/deploy. Updates pull the image without git pull; never overwrite existing secrets by repeating the initial download. Source cloning and --build belong only to a separate optional developer workflow at the end of both public guides. Both languages must stay equivalent.
