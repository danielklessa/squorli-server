This file is the central project description for all coding agents (Claude Code, Codex, Cursor, etc.).
`CLAUDE.md` includes it and only adds Claude-specific rules.
**Mandatory:** Whoever changes the structure, commands, configuration, protocol or milestone state updates this file in the same step.

## 1. What the project is

**Rail marks for every server, muting a server or a channel (17 September 2026, user's wish):**
- **All servers of the rail are connected in the background.** Until now a foreign server was only connected when it was opened, so the rail could mark nothing else. `store.connectAccountServers()` (called whenever the account's server list arrives, only while signed in on the own server, not for a server with a pending account deletion) creates a `ServerConnection` per server and signs in exactly like `openServer()` (stored session, otherwise the browser key), without switching the view. Each connection syncs its read state, so the rail shows the unread bar and the mention badge for every server, live. **Consequences:** the user is online on all their servers while the client is open, one WebSocket per server, and a new device creates a session on every server of the account. A connected foreign welcome no longer refetches the directory's server list unless that server is not on the list yet.
- **Mutes are kept by the chat server per member** (every device shows the same): `members.muted` = the whole server, table `channel_mutes (user_id, channel_id)` = text channels (migration 0016, generated). `PUT /api/channels/:id/mute` and `PUT /api/me/mute` take `MuteRequest { muted }`, answer the member's complete `MuteState { serverMuted, channelIds }` and send it as the **server event `mute.update`** to the member's own connections only; `GET /api/read-state` carries `muted` per channel and `serverMuted` (both `.default(false)` in the protocol, so a server from before mutes parses as "not muted"). Muting needs no permission beyond `VIEW_CHANNELS`: it changes only the own view. **No `PROTOCOL_VERSION` bump** although the user allowed one: nothing requires it (additive fields with defaults, an event older clients drop), and a bump would only cut clients off from servers of the other version.
- **What muting means (Claude's decision, as in Discord, not confirmed by the user):** a muted channel gets no unread mark and does not count for the server's mark on the rail; a muted server gets no unread bar. **Mentions always show** (amber channel, badges), because a mention addresses the person. Unread and mention counting itself is unchanged, so unmuting shows the true state at once.
- **UI:** right-click on a text channel in the sidebar opens a `ContextMenu` with "Kanal stumm schalten" / "Stummschaltung aufheben" (`Sidebar.tsx`, props `muted`, `canMute`, `onMuteChannel`); a muted channel is dimmed and carries a `bell-off` icon. The rail's existing right-click menu gains "Server stumm schalten" / "Stummschaltung aufheben" (`ServerRail.tsx`, `onMute`, `RailState.muted`/`canMute`), also for the own server; a muted server's icon is dimmed and its tooltip says so. Both entries are only offered when the server keeps read states and mutes (`ServerConnState.readSync`). `App.tsx` computes the rail mark as "not server-muted and some unread channel that is not muted". Smoke test: 4 new checks (89 in total). Checked with a headless Chrome screenshot (rail and channel states, both menus); the interaction in the running app and with two real servers was not checked.

**Read states on the server, the same on every device (17 September 2026, user's wish):** the server now remembers how far each member has read each text channel, so unread marks and mention counters follow the person and not the browser. **Database:** table `read_states` (`user_id`, `channel_id`, `last_read_seq`, `updated_at`; primary key user + channel, both cascade; migration 0014 generated). No row = never opened: then the messages since `members.joined_at` count, so a new member sees what happened since joining and a new channel is unread for everyone. Migration 0015 (custom) gives every existing member a row per text channel at its newest message, otherwise an update would mark every channel for everyone. **API (`apps/server/src/routes/readState.ts`, `VIEW_CHANNELS`):** `GET /api/read-state` answers for all text channels in one query `{ channelId, lastReadSeq, latestSeq, unread, mentions }` (`ReadStateResponse`; only messages of other people newer than the read state count; `mentions` = those whose text contains `<@myUserId>`, a plain substring test, so a token quoted inside a code block counts here although the client does not render it as a mention). `POST /api/channels/:id/read { seq }` (`MarkReadRequest`) upserts with `greatest()` (never backwards) and caps `seq` at the newest message of the server (a number from the future would hide messages that do not exist yet); 404 for voice channels. It then sends the **new server event `read.update { channelId, lastReadSeq }` to the member's own connections only** (`hub.sendToUser`), so their other devices drop the mark at once. **No `PROTOCOL_VERSION` bump (stays 4):** the client drops events it cannot parse (`serverConnection.ts` `onmessage`: `if (parsed.success)`), so an older client simply ignores `read.update`, and nothing depends on receiving it; a bump would cut the multi-server client off from every server that is not updated yet (WS close 4002). **Client (`serverConnection.ts`):** after every welcome `syncReadState()` asks the server and takes its marks and counters (a live message newer than the answer keeps its mark); whenever a channel is on screen `rememberRead()` acknowledges the newest message, coalesced to one request per 800 ms and channel; `read.update` clears a channel that was read elsewhere (or re-syncs when it was read only in part); coming back to the tab re-syncs at most every 15 s as a safety net. **Older servers** answer `GET /api/read-state` with 404: then the per-device state below (`readState.ts`, `catchUpChannels`) decides as before, per server. The per-device state is still written in both cases. The limit of 50 messages per channel no longer applies with a current server. Smoke test: 6 new checks (unread since joining, own messages ignored, mention counted, mark read + event only to my connections, never backwards or into the future, text channels / input / sign-in, a newer message marks again).

**Unread marks and mention highlight, also across sessions (17 September 2026, user's wish: "mark a channel in general when it has unread messages, highlight it when I was mentioned"):** in the sidebar a read channel is muted, an **unread** one is marked (bright bold name plus a small bar at the left edge, the same sign as on the rail), a channel that **mentions me** is highlighted (amber name, amber bar and ground, counter `.mention-badge`); the open channel shows neither (`.channel.unread`, `.channel.mentioned` in `styles.css`). Until now both only counted messages that arrived over the WebSocket while connected, so a reload or an absence lost them. Now the client keeps a **read state per device** (`apps/web/src/readState.ts`, localStorage `chat.read.v1:<host>:<userId>` = channel -> `seq` of the newest message shown; pure functions `catchUp`, `markRead`, `pruneReadState`, tested): `ServerConnection` remembers the newest message whenever a channel is on screen (select, history loaded, live message in the open channel) and after **every welcome** (`catchUpChannels`) fetches the newest page (50) of each text channel that is not on screen, one after the other, at most 50 channels, and marks unread / counts mentions among the messages newer than the read state (own messages never count; mentions via the Markdown parser). A channel this device has never seen starts as read (a new member or browser must not find everything marked). The fetched pages also fill the message cache, so opening such a channel needs no request, and after a reconnect the other channels' caches get their missed messages. **Limits (deliberate, no server change):** the read state is per device, not per account (another browser has its own); only the newest 50 messages per channel are looked at, so more than 50 missed messages still mark the channel but mentions further back are not counted; since the same day the server keeps read states (entry above) and this per-device state is only the fallback against older servers. Checked with a headless Chrome screenshot (all four channel states); the catch-up against a running server was not exercised.

**Mentions in the channel chat (17 September 2026, user's wish):** typing `@` in the composer opens a list of members (`MentionSuggest.tsx`, hook `useMentionSuggest`: names or handles starting with the query first, then word starts, then containing it; arrows choose, Enter or Tab accept, Escape dismisses, a click works too; while the list is open Enter does not send). **Stored as `<@userId>`** in the message content (ids never change, names do); the server treats it as plain text, so there is no server, schema or `PROTOCOL_VERSION` change. `apps/web/src/mentions.ts` (pure, tested): `encodeMentions` turns `@Name` and `@handle` into tokens when sending and when saving an edit (longest name first, not inside code, not in `mail@host`; the member chosen in the list decides between equal names), `decodeMentions` shows names again in the edit field and in the delete confirmation, `mentionedIds`/`mentionsUser` ask the Markdown parser, so a token inside code is no mention. `markdown.ts` has the inline node `mention`; `MessageText.tsx` renders it through `MentionContext` (provided by `ChatView` with the member names and the own id) as a chip with the **current** name, "ehemaliges Mitglied" for people who left, amber for yourself; without the context (direct messages) a token stays text. A message that mentions you gets an amber edge (`.msg.mentions-me`). **Counters:** `ServerConnState.mentions` counts per channel (like `unread`, cleared when the channel is opened; since the read state above also for messages from before the session); the sidebar shows the number on the channel (`.mention-badge`), the rail the sum per server at the top right of its entry (`RailState.mentions`). **Deliberately not included** (Claude's decisions, not confirmed by the user): `@everyone`/`@here` and role mentions (would need a permission against abuse, i.e. protocol, migration and role editor), sounds or desktop notifications, mentions in 1:1 direct messages, a suggestion list in the edit field (a typed unique name still becomes a mention). Checked with a headless Chrome screenshot of the built CSS (chips, highlighted message, suggestion list, badges); the interaction in the running app was not checked.

**Third-party licenses (17 September 2026, user's wish: meet the obligations around Apache 2.0):** Einstellungen > "Lizenzen" (`apps/web/src/LicensesTab.tsx`, tab `licenses` in `SettingsDialog.tsx`, icon `scale`) shows Squorli's own license (Apache 2.0, copyright, link to the source, version of the server that serves the client via the new prop `clientVersion` = `home.serverVersion`) and every third-party package, font and data set inside the client with version, SPDX license, source and the full license text (`<details>` per package). The list is **generated** by `tools/licenses.mjs` (`pnpm licenses`, also part of `pnpm build`): it walks the production dependencies of `@squorli/web` including those of `@squorli/protocol` through `node_modules` (pnpm layout), adds the packages whose assets are shipped although they are dev dependencies (`ASSETS`: `emojibase-data`) and the emoji font, which is no package (`FONT_DIR`: `font.json` + `OFL.txt` written by `tools/emoji.mjs`), and writes `apps/web/src/licenses/thirdParty.ts` (lazy chunk, identical texts stored once; a package without a license file gets the standard Apache text when it is Apache-2.0, otherwise only its SPDX statement) and `THIRD-PARTY-NOTICES.md` in the repo root. It fails when a package states no license. The walk is a superset of what the bundler keeps. Both outputs are **committed**: the Docker build runs only `pnpm --filter @squorli/web build` and has no `tools/` in its context. `NOTICE` names the bundled fonts/data and points to the generated file; the image now carries `LICENSE`, `NOTICE` and `THIRD-PARTY-NOTICES.md` in `/app` (Dockerfile). The server's packages keep their own license files in the image's `node_modules`. **Whoever adds or updates a client dependency, or ships an asset of a dev dependency (then add it to `ASSETS`), runs `pnpm licenses` and commits the result.** Not legal advice; the texts are collected mechanically.

**Emoji in the chat (17 September 2026, user's wish):** font, automatic conversion and a picker, for channels and direct messages alike.
- **Font: Noto Color Emoji** (SIL OFL 1.1, Google; free to redistribute, complete, kept current). **Self-hosted files in the repo:** `tools/emoji.mjs` downloads the `unicode-range` slices that Google Fonts serves to Chromium (COLRv1, v47: 11 files, 10 kB to 709 kB, about 2 MB in total) once into `apps/web/src/emoji/font/` together with `OFL.txt` and `font.json`, and writes `apps/web/src/emoji/font.css`; after that only our own server delivers them (no CDN, no font service at runtime), and a browser fetches only the slices whose emoji occur. The files are committed (about 2 MB of binaries) because the Docker build has neither `tools/` nor should it depend on Google. **Do not use `@fontsource/noto-color-emoji` (5.3.1):** its slices carry COLRv1 and SVG tables but render as blank boxes in Chromium; that was the first attempt and the user saw no emoji at all (found and fixed on 17 September 2026 with headless Chrome screenshots; the package's unsliced file renders but weighs 5.7 MB). **Safari has no COLRv1:** `styles.css` names the font only inside `@supports (font-tech(color-COLRv1))` (root stack and `.emoji`), so Safari keeps Apple Color Emoji instead of blank glyphs; Chromium 108+ and Firefox 107+ get Noto. Windows shows no flag emoji by itself, which the font also fixes. `main.tsx` imports `font.css`. The font is the **last** entry of the root `font-family` (it also covers digits, `#` and `*` for keycaps, which the text font must win); in messages every emoji is a `<span class="emoji">` with the font first, 1.3 em, and a message of nothing but up to 12 emoji is shown large (`.md-jumbo`). Verified with headless Chrome against the built CSS: emoji in text, large emoji, root stack, the message input, the picker grid, flags, skin tones, ZWJ families and keycaps render; digits stay in the text font. Not checked: Firefox, Safari.
- **Automatic conversion at display time** (`emoji/convert.ts`, called from `markdown.ts`; messages stay stored as typed, so nothing is lost and older messages convert too): shortcodes `:smile:` (the Markdown habit; union of the GitHub, iamcal = Slack/Discord style and emojibase sets, 3370 names, `emoji/shortcodes.ts` is part of the main bundle, lookup with `Object.hasOwn` so `:constructor:` finds nothing; not directly after a letter or digit, so `12:30:45` stays) and classic emoticons (`:)`, `;-)`, `:D`, `:P`, `<3`, `xD`, `^^` ... in `EMOTICONS`, deliberately few: only as a word of their own, so `http://`, `C:/` and `xDrive` stay; `8)`, `:3`, `D:` are left out on purpose). Real emoji are found by a Unicode-property regular expression (flags, keycaps, tag sequences, ZWJ sequences, skin tones; characters with text presentation such as ©, ™, ↔ only count with U+FE0F). Never inside code spans, code blocks or addresses; a backslash keeps a form literal (`\:)`). The `title` of a converted emoji shows what was typed. A test checks that every emoji of the picker is recognized as exactly one emoji.
- **Picker** (`EmojiPicker.tsx`: `EmojiButton` in the composer of `ChatView` and `DmView`, smiley icon next to "Senden", as high as that button and without a background, also on hover: user's wish): own component (no picker library), a body portal opening upwards from the button (`menuPosition`), search field with focus, nine categories plus "Zuletzt verwendet", skin tone choice, preview line with name and shortcode. Names and keywords come in the client's language (`emoji/data.de.ts`, `data.en.ts`, generated from `emojibase-data` 17.0.0, MIT, dev dependency; about 1900 emoji each, lazy chunks of 55-67 kB gzip fetched when the picker opens); search covers name, keywords and the English shortcodes (`:thu` finds 👍). Inserts at the caret of the input (replacing a selection) and returns the focus there; Shift+click or Shift+Enter keeps the picker open; arrow keys move through the grid (8 columns, `COLUMNS` = the CSS grid), ArrowDown from the search enters it, Enter in the search takes the first hit, Escape closes. Hover/focus preview uses event delegation and memoized grids so the 1900 buttons do not re-render. Pure logic in `emoji/picker.ts` (tested). **Recently used and the skin tone are stored per device** (`chat.emoji.recent.v1`, `chat.emoji.tone.v1`) and deliberately not in the directory account (usage history; would need a protocol and directory change) - Claude's decision, not confirmed by the user. The edit field has no picker. `pnpm emoji` regenerates font CSS and data after updating one of the two packages; the output is committed and not part of `pnpm build`.

**More Markdown (17 September 2026, user's wish):** task lists (`- [ ]`, `- [x]`, also numbered and nested; rendered as a disabled checkbox that shows the written state, `ListItem.checked`), highlight `==text==` (`<mark>`, quiet amber), subscript `H~2~O` and superscript `x^2^` (single `~`/`^` on both sides and no white space inside, so `~5 min, ~10 min` and `2^10` stay text; `~~` stays strikethrough). `=` follows the intraword rule of `_` (`a==b` and `x == y` stay text); content consisting only of the delimiter (`=====`) is no markup.

**Focus stays in the message input (17 September 2026, user's wish):** after sending (Enter or the button) the composer of `ChatView` and `DmView` keeps/gets the focus, so the next message can be typed right away. Cause was `disabled` while sending, which drops the focus; the input is now `readOnly` during the request (still `disabled` without `SEND_MESSAGES`) and `submit()` focuses it in `finally`. `AutoGrowTextarea` takes `inputRef` for this and for the emoji picker.

**Growing message input (17 September 2026, user's wish):** the composer of the channel chat and of the direct messages, and the field for editing a message, grow with their content up to **one third of the chat area's height** (`.chat`) and only then scroll. `apps/web/src/AutoGrowTextarea.tsx` measures `scrollHeight` in a layout effect on every value change and follows size changes of the area with a `ResizeObserver` (script instead of CSS `field-sizing`, which Firefox lacks); the rule itself is the pure `grownHeight()` in `autoGrow.ts` (`INPUT_MAX_SHARE` = 1/3, never below `INPUT_MIN_LIMIT` = 64 px so a phone with the keyboard open keeps about two lines; tested). The fixed `max-height: 10rem` of `.composer-row textarea` is gone. `ChatView.tsx` and `DmView.tsx` observe the message list and keep the newest message in view while the input grows or shrinks (only if the user has not scrolled up). Typecheck, all tests and build green; not checked in a browser.

**Markdown in the text chat (17 September 2026, user's wish):** channel messages and direct messages are rendered as Markdown by the shared `apps/web/src/MessageText.tsx`; it replaces the two copies of `renderText` (links only) in `ChatView.tsx` and `DmView.tsx`. `apps/web/src/markdown.ts` is an own, pure parser (text -> tree; no library, following "no new dependencies": Claude's decision, not confirmed by the user); the component turns the tree into React elements, message text never becomes HTML (`dangerouslySetInnerHTML` stays taboo). Deliberately a chat subset, not full CommonMark: paragraphs where a single line break stays a line break, headings `#` to `###` (rendered as h3-h5, the page owns h1/h2), fenced code (also ```` ```one line``` ````; an unclosed fence stays text; no syntax highlighting, the language is only `data-lang`), quotes `> ` (space required, nesting capped at 6), bullet and numbered lists nested by indentation (start number kept; a number other than 1 does not interrupt a paragraph), rule, `code`, `**strong**`/`__strong__`, `*em*`/`_em_` (no `_` emphasis inside words), `~~del~~`, `[text](url)`, `<url>`, bare URLs (trailing sentence punctuation excluded), backslash escapes. **Link safety:** only `http`, `https` and `mailto` become links; a masked link whose label itself looks like a web address is refused and stays literal (phishing); every link shows its target as `title` and opens with `noreferrer noopener`. **Images are never embedded** (`![alt](url)` becomes a link): a remote image would reveal the reader's IP address to a foreign host; uploaded attachments are unchanged. **Tables (GFM, user's wish):** a header row followed by a delimiter row (`---`, `:--`, `:-:`, `--:` = alignment) with the same number of cells; the delimiter row is what tells a table from a sentence containing `|`. Outer pipes are optional, `\|` is a pipe inside a cell, body rows run until a blank line or a line without `|` and are cut or filled to the header's width, at most 32 columns, cells take inline formatting; a table may interrupt a paragraph; rendered inside `.md-table`, which scrolls sideways instead of widening the chat. **Copy button on code blocks (user's wish):** every fenced block carries a button (top right, on hover or keyboard focus, always visible on touch) that copies exactly the block's content; Clipboard API with a fallback to the selection command for plain http, a check mark and a `role="status"` text confirm for two seconds (`chat.copyCode`, `chat.codeCopied`, `chat.codeCopyFailed`; icons `copy`, `check`). Inline code has no button. Not supported on purpose: raw HTML, indented code, setext headings, underline/spoilers. Storage, protocol and server are untouched: messages stay plain text, editing shows the raw Markdown, `PROTOCOL_VERSION` stays 4. The component is memoized because the chat views re-render on every composer keystroke. The "(bearbeitet)" mark sits in the last paragraph/heading, or in its own line after a code block/list/quote. Tests: `markdown.test.ts` (25, including tables and hostile input within a time bound) and `MessageText.test.tsx` (5, `renderToStaticMarkup`: no markup injection, link attributes, edited mark). Typecheck, all tests and build green; the look in a browser was not checked.

**Playback volume per person, 0-200 % (17 September 2026, user's wish):** right-click on a member in a voice channel (sidebar), on their tile in the stage or the member list's menu shows "Lautstärke für mich" with a slider, the percentage and a reset to 100 % (`UserVolumeControl.tsx`); not for yourself. Local playback only, nothing is sent. Stored per device in `chat.userVolumes.v1`, keyed by the person's **public key** so it holds on every server (`voice/userVolumes.ts`, tested; only real adjustments are stored); deliberately not in the directory account, because it depends on the headset in front of this browser and is a map without bound. `VoiceClient.getUserVolume/setUserVolume(publicKey)` also work without a connection; `setPeerKeys` / `JoinOptions.peerKeys` map LiveKit identities to keys (`App.tsx`), bots fall back to `id:<identity>`. Up to 100 % the `<audio>` element's volume does it; above, a `GainNode` on the speaker meter's `MediaStreamAudioSourceNode` plays into the shared `AudioContext` while the element stays attached at volume 0 (Chromium feeds a remote stream into Web Audio only while an element plays it). Consequences: deafening sets that gain to 0 (`setDeafened` -> `applyUserVolumes`), a context that is not running falls back to 100 % instead of silence (re-applied on `statechange`), and the boosted voice follows the voice output device only where `AudioContext.setSinkId` exists (Chromium; elsewhere the system default). The volume control of a camera pop-out is the same per-person value (slider to 200 % there, screen audio stays 0-100 %). `ContextMenu` arrow navigation includes `[data-menu-item]` (the slider). Typecheck, all tests and build green; not checked in a browser with real audio.

**Join and leave cues (16 September 2026):** Four different short sounds mark voice-room changes: you joining, you leaving, someone else joining your room, someone else leaving it. `apps/web/src/voice/sounds.ts` synthesizes them with Web Audio (no audio assets): your own pair is a sine C5/G5, the pair for other people a shorter, quieter triangle E5/A5; rising means arriving, falling means leaving. `voiceClient.ts` triggers them on a completed join, on leaving, and on LiveKit's participant events; switching between rooms plays only the join cue, a failed connection attempt plays nothing, participants already present within 1.5 s of connecting are not announced, and deafening silences all cues. ## 5. Conventions

- **Language:** Documentation, READMEs and AI instructions (AGENTS.md, CLAUDE.md, docs/, deploy READMEs, comments in env templates and deploy configs) are always in English (decision of the user, 14 September 2026). Code comments are English. **UI texts are bilingual German/English (user decision, 15 September 2026):** every text a user sees in the web client comes from the catalogs `apps/web/src/i18n/de.ts` (reference, all keys) and `en.ts` (same keys, enforced by the `Messages` type and the test) via `t("key", { params })`; never write a literal German or English sentence in a component, an error mapping or the voice core. The locale is fixed at page load: an explicit choice in `localStorage` (`chat.locale`, select in the login footer and in Einstellungen > Ansicht; with a directory account it follows the account, see section 1) wins, otherwise the first entry of `navigator.languages` we support, otherwise English. Dates use `fmtDateTime`/`fmtTime`/`fmtDay` from the i18n module (`localeTag`). The 503 page of the server picks German or English from `Accept-Language` (`preferredLanguage()` in `src/index.ts`). **Everything a user sees carries real umlauts** (ä/ö/ü/ß) in the German catalog (user requirement 13 September 2026); the ae/oe/ue transliteration is used only in comments, identifiers and developer log lines. `PERMISSION_LABELS` in the protocol package stays German and is no longer used by the client (labels come from the `perm.*` keys).
- **Formatting:** `.editorconfig` (2 spaces, LF, UTF-8, newline at end of file). No linter/formatter configured; keep the existing style (compact one-liners are common).
- **TypeScript:** `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`. ESM everywhere (`"type": "module"`). Imports without file extension.
- **Validation:** All inputs (HTTP bodies, WS messages, env) go through zod schemas. Define new REST/WS types first in `packages/protocol/src/index.ts`, derive the types from there, never declare them twice.
- **Protocol version:** Bump `PROTOCOL_VERSION` in `@squorli/protocol` on incompatible changes (currently 4; new permission bits are not an incompatible change; a new server event is one when clients must understand it, because the client parses events strictly with zod and drops what it cannot parse. An event that older clients may safely miss, such as `read.update`, needs no bump, and a bump is costly: the multi-server client cannot connect to servers of another version); the server rejects other versions with WS code 4002. The constant is also in `apps/server/scripts/smoke.mjs`, update it there too.
- **Voice channel presence vs. media:** `voice.join`/`voice.leave` over the WebSocket are the intent ("I am in the channel", for everyone's sidebar). Whether someone actually sends, hears or speaks is known only to LiveKit; the client shows both together. Participants known only to LiveKit (bots) appear as "(extern)" (external).
- **Mute and deafen (Discord logic, user requirement 13 September 2026):** `setMuted()` = microphone muted by hand; `setDeafened()` = incoming audio muted (`<audio>.muted`) **and** microphone force-muted. Undeafening restores the microphone only if it was not muted by hand (`micMutedByUser` in the voice core). Clicking the microphone while deafened ("Ton aus") lifts both. Deafen ("Ton aus") is set as the LiveKit attribute `deafened` (token grant `canUpdateOwnMetadata`) so others see it in the sidebar and tiles.
- **Voice codec:** always Opus in the browser (mandatory WebRTC codec, nothing better available). **The bitrate goes to LiveKit as `audioPreset: { maxBitrate }`** (`micPublishOptions()` in `voiceClient.ts`, typed as `TrackPublishOptions` and pinned by `micOptions.test.ts`); until 17 September 2026 it was passed as `audioBitrate`, which the SDK ignores silently, so every channel ran at the SDK default of 48 kbit/s whatever the admin chose. Check the real rate in the debug view ("audio send" kbit/s; with DTX it drops to almost nothing in silence, so measure while speaking). Quality per voice channel in the admin panel: `audioBitrate` (kbit/s, choice from `AUDIO_BITRATES`, default 64) and `audioStereo`. Mono = DTX + RED (silence costs nothing, redundancy against packet loss) with the browser's echo/noise suppression; stereo = `forceStereo`, capture with `channelCount: 2` and **without** audio processing (which would mix down to mono), for music. Changing the channel switches connected clients live (`setAudioProfile()`: republish the microphone).
- **Unlock audio inside the user gesture:** `client.prepareAudio()` sits in `App.joinVoice()` before the first `await`. It creates the single shared `AudioContext` (microphone gate and level meter hang off it), calls `resume()` and plays 0.1 s of silence once (`SILENT_WAV`) so that Safari/Firefox unlock `<audio>` playback for the document. Without this the context was only created after the token and `room.connect()`: level 0 (nobody heard the user) and silent playback on the first join (reported by two users on 14 September 2026). In addition, every gesture in the document (pointerdown/keydown, capture) releases blocked audio; the dock shows "Ton freigeben" (release audio, playback) or "Mikrofon freigeben" (release microphone, context not `running`), the debug view shows the "Audio" line. `MicPipeline.start()` waits for `resume()` at most 300 ms.
- **Speaker outline:** own participant = `gateOpen && !micMuted` (immediate). Others = local RMS measurement per subscribed microphone track (AnalyserNode, 50 ms, `VoiceGate` with threshold 0.015 and 250 ms hold, `addMeter()`); LiveKit's `isSpeaking` (server notification, ~0.5-1 s later) only as a fallback when the audio context is not running. `deploy/livekit/livekit.yaml` sets `audio.update_interval: 150` for this.
- **Speech gate is local:** voice activation and PTT switch a GainNode in `micPipeline.ts`, not the LiveKit track. The track stays published and "unmuted"; only the mute button uses LiveKit mute (visible to others). This avoids signaling on every word (PLAN 3.5).
- **Owners (several, 14 September 2026):** `server_settings.owner_id` = first owner (at first login, irrevocable), further ones via `members.is_owner` (`PUT /api/members/:id/owner`, owners only, not oneself). `actorOf()` sets `isOwner` from both, the bootstrap marks the first owner in `members` retroactively. Owners always have `ADMINISTRATOR`, rank above every role (`outranks`), cannot be kicked/banned/moderated and are at the very top of the member list. `Member.isOwner` in the protocol; `ServerSettings.ownerId` remains the first one.
- **Only with account (user requirement, 14 September 2026):** `server_settings.require_account` (migration 0011, admin panel > Server, `PATCH /api/settings`). `/api/auth/verify` rejects keys without a directory handle with 403 `account_required`; owners and the very first login are exempt (no lock-out), existing members without a handle are locked out too. If the directory is unreachable, the cached `users.handle` counts. Without `DIRECTORY_URL` the option has no effect and `/api/health` reports `requireAccount: false`; the admin panel disables the checkbox. **Forcing at deployment:** `REQUIRE_ACCOUNT=true|false` in the environment overrides the stored setting (`setRequireAccountForced()` in `state.ts`, applied in `loadSettings()`), `ServerSettings.requireAccountLocked` is then true, `PATCH /api/settings` with `requireAccount` answers 409 `locked_by_config`, the admin panel shows the checkbox disabled with a note. Empty = the admin panel decides. The login screen hides the browser-key path entirely for a key without handle (only "Mit Konto anmelden" remains, with a note); a key with a verified handle is an account and keeps the usual path.
- **Multi-server client (14 September 2026, user's requirement):** the web client of one server talks to other Squorli servers directly (`ServerApi` with `base` = their origin, WebSocket `wss://<host>/api/ws`, LiveKit URL from their `/api/rtc-token`). The rail switches the shown server without leaving the page; the voice connection stays on its server until the user joins a voice channel on another server, which disconnects the previous one. Login at a foreign server = the same browser key, signature over that server's `/api/health` domain, no invite (the rail only lists servers the handle is a member of); its session token is kept per host. Consequences: every chat server answers CORS for **all origins** (`@fastify/cors` `origin: true`, auth is Bearer-only, no cookies, so a foreign origin cannot act without the token; the signature stays bound to `PUBLIC_DOMAIN`), relative server URLs (attachments, icon) are resolved through `api.abs()`, older servers without CORS show "nicht erreichbar oder erlaubt keinen Zugriff aus anderen Clients" with a link to open them directly. The admin panel, settings dialog (sessions, name on this server; the mini profile too), member list and chat always act on the active server. Not multi-server: the login screen, the directory account and the friends/DM view (they belong to the own server's directory).
- **Server directory (M6d, 14 September 2026):** the chat server sends `name`, `listed`, `description` (max 200), `openJoin` and `memberCount` with every registration (`ServerRegisterRequest`); the directory fetches the icon itself from `<proofUrl-Basis>/api/server-icon` (host is proven, raster images up to 2 MB, `iconUpdatedAt` stays when the bytes are unchanged) and serves it under `GET /api/servers/<host>/icon`. Clients therefore load server icons only from the directory (`directoryServerIconUrl()`), never from foreign servers. Public listing `GET /api/servers` = servers with `listed` that registered within 3 days. Admin panel > Server: "Im Serververzeichnis auflisten" + Beschreibung (disabled without directory). Changing name/listed/description/openJoin/icon re-registers (debounced 1.5 s, registration limit at the directory is 10/min per IP). Join via link = open the server's own origin.
- **Login splash:** server icon and server name from `/api/health` at the top of the login card (fallback: Squorli icon mark and "Squorli"), footer "Betrieben mit Squorli · Version <version>" below the card; `version` comes from `apps/server/package.json` (read at startup, `../package.json` relative to `dist`/`src`, also in the container).
- **Server name and icon:** `/api/health` returns `serverName` and `iconUrl` so that title and favicon are already correct in the login; when logged in, `settings.name`/`settings.iconUrl` apply (live update via `structure`). Icon only as PNG/JPEG/WebP/GIF up to 2 MB (no SVG: could contain scripts and is served same-origin), file `DATA_DIR/server-icon`, URL with `?v=<timestamp>` and `immutable` cache.
- **Checking permissions:** Every protected route fetches `requireMember()` and checks `can(actor, Permission.X)`; effects on other members/roles additionally `outranks()`/`canTouchRole()`/`canGrant()` from `authz.ts`. The owner is always administrator. Structure changes end with `broadcastStructure()`. **Order and grouping of permissions (user's requirement, 17 September 2026, applies to every permission added from now on):** the role editor shows permissions in groups sorted by meaning (`PERMISSION_GROUPS` in `permissions.ts`: `admin` "Verwaltung" first with `ADMINISTRATOR` at its top (user's decision), then `text` "Kanäle und Nachrichten", `voice` "Sprache und Video", `members` "Mitglieder"; apart from `ADMINISTRATOR` a group runs from everyday to powerful; group titles from the `permGroup.*` keys, rendered as `fieldset.perm-group` in `AdminPanel.tsx`). The bit order is history and never the display order. Whoever adds a permission must sort it into the group and position where it belongs by meaning (next to related ones, e.g. watching before sharing), never simply append it, and must re-check the whole arrangement each time: does a group get too long, does a new group make more sense, are the group titles still accurate. A test in `index.test.ts` fails if a permission is in no group or in two. New permissions: append the bit in `permissions.ts`, add the label (`perm.*` in both catalogs), sort it into `PERMISSION_GROUPS`, and for existing servers write it into the appropriate role via a custom migration (`drizzle-kit generate --custom`) (see 0003/0004 as examples); the bit values are pinned in `index.test.ts`.
- **Media permissions twice:** camera/screen only with `STREAM_VIDEO` and without a block (`members.stream_blocked`, subtracted in `actorOf()`). The client hides the buttons, the app server writes `canPublishSources` into the LiveKit token (microphone always; camera, screen, screen audio only with the permission). LiveKit enforces it; on changes at runtime via `RoomServiceClient.updateParticipant` (`livekit/admin.ts`).
- **Watching camera/screen (`VIEW_VIDEO`, 17 September 2026, user's requirement):** a member without the permission receives only microphones, no camera, screen or screen audio. LiveKit has no per-source subscribe grant in the token (`canSubscribe` is all or nothing, `livekit-server-sdk` 2.19), so the restriction is set by the **senders**: every client calls `setTrackSubscriptionPermissions` for its own tracks and LiveKit enforces it, so a modified receiver cannot get around it. `voice/videoAccess.ts` computes the list from the server state exactly like `actorOf()` (OR of the member's roles and the default role, owners = administrators; `streamBlocked` plays no part): if the default role carries `VIEW_VIDEO` everyone is allowed (`allParticipantsAllowed`, nothing is sent per member); otherwise (the default, guests lack it) all members are listed, viewers with `allowAll`, the others with `allowedTrackSids` = the sender's microphone track ids (always set, because a missing list means "everything"; empty before the microphone is published). "Open" is decided by the default role and not by an empty list, so a member who joined seconds ago cannot slip through; participants who are no members (bots) get the microphone only. The list is re-sent when roles/members change (`App.tsx` effect -> `client.setVideoAccess`), when a local track is (un)published (republishing the microphone changes its id) and when an unknown participant connects; identical lists are skipped, the SDK repeats it after a reconnect. Receiver side: without the permission the client unsubscribes from video and screen audio (`applyVideoSubscriptions`), shows no remote tiles and the stage explains why. Limit: a sender running a client older than this change does not restrict its tracks; then only the honest receiver client holds back. The app server has no part in this beyond the bit in roles and `me`.
- **Moderation takes effect server-side:** stopping camera/screen = LiveKit `mutePublishedTrack` + WS `voice.stop`; moving = WS `voice.moved` (the client fetches a token for the target channel itself and joins, the server checks that like any join). Only with `MODERATE_VOICE`, never against the owner or oneself, rank must be higher.
- **Background blur:** `@livekit/track-processors` (BackgroundBlur, MediaPipe segmentation in the browser). Loads WASM from jsdelivr and the model from storage.googleapis.com; without internet on the client the effect does not work (self-host later via `assetPaths`). Check support via `supportsBackgroundProcessors()`; Firefox/Safari show the option disabled.
- **Separate output for screen audio:** `setSinkId` per `ScreenShareAudio` track (Chromium only). LiveKit's `switchActiveDevice("audiooutput")` re-routes all tracks, as does `MediaDevicesChanged`; `applyScreenSink()` therefore runs again after subscription, device change and settings change. The debug view shows device, track count and errors ("Bildschirm-Ton Ausgabe"); without a track (0) there is simply no remote share with audio yet.
- **Video (M3):** camera 720p with simulcast (180p/360p/720p, VP8), `adaptiveStream` + `dynacast` in the room: receivers get the layer that matches the size of the `<video>`. The stage only has to render the `<video>` at a suitable size. Screen share: 1080p30 (`ScreenSharePresets.h1080fps30`, up to 5 Mbit/s), **without simulcast** (otherwise adaptiveStream fetches the coarse layer for small tiles, text becomes unreadable), `contentHint: "detail"`. It always requests `audio: true` and publishes the audio as its own track (`ScreenShareAudio`), never mixed with the microphone; whether audio arrives is reported by `screenAudio` in the state, `explainScreenAudio()` provides the hint text. Cancelling in the browser dialog (NotAllowedError/AbortError) is not an error.
- **Database:** Change the schema only in `apps/server/src/db/schema.ts`, then `pnpm db:generate`. Migrations are applied automatically at server start; do not edit generated SQL files by hand.
- **Configuration:** Exclusively via environment variables, validated in `config.ts`. The server loads `apps/server/.env` via `process.loadEnvFile` (built into Node, no dotenv dependency); variables already set take precedence. In the container there is no .env file, everything comes via compose.
- **No new dependencies** without need; if necessary, pin the version as before (caret ranges) and commit the lockfile.
- **Directory service (M6):** The chat server never depends on the service: handle resolution at login is best effort (timeout 2.5 s, errors only logged), display falls back to the display name or `anon-<key>`. The web client calls the service directly (URL from `/api/health`, CORS open for GET/POST). Registration = signature over the service's host + handle + nonce; one key has exactly one handle, handles are immutable (M6a). The service itself (routes, schema, account page, smoke test) lives in `../squorli-directory` (section 2a).
- **Key backup (M6b):** The private key leaves the client only encrypted. `packages/protocol/src/backup.ts`: PBKDF2-SHA256 (600,000 iterations, 16-byte salt) -> HKDF into two keys: AES-256-GCM (encrypts the 32-byte seed, stays in the client) and auth key (is sent, the service stores only its SHA-256 in `key_backups.auth_hash`). Storing: `PUT /api/backup`, signed over "community-directory-backup\n<host>\n<nonce>\n<ciphertext>", upsert (= change password). Fetching in two steps: `GET /api/backup/:handle/params` (salt, iterations) -> client derives -> `POST /api/backup/fetch` with auth key -> blob with iv + ciphertext. Wrong password = 401 `auth_invalid`; rate limit `BACKUP_RATE_LIMIT` per IP **and** per handle (default 10/min), uploads have their own window. Password at least `BACKUP_MIN_PASSWORD` (8) characters, checked client-side only; no reset possible (the directory does not know it).
- **Account page of the service (`../squorli-directory/apps/directory/web/`):** deliberately without a framework (one script file, tsup), same colors as the client, German texts with umlauts, no browser dialogs. "Konto anlegen" (create account) first registers the handle and then stores the backup; if only the backup fails, the key stays in page memory and the next click repeats only the backup step; afterwards you are directly in the account area. "Anmelden" (sign in; handle + password, code if needed) fetches the seed into page memory only (never localStorage) and signs the account actions with it; "Abmelden" (sign out) nulls it. The chat client links the page in the login ("Noch kein Konto?", "Konto verwalten" with `?handle=`) and in Einstellungen > Konto and signs in with "Mit Konto anmelden": `api.directoryRestore()` fetches and decrypts, `store.loginWithHandle()` replaces the device key (with a confirmation via `askConfirm` if the previous one has a handle) and then logs in normally.
- **Second factor (M6c):** TOTP per RFC 6238 (own implementation `../squorli-directory/apps/directory/src/totp.ts`, no library) or recovery code; the service recognizes the form (6 digits = TOTP). Required, if `totp_enabled`, for `POST /api/backup/fetch`, `PUT /api/backup`, `totp-disable` and `recovery-regenerate`; **never at chat login by key** (the key is the factor). `totp_required` (401) comes only after a correct password or valid signature, so that nobody learns without the password whether an account has an authenticator; public responses (`/api/handles`, `/api/keys`) reveal nothing. Each TOTP step is valid once (`totp_last_step`, otherwise 401 `totp_reused`), window +-1 step; recovery codes are consumed atomically (`used_at`). Only failed attempts count against `BACKUP_RATE_LIMIT` per account (`RateLimiter.blocked()/hit()`), likewise only wrong passwords per IP/handle. The secret is stored AES-256-GCM-encrypted in the DB (`secrets.ts`, key `DIRECTORY_SECRET_KEY`, AAD = account ID); without the key `features.totp=false` and 503 `totp_unavailable`, recovery codes (SHA-256 only) keep working. Setup: `totp-setup` generates the secret (only with a backup, otherwise 409 `no_backup`), it becomes active only with `totp-enable` + code, which at the same time returns the 10 recovery codes (shown once). Signed account actions: `directoryActionMessage(host, action, nonce, code)`, body `SignedActionRequest`/`CodeActionRequest`; the code is part of the message so that it cannot be swapped.
- **Device management (M6c):** `sessions.id` is the public identifier (the token stays secret), `label` comes from the User-Agent at login (`labelFromUserAgent`, the client cannot set it), `last_used_at` is written in `resolveSession()` at most every 5 min. Remote logout deletes the row and closes exactly its WebSocket with **Close 4011 `session_revoked`** (`hub.disconnectSession`; kick remains 4010 + `removed`). The client reacts in `store.sessionLost()`: WS close 4011, WS error `unauthorized` and REST 401 with a token set (`api.onUnauthorized`) lead to the login with a message, without reconnect. `store.logout()` calls `DELETE /api/me/sessions/current` (best effort). No `PROTOCOL_VERSION` bump: close codes are not events. The directory knows no devices, only the list of key fetches (`key_fetches`, 90 days, display only): whoever has the key has it.
- **Account deletion through the directory (15 September 2026, user's wish):** a user deletes their account on one server from the directory's account page or via right-click on the server in the rail; both sign the action `server-leave` at the directory. The directory only relays: it pushes `{publicKey}` to `POST /api/directory/leave`, and the server confirms with its own token (`confirmLeave`) before deleting anything, so an unsigned push can at most trigger a check (same principle as `/api/directory/notify`). The first owner (`server_settings.owner_id`) is refused (`founder`), other owners and members are deleted completely (`users` row with cascade, attachment files, WS close 4012, no `removed` event and no `PROTOCOL_VERSION` bump: close codes are not events). Missed pushes are fetched via `pendingLeaves()` in the 5-minute sync. There is no local "delete my account" route on the chat server; the directory is the single entry point (the user's decision).
- **Security:** Do not weaken the auth path (single-use challenge, domain binding of the signature, session TTL). LiveKit secret at least 16 characters (schema), 32+ in production. `TRUSTED_PROXIES` only relevant in external mode.
- **Symbols only via `<Icon name="…"/>`** (Lucide web font, ISC license, self-hosted under `apps/web/src/icons/`), no emojis and no Unicode arrows in the UI (user requirement: uniform, white, license-free). Emoji as chat content and as the things to choose in the emoji picker (including its skin tone samples) are content, not UI symbols; the picker's own controls use `<Icon>`. Color = `currentColor`, size = `font-size`. Look up new names at https://lucide.dev/icons, then `pnpm icons`. Hang up = `phone` rotated by 135 degrees, white on red.
- **User settings follow the directory account, the device selection does not (17 September 2026):** a new user-level setting goes into `VoiceSettings` (or its own per-device store), into the protocol's `AccountSettings` **with a default** (older stored objects and older clients must stay valid; copy `directory.ts` to `../squorli-directory`), into `accountSettings.ts` (all three functions) and into `SettingsDialog.tsx`. Device ids never go into the account. Never add a second settings dialog: everything a user sets for themselves is reachable through the gear.
- **Categorized modals: categories always on the left** (user requirement 13 September 2026, applies without instruction to the contrary to all future modals with several sections). Building blocks: `.modal` > `.modal-head` (title, `.spacer`, close) + `.settings-layout` (`.settings-nav` on the left with `<Icon>` + label, `.settings-body` on the right). Examples: settings (`SettingsDialog.tsx`) and admin panel (`AdminPanel.tsx`). No tab bar at the top.
- **No browser dialogs in the client:** `alert`, `confirm`, `prompt` are taboo (user requirement). Confirmations via `askConfirm()`, text inputs via `askInput()` from `apps/web/src/dialogs.tsx`; both return promises and render their own modal (z-index above admin panel/profile). Show errors inline as `.error` text, not as a popup.
- **Tests:** Vitest, files `*.test.ts` next to the code. Pure logic (stores, schemas) via unit test; flows via `scripts/smoke.mjs`.

## 6. Architecture in brief

- One process: Fastify serves the API, the WebSocket (`/api/ws`) and the static web client (SPA fallback to `index.html`, unknown `/api/*` -> 404 JSON).
- Identity = Ed25519 public key; the first login creates the user (`onConflictDoUpdate`). What is signed is `community-chat-login\n<domain>\n<nonce>`, so `PUBLIC_DOMAIN` must match the hostname the client sees (dev: `localhost`).
- Media never passes through the app server: the client fetches `/api/rtc-token` and connects directly to LiveKit (`wss://<PUBLIC_DOMAIN>/rtc`, the proxy forwards `/rtc*` to `livekit:7880`). UDP 7882 / TCP 7881 must be reachable directly.
- Operating modes: `PROXY_MODE=bundled` (bundled Caddy with Let's Encrypt on 443) or `external` (own proxy, see `deploy/proxies/README.md`, status untested).
- The challenge store is in-memory (single node). Multi-node later via Redis.

## 7. Known pitfalls

- **Smoke test without a running server** fails with `ECONNREFUSED`; run `pnpm dev` or `node dist/index.js` first.
- **`PUBLIC_DOMAIN` must match the hostname in the browser address bar exactly** (dev: `localhost`; behind the proxy: `chat.example.org`; access via LAN IP: the IP). Otherwise `POST /api/auth/verify -> 401 (signature_invalid)`. `/api/health` returns `domain`; since the fix, the client shows both values in the error message. The smoke test always signs with `localhost`.
- **Windows:** `process.exit()` while WebSockets are still closing triggers a libuv assertion; the smoke test therefore waits for `close`. Follow the same pattern in future scripts.
- **Docker build from Windows:** without `.dockerignore`, the host `node_modules` end up in the build context; do not delete the file. `tools/` is deliberately excluded: the Dockerfile must not call `tools/icons.mjs`; the generated icon files under `apps/web/src/icons/` are in the repo and are sufficient.
- **`pnpm deploy` under pnpm 10** aborts without `--legacy` with `ERR_PNPM_DEPLOY_NONINJECTED_WORKSPACE` (the flag is in the Dockerfile).
- **`@squorli/protocol` has no build:** its entry is `src/index.ts`. The server therefore bundles it into `dist/index.js` via `noExternal`. Anyone who introduces further workspace packages as runtime dependencies of the server must add them to `tsup.config.ts` as well.
- **Testing the image locally:** `docker run --rm -p 3000:3000 --network squorli-dev_default -e PUBLIC_DOMAIN=localhost -e DATABASE_URL=postgres://chat:chat@postgres:5432/chat -e LIVEKIT_URL=http://livekit:7880 -e LIVEKIT_API_KEY=devkey -e LIVEKIT_API_SECRET=<32 characters> squorli/app:local`, then run the smoke test.
- **Background processes on Windows:** `tsx watch` and Vite survive a hard kill of the parent shell. `pnpm dev` (wrapper) cleans up via `taskkill /T`; anyone using `pnpm dev:apps` directly checks `netstat -ano | grep ":3000 "` and `taskkill //F //T //PID <pid>` before restarting. **Beware German Windows:** `netstat` prints `ABHÖREN` instead of `LISTEN`; filter with `grep -E "ABH|LISTEN"`, otherwise the cleanup finds nothing and an old test server (with an old protocol) stays on the port while the new one cannot bind.
- **"Batchvorgang abbrechen (J/N)?" on Ctrl+C** ("Terminate batch job (Y/N)?") comes from the cmd.exe shells that pnpm opens for `tsx watch` and `vite`. Cosmetic; the wrapper terminates them immediately. Do not answer with J/N.
- **Wrapper test:** Ctrl+C cannot be triggered from scripts via `kill -INT` (MSYS does not reach native processes). Tested with `GenerateConsoleCtrlEvent` from PowerShell; alternatively terminate the apps via `taskkill`, the wrapper then stops the containers through the exit path.
- **Port 3000/5173/5432/7880-7882 in use:** dev compose and the Vite proxy are hard-wired to these ports.
- **Compose project is called `squorli-dev` since 14 September 2026 (previously `community-chat-dev`):** if old containers are still running, they occupy 5432/7880-7882 and the new stack does not start. Run `docker compose -p community-chat-dev down` (without `-v`) once, then `pnpm dev`. The data volume is pinned in `compose.dev.yml` to the old name `community-chat-dev_pgdata-dev` and declared as `external: true` (Compose requires this for volumes from another project); `tools/dev.mjs` creates it via `docker volume create` before `compose up`, so that a fresh machine starts as well. Anyone using `pnpm docker:dev` directly must create the volume once themselves. The dev DB is preserved this way (verified on 14 September 2026: users and handles present after the switch). Containers are now called `squorli-dev-postgres-1` / `squorli-dev-livekit-1` (in all `docker exec` commands). For an already running prod stack (`community-chat`), the same applies to `deploy/compose.yml` (network `squorli_internal`, volumes not pinned: back up data first).
- **LiveKit dev container** runs with `--dev` (keys `devkey`/`secret`); `.env.development` deliberately uses a longer secret only for token signing; a real media connection is not yet part of the client in M0.
- **Directory service in dev:** `pnpm dev` in `../squorli-directory` (own Postgres on :5433, service on :3100); the chat server needs `DIRECTORY_URL=http://localhost:3100` in `apps/server/.env`. Chat smoke test with directory: start the chat server with `DIRECTORY_URL=http://localhost:3101` against a smoke instance there (see its AGENTS.md). Until 14 September 2026 the dev database `directory` lived in `squorli-dev-postgres-1`; the README there has the `pg_dump | psql` line for taking the data over.
- **`EADDRINUSE :3000` right after `pnpm dev` (fixed 14 September 2026):** `tools/dev.mjs` used to load the entire `apps/server/.env` via `loadEnvFile` into its environment, which all apps inherit. The directory service thereby got `PORT=3000` and the chat `DATABASE_URL`. Now the wrapper reads only `LIVEKIT_DEV_NODE_IP` from the file and passes it exclusively to Compose. Rule: the wrapper never sets app variables; each app loads its own `.env`.
- **`DIRECTORY_URL` missing in `apps/server/.env` after the update:** `.env.development` has it, an existing `.env` gets it by hand (`DIRECTORY_URL=http://localhost:3100`); without it the login shows "Dieser Server nutzt kein Verzeichnis" (this server does not use a directory).
- **Session "logged out from another device" in your own browser:** after "Alle anderen Geraete abmelden" (log out all other devices) or a `DELETE /api/me/sessions/:id`, the session currently in use is kept (`current`); anyone who gets thrown out anyway has two tabs with two sessions of the same key (every login creates a new session; a second tab only shares it via `localStorage`).
- **Smoke test against a test DB:** `docker exec squorli-dev-postgres-1 psql -U chat -d chat -c "CREATE DATABASE chat_smoke"`, then `PORT=3001 PUBLIC_DOMAIN=localhost DATABASE_URL=postgres://chat:chat@localhost:5432/chat_smoke npx tsx src/index.ts` in `apps/server` and `SMOKE_URL=http://localhost:3001 pnpm smoke`. This way the owner of the dev DB remains your own browser key.
- **Schema change while `tsx watch` is running:** the dev server restarts immediately after `schema.ts` is saved, i.e. before `pnpm db:generate` has generated the migration; it then runs against the old schema and queries on new columns fail (server stops responding). After `db:generate`, trigger a second restart (`touch apps/server/src/index.ts`), then the migrations are applied. Check: `SELECT count(*) FROM drizzle.__drizzle_migrations`.
- **Raw SQL with Date parameters** (`sql` + `${new Date()}`) fails in postgres-js; use `now()` in SQL.
- **Attachments are publicly retrievable by ID** (`/api/attachments/<uuid>/<name>`, no token), so that `<img src>` works. Like CDN links on Discord; the UUID is the secret.
- **White screen after deploy, "Expected a JavaScript module ... MIME type text/html":** the browser had the old `index.html` with the old asset hash in its cache. Since the fix: missing files with an extension get a 404 instead of the app shell, `index.html` is served with `cache-control: no-cache`, hashed assets with `immutable`. The user must hard-reload once after the fix. Run `pnpm build` (root) after every client change, otherwise an old client sits in `apps/server/public`. Second cause (fixed): `@fastify/static` ran with `wildcard: false` and registered one route per file at startup; new assets after a build without a restart got a 404. Now `wildcard: true`, files are resolved per request.
- **`Route GET:/ not found` (Fastify 404 on `/`):** the server is running without a built web client. Since the fix, `/` answers with 503 and an explanation; the cause is a start without `pnpm build` (missing `apps/server/public`) or an old Docker image. `/api/health` works regardless.
- **Server icon gone after emptying `apps/server/data`:** the DB still had `icon_mime`, so favicon, sidebar, login and server rail showed a broken image (happened 14 September 2026). Since the fix the settings routes check at startup whether `DATA_DIR/server-icon` exists and otherwise clear the entry with a warning; upload the icon again in Verwaltung > Server. When emptying the data folder, keep `server-icon` or expect this.
- **`apps/server/public/` and `apps/server/.env` are gitignored**; never commit them. New variables in `.env.development` must be copied by hand into the existing `apps/server/.env` (e.g. `LIVEKIT_PUBLIC_URL`).
- **"could not establish signal connection" / Safari "Load failed":** the client cannot reach the LiveKit URL issued by the server. Usually `apps/server/.env` still contains `LIVEKIT_PUBLIC_URL=ws://localhost:7880` from `.env.development` while the server runs publicly. Remove the variable (default `wss://PUBLIC_DOMAIN`, the proxy forwards `/rtc`). The server warns about this combination at startup; the client names the URL in the error message and in the debug view. Second cause: `LIVEKIT_PUBLIC_URL=wss://domain:7880` (port 7880 does not speak TLS and is not exposed; correct is without a port via the proxy). Third cause: the proxy does not forward `/rtc` (`/rtc/validate` must return 401).
- **Participant drops out of the channel after ~15 s:** the signal connection is up, media (ICE) never gets established, LiveKit disconnects with CONNECTION_TIMEOUT/UNKNOWN. Causes: 7882/udp + 7881/tcp not forwarded to the chat host, LiveKit does not know its public IP (`LIVEKIT_NODE_IP`), or the dev stack is running with `--node-ip 127.0.0.1`. The client shows the disconnect reason as an error and logs room events in the debug view; on the server, search `docker logs <livekit>` for "ice" / "connection timeout". SIGNAL_CLOSE, by contrast, = WebSocket closed (proxy timeout, network switch, phone in the background).
- **LiveKit URL for clients without `/rtc`:** livekit-client appends `/rtc` itself. `wss://domain/rtc` would result in `/rtc/rtc` and fails. The server delivers `LIVEKIT_PUBLIC_URL` or `wss://PUBLIC_DOMAIN`.
- **LiveKit in Docker on Windows/macOS:** without `--node-ip`, LiveKit offers the internal container IP as ICE candidate, and browsers on the host then get no media. `compose.dev.yml` sets `--node-ip ${LIVEKIT_DEV_NODE_IP:-127.0.0.1}`; `tools/dev.mjs` loads `apps/server/.env` for this. For a second device in the LAN set `LIVEKIT_DEV_NODE_IP=<host LAN IP>`, for tests from outside the public IP, and open the client from that device via the LAN IP (then `localhost` is no longer a secure context: microphone only with HTTPS, see PLAN 5 mkcert).
- **LiveKit dev secret:** `--dev` sets `devkey`/`secret`; the container receives the longer secret from `.env.development` via `LIVEKIT_KEYS`, because `config.ts` requires at least 16 characters. Token check without a browser: `GET http://localhost:7880/rtc/validate?access_token=<jwt>` must return 200.
- **Browser autoplay:** audio from other participants may be blocked until the user clicks once; the client then shows "Ton freigeben" (unblock audio) (`room.startAudio()`).
- **Choosing an output device** (setSinkId) exists only in Chromium; Firefox/Safari show an empty list.
- **Screen share without audio:** only Chromium delivers audio, and there only with "Tab" (tab audio) or on Windows with "entire screen" with system audio enabled; individual windows never. Firefox/Safari never. The stage shows a yellow notice in both cases. The matrix in PLAN 3.6 is checked with `/test/screenshare.html` per browser/operating system and recorded there.
- **`docker stats` does not measure the load test:** `pnpm bots` attaches itself to the network namespace of the LiveKit container; the media traffic runs over loopback and does not show up in NET I/O. Read the bandwidth from the `lk` table (subscriber) or from the debug view in the client.
- **`@types/dom-mediacapture-transform`** is a peer dependency of `@livekit/track-processors` (types for MediaStreamTrackProcessor); as a devDependency in the web package, otherwise `tsc` breaks.
- **Fresh database had only the role "Mitglied" (fixed 14 September 2026):** migration 0004 creates "Mitglied" in empty databases as well; since then the bootstrap no longer checks for "no roles" but for "no default role" and creates Gast/Admin/Mitglied individually as needed. Check the fresh-install path: recreate `chat_smoke` from scratch via `DROP DATABASE ... WITH (FORCE)` + `CREATE DATABASE` and run `pnpm smoke` (not only against an incrementally migrated DB).
- **Resetting the dev database** (new owner at the next login): `docker exec squorli-dev-postgres-1 psql -U chat -d postgres -c "DROP DATABASE chat WITH (FORCE)" -c "CREATE DATABASE chat OWNER chat"`, empty `apps/server/data/attachments`, then `touch apps/server/src/index.ts` (migrations + bootstrap run only at startup). The database `directory` in the same container is the old dev database of the directory service (before the move); leave it until the data is taken over into `../squorli-directory`.
- **Only guest after joining:** anyone who cannot write does not yet have the "Mitglied" (member) role. An admin assigns it in the member list (click on the name). This is intended (decision of 13 September 2026), not a bug.
- **Production compose always with `--env-file ../.env`:** `env_file:` in the service only covers the container environment; the `${POSTGRES_PASSWORD}`/`${LIVEKIT_API_KEY}` placeholders in `compose.yml` are filled by Compose only from `deploy/.env` or the `--env-file`. Without the flag: empty DB password, `LIVEKIT_KEYS: ": "`. Check with `docker compose --env-file ../.env ... config`.
- **external mode publishes no HTTP ports.** A proxy on the host needs the overlay `proxies/nginx.ports.yml`; a proxy in a container attaches to the network `squorli_internal`.

## Standard container installation

The default user installation requires no Git clone, Node.js or application build. Download only .env.example, deploy/compose.yml, Caddyfile, livekit.yaml and the optional nginx port overlay into a fresh squorli directory. Configure .env with APP_IMAGE and the matching proxy mode, then run Compose pull and up --no-build from squorli/deploy. Updates pull the image without git pull; never overwrite existing secrets by repeating the initial download. Source cloning and --build belong only to a separate optional developer workflow at the end of both public guides. Both languages must stay equivalent.
